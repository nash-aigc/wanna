# 18 · 状态类问题的查法：**该写的那一格没人写**

> 触发这一篇的是 2026-09-27 那个 bug：「语音播放的过程中打断它，界面没有回到最开始那个样子
>（刘海下面应该有一行字幕）」。
>
> 它是一条**可复用的方法**：症状发生在屏幕上，原因却在状态机里 —— 而且**不是写错了，是没人写**。
> 这一类问题在这个仓库已经出现过好几次（相位、`voiceState`、`isActivityPhaseHeldAtIdle`、
> `expansionProgress`），所以把查法单独立一篇。

---

## 一、先把症状翻译成**一句判据**

「打断之后字幕那一行没出现」这句话没法直接查。要问的是：

> **画出那一行的判据是什么？此刻它算出来是几？**

在这个仓库里那句话是（`NotchPanelModel.notchBandSitsAboveTranscriptLine`）：

```swift
activityPhase == .listening && !isFullscreenSuppressed
```

翻到这一步，问题就从"界面"变成了"**`activityPhase` 此刻是什么、谁写的**" ——
这是这个方法的全部：**先从视图往上找到一个可以直接读的布尔量，再顺着它去找它的输入。**

⚠️ 不要跳过这一步直接去 `OverlayWindow` / `NotchActivityView` 里找"为什么没画" ——
视图那一层是**结果**，它照判据办事，没有 bug 可找。这个仓库里"改了半天界面没反应"的几轮，
全都死在跳过这一步上（见 `13-顽固问题排查法.md`）。

## 二、把**这个字段的所有写入者**列出来

```bash
grep -n "voiceState = " Wanna/CompanionManager.swift
```

然后拿生命周期对着看：按下说话 → 出声 → 播完 → 打断 → 追问 …… **每一个事件有没有对应的
写入者**。这一次列出来是这样：

| 事件 | 谁写 |
|---|---|
| 开始听 | `startPushToTalk…` 那条 → `.listening` |
| 第一次出声 | TTS 的 first-audio 钩子 → `.responding` |
| 播完 | `scheduleVoiceStateResetAfterPlayback` → `.idle` |
| **用户说话打断** | **没有** ← 就是它 |

**"没有"这一步就是根因**，而且它长得不像 bug：代码里那一格是空的，不是错的。
所以这一类问题的症状永远是"**该出现的东西没出现**"，而不是崩溃、不是报错、不是值不对。

## 三、为什么没人写？—— 去找**那条挡在前面的规矩**

`voiceState` 有一条写在注释里的规矩：「**第一次出声时置 `.responding`，别的一律不许清**」。
它是**对的**：`scheduleVoiceStateResetAfterPlayback` 靠它认出"这是我这轮的回答播完了，
可以收尾了"；谁都能清它的话，那个任务就会在别的时候把正在播的回答收掉。

但它划出了一块空白：**"打断"这个事件既不是"开始听"、也不是"播完了"，它没有合法的写入者。**
于是打断之后发生的是：

1. 播报被停 → `isPlaying == false`；
2. 那个收尾任务（200ms 轮询）立刻认为"播完了" → 写 `.idle` + `forceActivityPhaseIdle()`；
3. 用户明明在说话，屏幕上是**一片 idle** → 判据算出来 false → 那一行不画。

**要记住的规律**：一条规则本身正确 ≠ 它覆盖了所有路径。**遇到"这个字段在这个场景下没人动"，
先去找那条"不许动它"的规矩** —— 然后问："那么谁来动？" 答案通常是：**这条路径自己**。

## 四、修法：只补**缺的那一次写**

```swift
switch voiceState {
case .processing, .responding: voiceState = .listening   // 它在忙（播报中 / 还在想），我插话
case .idle, .listening: break                             // 没在忙 / 已经在听，不动
}
```

补上之后**下游全是自动的**：`$voiceState` → `refreshActivityPhase()` → 相位 `.listening`
→ `syncListeningTranscriptPanel()` → 面板 `show()`（顺手清掉上一轮的字）→ 那一行出现、
两翼下圆角收直。

**不要顺着症状去下游加补丁**（"在 OverlayWindow 里判断一下正在打断就把它画出来"那种）——
那是第二个真相，而下一次改判据时它一定会漂。这个仓库为"两个地方各写一遍"付过的代价，
`10-踩过的坑.md` 里到处都是。

顺带一条小的：**别手动去取消那个收尾任务**。它自己有一条 `guard voiceState == .responding`，
状态一改它就自己让路 —— 先读它有没有这种自我保护的 guard，再决定要不要动手。

## 五、这一类问题的清单（照着做）

1. **找出判据**：屏幕上那个东西由哪一句布尔表达式决定？（找不到判据 = 还没读懂这块）
2. **读出它此刻的值**：日志/探针/AX（别用眼睛猜）。
3. **列这个字段的全部写入点**，对着生命周期找**空格**。
4. **找到那条"不许动它"的规矩**，确认它是为别的目的立的、不是错的。
5. **只补那一次写**，然后验证下游是否全部自动跟上（跟上了说明补对了位置）。
6. **写进 `10-踩过的坑.md`**：现象 → 判据 → 空的那一格 → 规矩 → 补的那一次写。

## 六、这个仓库里同一类的先例

| 症状 | 空着的那一格 |
|---|---|
| 「回复播完之后刘海等两秒才消失」 | 收尾那条路没有"这是一个 ENDING"的声明（后来补了 `forceActivityPhaseIdle`） |
| 「按 ESC 还是显示 thinking」 | ESC 没有把相位按住（后来补了 `holdActivityPhaseAtIdle`） |
| 「展开过程中窗口 frame 被改」 | 展开完成后没有承诺"这一帧就是最终帧" |
