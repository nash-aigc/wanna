# 开发经验

**这个仓库只有这一处沉淀「学到的」。** 踩坑、实测数字、复盘、事故分析全在这里 —— 不再有「解决方案/」「方案/」那些平行目录（2026-09-26 合并，只搬文件、没改内容，所以根目录里会出现重复的序号，那是两套编号叠在一起）。

读者是**下一个要改这块代码的 AI**，不是用户。所以规矩是：**把事情讲清楚就够，不要写长。** 一篇该有的是「现象 → 根因 → 修法 → 怎么验证」，不是过程叙述。

想知道这个 app 是什么、有哪些子系统、改代码要走什么流程，看 [`../AGENTS.md`](../AGENTS.md) —— 它同时就是 `../CLAUDE.md`（软链，同一个文件）。

## 以后怎么记：**修完就写，不用等用户提醒**

**任何时候一个 bug 修好了、一个功能落地了、一次排查有结论了，就把它写进来。** 这是这个仓库自己的规矩，和「改完代码要自己编译、自己重启」同级 —— **不需要用户说，也不需要等用户问。**

写在哪：

| 是什么 | 写进哪 | 里面该有什么 |
|---|---|---|
| **踩过的坑** | [`10-踩过的坑.md`](10-踩过的坑.md) | 现象、**根因**（不是把现象复述一遍）、修法。根因还没查清就先写「还没查清 + 已经排除了什么」 |
| **量到的数字** | [`09-实测数据.md`](09-实测数据.md) | 数字、**日期**、**测法**（怎么复现）。没量过的一律写「推测」，不许写成结论 |
| **一条子系统的经验** | 对应那篇（光标 → [`../全局框架/02-光标与覆盖层.md`](../全局框架/02-光标与覆盖层.md)、语音 → [`../全局框架/05-语音管线.md`](../全局框架/05-语音管线.md)、操作电脑 → [`../全局框架/11-操作电脑.md`](../全局框架/11-操作电脑.md)…） | 改它之前必须先知道什么 |
| **一整件事**（用户可见的功能、几轮才落地的方案、一次事故复盘） | 本目录根下新开一篇 | 需求 → 根因 → 方案 → 怎么验证。该长就长，但别为了长而长 |
| **可复用的排查方法** | [`00-问题根因排查法.md`](00-问题根因排查法.md) / [`13-顽固问题排查法.md`](13-顽固问题排查法.md) / [`18-状态类问题的查法.md`](18-状态类问题的查法.md) | 下次遇到说不清的问题时照着做 |

三条硬规矩：

1. **只写这个仓库里真实存在的事实。** 代码里没有的 API、没跑过的流程，不写。
2. **文档和代码一起提交。** 过期的文档比没有文档更坏 —— 改了哪个子系统就顺手更新那一篇。
3. **写规律，不要只写这一次的结论。** 「锚定 X 就错了」比「这次是 X 不对」有用十倍。
