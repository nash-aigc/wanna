# 给 Python agent 装本地追踪（2026-09-29）

用户选的方案，以及**两个只有真跑才会发现的坑**。

## 一、为什么不是"官方首选"

官方对**非 OpenAI 模型**的首选是零代码那条：给 exporter 一个 OpenAI key，
用官方 Traces 面板（原文：*"you can provide an OpenAI API key to the tracing
exporter to enable free tracing in the OpenAI Traces dashboard"*）。

**否掉它的理由是数据**，不是复杂度 —— 一个 span 里装的是：

```python
class FunctionSpanData:
    __slots__ = ("name", "input", "output", "mcp_data")
```

`input` = 工具参数，`output` = **工具返回** —— 对我们就是 `read_screen` 读到的
**整棵界面文本**、`read_file` 读到的**文件内容**。传到 `api.openai.com` 就是外发。
**这个仓库已经因为同样的理由删过一次 PostHog。**

顺带查清一条**容易想当然的**：DeepSeek 这类"OpenAI 协议"的 key **不管用** ——
`BackendSpanExporter._OPENAI_TRACING_INGEST_ENDPOINT` 写死是
`https://api.openai.com/v1/traces/ingest`，而 `/v1/traces/ingest`
**不属于"OpenAI 兼容协议"**（那只覆盖 chat/completions 那一类）。
"协议兼容"不等于"这家实现了我需要的每一个端点"。

## 二、坑 1：`add_trace_processor` ≠ `set_trace_processors`（**语义相反**）

官方对两者的区别写得很清楚：

- `add_trace_processor()` —— **追加**一个，**默认那个往 OpenAI 发的仍然在**
- `set_trace_processors()` —— **替换**，不装 OpenAI 的 exporter 就一个字节都不发

第一版我差点用 `add_trace_processor`（名字听起来更"温和"）。**用了它等于没改** ——
本地写了一路，同时每一轮还在往 api.openai.com 发一路，而且**屏幕上完全看不出来**。
判据：**这类"加一个处理器"的 API，永远先确认它是追加还是替换。**

## 三、坑 2：不收缩的话一条 `screenshot` 就是 344 KB

真跑一轮，日志 **377 KB / 17 条 span**。统计下来一条 `function` span 占了 **344 085 字节**
——`screenshot` 的返回是整张图的 base64：

后果两条，都是静默的：
1. 日志几轮就把 2MB 轮转顶掉，**想查的那一轮已经被冲走了**；
2. `grep` 出来是一屏乱码，**等于没记**。

修法是逐字段收缩：一串 200 以上的 base64 字母数字（或 `data:` 开头）整段换成
`<省略二进制内容 N 字节>`，其余长文本 4000 字符截断。

**改完 377 KB → 44 KB**，而且真能看了 —— 每条带毫秒耗时
（实测 1300 / 696 / 989 / 1035 / 593 ms），这是在这之前**完全没有的数**。

## 四、它补的是什么

在此之前 Python 那一侧我只有 `{"type":"step","tool":"click"}` 这种一行 ——
**没有耗时、没有参数、没有返回**。所以用户问"它为什么没做那件事"时，
我在 Python 那侧基本是瞎的，只能推。

现在每一次 run 的每个模型步骤、每次工具调用，**输入输出和耗时都在一个文件里**。
形状上它不是新东西：这个仓库已有 `主Agent诊断.log`（Swift 那条链）和
`录音诊断.log`（录音那条），这一条是把同一条规矩延伸到 Python 那一侧。
