## 一、需求（用户的原话与逐条拆解）

### 1.1 一句话

> 主 Agent 的快捷键按下之后，整个**这两张卡片**分别是做什么用的？上面的右上角这张卡片是
> **实时的显示 AI 对用户的任务的理解**，让用户看到是不是正确的理解。

### 1.2 两张卡片的分工（用户 2026-09-27 定稿）

| | **右上角**（鼠标右上方） | **右下角**（鼠标右下方） |
|---|---|---|
| 存在的时段 | 按下快捷键 → 发送之前（含追问窗口） | **同一段** |
| 是什么 | **AI 对任务的理解对不对** | **答案预览**：对用户提问的回答 |
| 内容 | 选项 / 理解四行 / 输入框 / 取消三列 | 一段答案（与最终结果同一张卡片） |
| 交互 | 点击确认·否定、口述、键盘输入 | 只读 |
| 发送之后 | 收起 | 让位给真正的结果 |
| 打断或答完继续说 | 两张一起重新出现（"大循环里的小循环"） | 同左 |

### 1.3 逐条需求

**A. 选项（"任务方向"）**

1. **只有一个来源**：「就是一个固定的文件。我记得之前我是添加了 3 个还是 4 个来源，什么实时的，
   **这都不要**」。这个文件可以被三种方式改：**AI 之后改**、**人手动改**、
   **每天中午 12 点复盘 agent 定时追加**（先去重再追加；扫用户全部历史记录与聊天记录，
   出现**超过两次**的才收成 **3~7 个字**的选项）。
2. **判断用 JEV 决策模型**，是**实时**的：「因为用户的提示词一直在变，所以说它根据用户的提示词
   变化来去判断出来用户当前正在做的事情到底是什么」。
3. **选项可不显示**：「用户的需求可能是全新的，它会导致这些选项……显示不出来，那么如果显示不出来的话，
   就**不要去强制性的显示**」。
4. **点击与口述都要保留**：「这个表格里面这些选项它可以被点击的……或者是可以被否定，对不对？
   这个要**保留**」。

**B. 固定（用户明确说过的方向）**

5. 「只要用户明确的说哪一个方向对，哪一个方向不对，就要把这个最终确定的……**一定要去在卡片上显示，
   无论是对还是不对都要显示**」。**没说过的可以自由替换、自由轮换**。
6. 固定**保留到用户说取消**（「除非在用户下一次说取消任务方向一……」）。

**C. 两拍语义**（用户讲得最清楚的一段）

7. 「这 3 秒呢，同时调用了 JEV 模型，也同时调用了大语言模型……而这个理解是由大语言模型在
   **第二轮**……**你必须要知道用户表达的是对上一轮 JEV 模型它的结果的一个选择**」
   → 用户对选项的评论**由大模型在下一轮读懂**，并且它说的编号指的是**上一轮那一列**。
8. **跨轮连续性**：「你要在发送给下一轮模型的时候要**保留前三轮**，然后你要标记一下……
   最早的那一轮和最近的那一轮分别是什么，然后让它**重点参考最近一轮**」。

**D. 理解四行**

9. 格式固定、**换行显示、可多行**：「AI 对任务的理解是有格式的，比如软件是什么、文件是什么、
   目标是什么、类型是什么、细节是什么」；随后收敛成用户点名的四行
   **目标问题 / 类型 / 参考 / 细节**（「第三行是内容参考，或者叫参考……**它就是两个字**」）。
10. **不许跳**：「他回复结果的时候**总是跳、总是蹦**……内容有时候有软件目标细节，有时候没有，
    就是突然间有、突然间没有。**这几行固定在这**……这对体验影响太差了」。
11. **要有动画**：「这个卡片返回的结果是**一次性返回**的……我希望让它有一种**动画效果**，
    而不是突然间显示出来」。

**E. 右下角答案预览**

12. 「鼠标右下角这部分显示的是对用户提示词回复的一个**结果**……右下角这卡片其实就是一个
    **答案的预览区**」，而且「跟正常的这个任务执行之后返回结果的**卡片的动效、文字的效果渲染效果
    是一样的**」。
13. 判据是**有没有问题**：「你就要去识别出来用户的意图里面是不是**包含问题**」
    （「北京在哪」「杨幂是谁」「左右两张图有什么区别」「这道题选 A 还是 B」）。
14. 参考材料要**打标签**：屏幕截图 + 用户提示词 + 已确定的选项 + 右上角卡片的内容，
    **以用户的提示词为目标**。
15. **每轮都要能看见屏幕**（这是他实测报回来的）：「他为什么会显示**没有看到屏幕**呢？
    **他应该直接看到屏幕啊**」。
16. **不朗读**（我定的：他正在说话，念出来会和麦克风打架 —— 见 §5 的取舍清单）。

**F. 发送（按下第二次 / 静音自动发送）**

17. 发什么：「如果用户明确的说了哪一个选项，那个选项的时候**才去发这个选项**，
    **如果没说的话就不要发**……你也不要去把什么猜测的比例概率什么……也不需要去发送」；
    「这个词跟**描述**的部分就会作为提示词的一部分来去发给 AI」；
    「这个大语言模型的理解，你可以去发，发过去」。
18. **转写后面加一段固定说明**：「必须要去再增加一个……系统提示词，来去备注到用户的刚才
    **整段转写的文本的后面**，然后去让 AI 理解到其中用户关于……方向一、方向 2、方向 3，
    他是关于这个某一个位置卡片的任务的理解，然后这部分**不是真正的要去执行的任务**……
    **你帮我梳理出来一个这个提示词是固定的就可以，不需要实时生成**」。
19. 发送之后**两张卡片一起消失**，主 Agent 的结果照常落右下角。

**G. 取消**

20. 板子最下面一行三列：**取消本次 / 取消十分钟 / 取消今日**（今日 = 到明日凌晨 0 点，不是 24 小时）。
21. 总闸门也可以口述：「取消任务看板」或「取消任务方向」（**必须精准**，「取消任务」四个字不算）。
22. ESC = **全部取消**：后端监控、两张卡片、所有进程。

## 二、设计（为什么是这个形状）

### 2.1 一次请求，三节输出

每 3 秒那一轮**只调一次大模型**（用户：「同时也调用了一个大语言模型」），它一次产出三样：

```
目标问题：…   类型：…   参考：…   细节：…     ← ① 理解四行（画在右上角）
答案：…                                        ← ② 答案预览（画在右下角，没有就不写这一行）
选择：1 对，3 不对                              ← ③ 对上一轮选项的判定（没有就不写这一行）
```

三节**各自解析**（`DirectionBoardPrompt.parseUnderstandingLines` / `parseAnswer` /
`DirectionBoardMatching.parseSelectionVerdict`），任一节缺失不影响其余两节。
选这个形状的理由：省钱（一次调用 vs 三次）、延迟低（答案与理解同时到）、
而且**三样本来就共享同一份输入**（用户的话 + 屏幕 + 方向清单 + 上一轮那一列）。

### 2.2 两拍判定：为什么必须记「上一轮那一列」

- 第 N 轮：JEV 按概率选出 1..N 格 → 画在板上；
- 用户说「方向一对、方向二不对」；
- **第 N+1 轮**的请求里带上「上一轮显示的是哪几格」（编号 → 关键词 + 当前状态），
  模型回一行 `选择：1 对，2 不对`；
- 代码用**上一轮的编号映射**回填固定状态。

**为什么不能按当前屏幕的编号回填**：JEV 每 3 秒重判一次，用户说话的这几秒里那一列**可能已经重排**。
所以 `DirectionBoardSession` 存一份 `previousRoundItems` 快照，
`parseSelectionVerdict(_:previousRound:)` 收的就是它。有单测钉着这条
（含"上一轮第 2 个这一轮已经换人"的情形）。

**由此删掉的东西**：本地那一整套"口述第 N 个方向"的正则解析（`spokenSelectionNumber` /
`spokenCancelSelectionNumber` / `applySpokenSelectionIfAny`，以及曾经为了修"说第二个方向却选了两格"
而加的编号映射表）。口述统一走大模型那一拍、**点击仍然是瞬时的**。
只有**总闸门**（「取消任务看板」）继续本地判定 —— 它要立刻生效。

### 2.3 显示规则：固定项在前，且"对"和"不对"都留着

```
[ 固定的（按固定顺序，编号 1..k，✓ 或 ✗）] + [ JEV 过阈值的（可轮换，编号接着排）]
```

- 固定项**不参与 JEV 提问**（状态已知，省一次判断）；
- 列数满了（默认最多 10 格、屏幕上一行 5 列）**先砍 JEV 那部分**，固定项一个都不砍；
- 用户没提过的那些**可以自由轮换** —— 这正是他说的"其他没有说过的……都可以自由的替换"。

### 2.4 数据放在哪

| 数据 | 文件 | 为什么在这 |
|---|---|---|
| 方向清单 | `~/Library/Application Support/Wanna/TaskDirections.json`（0600） | 用户说它只由 AI / 人 / 复盘改，所以**只有那三个写入口** |
| 用户的固定状态 | 同目录 `TaskDirectionPins.json`（0600） | 他选的是"一直保留到说取消"（跨大轮、跨对话），所以要落盘；而**不写进清单** —— 清单要保持是"一份可读的备选项列表" |
| JEV key | 同目录 `JevKey.txt`（0600） | 不进 `AppSettings`，所以**导出设置不会把它带出去** |

三个文件都是同一个形状：`nonisolated` + `NSLock` + 原子写后补 0600 + 变更通知（仓规）。

⚠️ 一个死锁的坑：`TaskDirectionStore` 的**公开入口只加一次锁**，内部一律叫 `…Locked`
（假定已持锁）。第一版是 `allDirections()` 持锁 → `loadFromDisk` 里又调 `write` 再锁一次，
`NSLock` 不可重入 → **第一次读清单就死锁**，App 卡死在 Listening。

### 2.5 节奏闸门（三条，都是用户要的）

每 3 秒看一次，但**要同时满足**才发：

1. 识别文本**变了**（用户：「检测这 3 秒之内用户的提示词是否跟上次相同，如果相同就不发送」）；
2. **新增 ≥10 个字**（标点不算；用户：「如果 3 秒之内用户新增的内容少于 10 个字，也不发送，
   因为相当于这句话还没说完」；阈值在设置页可调 5…20）；
3. 同时**最多一个请求在飞**（代次计数丢弃过期回复）。

### 3.4 关键类型

```swift
// 一条方向（清单里的一行）
struct TaskDirection { id; keyword; detail; matchKeywords: [String]?; source; addedAt }

// 用户明确说过的判定（存 TaskDirectionPins.json）
enum TaskDirectionStore.PinState { case confirmed, denied }

// 板上的一格（每一轮算出来）
struct DirectionBoardDisplayItem {
    directionID; keyword; number;          // number 从 1 开始、连续
    state: .pending / .confirmed / .denied
    reason: .pinnedByUser / .localKeyword / .jevProbability
}

// 提交时带走的东西
struct DirectionBoardTurnDecision {
    confirmedDirections: [(keyword, detail)]
    typedInput: String
    understanding: [(label, value)]
}
```

### 3.5 提示词

**系统**（`understandingSystemPrompt`）只给方向清单（约三百 token，不是主 Agent 那五千字）+
那三节的格式要求 + 「每一轮都带了当下的屏幕截图，请**看图**再回答……**看不到就照实说，不要编**」。

**用户消息**（`understandingUserPrompt`）三块：用户说的话 / **上一轮显示的那一列**（编号 + 关键词 + 状态，
并说明"如果用户在评论这些方向，请按**这套编号**理解"）/ **最近三轮的理解**（标「最近一次 /
倒数第二次 / 倒数第三次」，写明以最近一次为主）。

**发送时的两个块**（`DirectionBoardPrompt.decoration` + `boardReferenceNote`）：

```
<user_intent_tags>
用户真实意图的任务方向是：看图说话（看屏幕或某张图，描述/识别里面有什么）
模型对这次任务的理解是：目标问题：…；类型：…；参考：…；细节：…
用户的补充说明是：…
</user_intent_tags>

<screen_contents> …（图形界面读取，如果有）… </screen_contents>

the user just said, out loud: <用户原话>

<board_reference>
上面这段转写里出现的「方向一 / 任务方向 3 / 第 4 个」这类说法，是用户在跟屏幕上那块任务方向看板
交互（确认或取消某一条方向），**不是**要你执行的任务本身 —— 请忽略这些片段，只按其余的话执行。
</board_reference>
```

### 3.6 三个解析器（最容易静默出错的地方）

| 解析器 | 契约 | 已踩过的坑 |
|---|---|---|
| `parseUnderstandingLines` | **永远返回四行**（缺的值是空串），按用户定的顺序 | ① 模型把四行写在**同一行**里（要按标签位置切）② `目标问题:` 里嵌着 `目标:` 与 `问题:`（要去重叠，否则那一行被切成三段空值）③ 模型写回老标签（`软件`/`文件`/`目标`）—— 每行带一串**别名** ④ 「答案」「选择」是**边界标签**：只截断、不成行 |
| `parseAnswer` / `parseSection` | 取「标签:」到行尾或下一个标签处，最多续两行；**没有就返回 nil** | 解析读的必须是**原文**，不是被 200 字上限截过的显示文本（否则「细节」写到一半就断了） |
| `parseSelectionVerdict` | 按**上一轮的编号**回填判定；认阿拉伯与中文数字 | ① 不能按空格/逗号切（`1 对，3 不对` 会被拆成四段、每段缺一半）② `取消 2` 的判定词在编号**前面** → 取"两个编号之间那一段" ③ 越界的编号直接忽略（不猜） |

### 3.7 视图与那两块窗口

**卡片四段**（自上而下）：编号方向格（多列，最多 5 列）/ **理解四行**（标签列定宽 50，
空值画 `—`）/ 三行输入框 / 暗红三列取消（分割线**纯白**、1.5×20）。

- **高度恒定**：四行永远画着（即使是占位符），所以模型怎么写卡片都不跳；
- **淡入**：每行的值带 `.id(value)` + `.transition(.opacity + offset(y:6))`，
  外层 `.animation(.easeOut(0.28).delay(行号 × 0.05))` —— **逐帧验过**（回复落地那一刻连拍五帧，
  第一帧占位符正在上移、错开不同高度，末帧就位，骨架全程不动）；
- 宽度 = 340 × 设置倍数（默认 2 → 680），**与内容无关、恒定**。

**那块面板**（`DirectionBoardPanelController`）三条分寸：

1. **不抢键盘**：`orderFrontRegardless()`，绝不 `makeKey()`；`becomesKeyOnlyIfNeeded = true`
   —— 只有点了输入框才是 key；
2. **尺寸归 SwiftUI、位置归我们**：`NSHostingView` 会按内容改窗口尺寸（
   `updateAnimatedWindowSize` ← `windowDidLayout`）而且**保持顶边** —— 实测它把窗口一路推到
   `AppKit y = -7`（底边掉出屏幕，卡片最下面那行被切）。所以订阅 `NSWindow.didResizeNotification`，
   每次改尺寸之后用「锚点 + 夹进屏幕」重算**原点**（只改原点，所以不成环）。净效果正是用户要的
   「左下角固定、内容往上长」；
3. **按住自动发送**：`holdsTheAutomaticSend()`（鼠标在板上 / 面板是 key / 2 秒内交互过）
   —— 静音到点那一下据此按住不发，并让边框呼吸一下（用户：「让用户知道任务没有完成、没有发送出去」）。

**右下角那张卡片**（`OverlayWindow`）只多了一个数据源：

```
conversationBubbleText：完成通知 → streamingAnswerText → **answerPreviewText** → liveTranscriptText
渲染分支：streamingAnswerText 或 answerPreviewText 非空 → 那张 AnswerCardView
```

→ 「跟正常结果卡片的动效与渲染一模一样」是**结构上成立**的，不是照着调的。
预览由看板通过**注入的闭包**写进 `CompanionManager.answerPreviewText`
（与 `voiceIdleProvider` / `sharedVoicePlaybackEngineProvider` 同一个先例：
跨子系统只走注入，不让对方去猜）。

### 3.8 设置页（设置 → 操作 → 任务方向看板）

总开关 / 看板宽度（1、1.5、2 倍）/ 每隔 3 秒问一次的门槛（新增字数 5…20）/
概率阈值（0.3…0.9）/ 取消状态 + 立刻恢复 / **方向清单**（在访达中显示、恢复默认、逐条删除、手动加一条）/
**已固定的方向**（列出 ✓✗、全部取消）/ JEV API Key。

### 4.1 单测（`WannaTests/DirectionBoardTests.swift`，37 条全过里的一部分）

## 八、2026-09-27 晚补：用户实测报的两个问题

### 8.1 右下角"显示了两个回复"（已修）

**现象**：他按住快捷键问第一句，右下角先显示一个回复，**没过半秒钟又变成一个全新的回复**。

**根因**：提交那一刻就把预览收了（`consumeTurnDecision` → `answerPreviewWriter?(nil)`），
而真正的答案要 1~2 秒才到 —— 于是卡片**先消失、再被真答案重新画出来**，两次内容还不一样。

**修法**：**交接**而不是"收掉再来"。
- 提交时**不动**预览（卡片一直挂着，不空一帧）；
- 真答案的**第一个字**到达时（`CompanionManager` 流式写入那一处）调 `clearAnswerPreview()`
  —— 两段文字落在**同一张卡片**上，用户看到的是"答案被补全了"；
- 这一轮被打断（`clearAnswerBubble`）、或下一轮真的开始（`beginListening`）时才收。

### 8.2 "连续问到第六七轮就卡死"（**根因未定，先装仪器**）

**现象**：一次快捷键之后连续追问，到第六七轮**字幕不再显示任何内容、问它也不回复、
三块界面全无变化**，但「不是软件卡死不能用」。

**为什么这一轮我没有直接修**：他说「你可以看一下刚才的记录」——而**那条路一个字都没落盘**。
双击启动的 App 里 `print` 进不了任何地方（既不是终端，也不在统一日志里：
`log show --predicate 'process == "Wanna"'` 返回 0 行）。唯一存在的日志是**长录音**那条路的
`录音诊断.log`，与这条链无关。**没有记录就没有根因**，靠读代码猜出来的结论这个仓库不接受。

**能排除的**（读过代码）：`VolcengineTranscriptionProvider.beginNextUtterance()` **有**重置
`connectionRecoveryAttempts = 0`，所以不是"重连预算用光"那一类。

**装了什么**（新文件 `Wanna/MainFlowDiagnostics.swift`，日志落在
`~/Library/Application Support/Wanna/主Agent诊断.log`）：

| 记什么 | 为什么是这一行 |
|---|---|
| **音频心跳**：连续监听期间每 2 秒一行 `N 块/2s 峰值 x.xxx` | **一句话三分**：0 块 = tap/引擎没了；有块但峰值恒 0 = 设备哑了（跨进程那一层）；有块有峰值 = 音频**到得了**，故障在下游（识别会话/网络） |
| **识别会话的生命周期**：这一句开始 / 定稿到达（带字数）/ tap 装 · 撤 | 「他说话了但没有字」与「字到了但没提交」是两件事 |
| **看板每一轮**：第 N 轮发请求（带转写字数） | 「看板不动了」是闸门没过还是请求没回来 |
| **主线程看门狗**：后台每 1 秒往主队列投一次，往返 > 2 秒就记一行**带当时的阶段标记** | 他的两句话（"不是软件卡死" / "界面没有任何变化"）正好是两种成因：主线程被堵住 vs 主线程闲着各条链各自停摆 |

分寸：只写文件、**不在主线程做 IO**（纯入队）；2MB 轮转；**不改变任何行为**。

### 8.3 顺带：截图从"每轮一张"改成"一句一张"

上一版为了修「他应该直接看到屏幕」把截图改成了**每一轮请求都截**（每 3 秒一次全屏
`SCScreenshotManager` 抓取）。现在改成**一句一张**：第一次请求时截、这一句里复用、
用户说「参考屏幕 / 看屏幕」时作废重截（他原来那条「每一次转写识别到就截一次屏」照旧成立）。

**这是省开销**（一句从 ~7 张降到 1 张，模型侧也少收 6 张图），**不是**"卡死的修复" ——
两者在时间上重合，但**相关不等于因果**，在拿到 8.2 的日志之前不许写成结论。

### 8.4 「按住 ESC 退出之后，右下角的卡片没有退出，一直跟着鼠标」（已修，**这是我引入的回归**）

**根因**：8.1 那次的修法把"收预览"从**提交那一刻**挪走了（挪到"真答案的第一个字"），
却没有给**其余出口**补上 —— 而 ESC 打断走的是 `cancelTurnByEscapeWhileListening()`，
它**不经过**答案管线，于是**没有任何人来收那张卡片**。用户看到的就是它永远跟着鼠标。

**修法（四道，前两道是结构性的）**：

| 道 | 在哪 | 管什么 |
|---|---|---|
| ① **相位** | `NotchWindowController.setActivityPhase(_:)` —— **相位的唯一写入口** | **相位一旦变成 `.idle` 就作废预览**。ESC 打断、监听窗口到期、空转写、以后新加的出口 —— 全都经过这里，**不可能再漏**。判据是 `== .idle` 而**不是** `!= .listening`：提交之后相位要先经过 `.transcribing`（等定稿）再 `.thinking`（截图 + 视觉请求），那段正是"预览等着被真答案交接"的 1~2 秒，用 `!= .listening` 会把它清掉 —— 那就又回到 8.1 的"两个回复"（两个 bug 会把对方改回来，这是量出来的） |
| ② **轮次出口** | `DirectionBoardSession.endListening(keepPreview:)` | 提交那一轮传 `true`（留着交接），**其余出口默认清**。三个调用点各自明确：ESC 清、`handleFinalTranscript` 留、窗口关闭清 |
| ③ **交接** | `CompanionManager` 流式写入第一处 | 真答案的第一个字到达时清（同一张卡片换内容，不空帧） |
| ④ **管线收尾** | `currentResponseTask` 的 `defer` | 覆盖"提交了但**根本没有答案**"——纯执行类任务不写 `streamingAnswerText`，第③道永远不会触发，不收就是又一张跟着鼠标的卡片 |

**单测钉着**（`onlyTheSubmittingTurnKeepsTheAnswerPreview`）：提交那一轮 `answerPreviewWriter` 一次都不写；
放弃那一轮写一个 `nil`。

⚠️ **教训**：一个"只在某个出口收"的资源，出口一多就必然漏。
**寿命要挂在那个子系统里唯一的那份真相上** —— 这里是相位。
（这一条与 `开发经验/18-状态类问题的查法.md` 是同一件事的两面：该写的那一格没人写 → 先找判据。）

## 九、2026-09-27 晚补：参考材料三类（屏幕 / 剪贴板 / 访达选中）+ 卡片上的标签与两个按钮

### 9.1 三类各自的分寸（他拍板的三条）

#### 拖动：SwiftUI 的 `DragGesture` 不能用（增益 1/2）

第一版用 `DragGesture.translation` → **实测拖 −180pt 窗口只走了 −92pt，增益正好 1/2**。
根因与设置里那个窗口缩放手柄**一模一样**：`translation` 是在**卡片自己的坐标系**里量的，
而卡片正随窗口一起动，于是每次只拿到"还差的那一半"。

改成 **`NSEvent` 本地监听 + 绝对定位**（按下时记下光标与窗口原点，之后按光标当前位置重算原点），
实测 **−200 走 −200、+150 走 +150，增益 1.000**。两个附带的好处：
监听**不吃点击**（`DragGesture` 会 —— `minimumDistance` 调大才不吞，而那又让它丢掉起步几 pt）。

⚠️ **监听里返回 `nil` 就是吞掉那个事件**：第一版我把 `mouseUp` 吞了，
而 SwiftUI 的按钮**靠 mouseUp 触发** —— 板上每一个按钮都会点不动。必须 `return event`。
（这一条是用合成点击验出来的：点「复制」→ 剪贴板里出现右下角那段回复。）

#### 访达那条：`-1743 Not authorized`，而且**没有弹授权框**

实测日志：`访达 AppleScript 出错 —— NSAppleScriptErrorMessage = "Not authorized to send Apple events
to Finder."`（-1743），而 `NSAppleEventsUsageDescription` **确实在**（`plutil -p` 核对过已进 bundle）、
脚本本身**编译通过**（`compileAndReturnError` 验过，编译不走 TCC）。
所以问题不在键、也不在脚本 —— 而是**那一发是在专用串行队列（非主线程）上发的**：
授权框只能由主线程上的那次发送带出来。

修法：拿到 `-1743` 就**回主线程再发一次**，那一发才会把「Wanna 想要控制访达」问出来。
（放主线程的代价是有可能等访达 —— 但只有第一发走主线程，而且刚加的主线程看门狗会抓到它。）

### 9.10 ⚠️ 一次自己造成的回归：看板整个不动了（2026-09-27 夜）

**现象**（用户附截图）：「我怎么说话，它都整个的卡片没有任何的反应」——
卡片上 `屏幕一/屏幕二/屏幕三` 三张截图都在（说明**话确实进来了**），而四行理解全是 `—`。

**根因**：9.8 那条"静音才刷"我读的是**连续监听那条链**的静音计时器
（`BuddyDictationManager.continuousListeningSilenceStartedAt`），而那个计时器**只存在于连续监听的
VAD 循环里** —— **按住说话那条路根本没有它**，于是 `secondsSinceLastSpeech` 恒返回 0、
闸门永远不过、**一次请求都不发**。卡片就成了一个只截屏、不思考的壳。

**修法**：判据换成**"距上一次识别到新字有多久"**（`latestTranscriptUpdateAt`，由
`noteLiveTranscript` 每次更新）—— 转写的到达时刻**两条路都有**（它是识别回调，不是引擎状态）。
同时删掉那个 provider 与它在 `BuddyDictationManager` 里的实现（没人用了）。
判据抽成纯函数 `hasPausedLongEnough(secondsSinceHeSpoke:threshold:)` 并加了单测。

**为什么我的验证没抓到**（这一条比 bug 本身更值得记）：
自检喂的是假转写，而**那个 provider 在没有录音时返回 `nil`**，我写的是
`if let silence = provider?() { … }` —— **nil 时整道闸门被跳过** ✗。
也就是说：**自检恰好绕开了我刚加的那道闸门**，所以我这边一路是绿的，真机上却是死的。
（同一天上午采集器那次也是同一个形状：自检没走真实接线。）
现在判据换成转写时刻之后，**自检会真的经过这道闸门** —— 这个洞补上了。

### 9.19 ⭐ 只在真机上看得见的一个截断：**值里的「疑问」被当成了第二个标签**

屏幕上是「疑问  一、关于「记到哪里」的」，后半句「疑问：是要写进 Notion 某一页……」**凭空消失**。
**指认它的证据是「目标」那一行**：同一轮、同样长、不含这两个字，折行完全正常 ——
所以问题不在视图（宽度/折行），在**送进视图的那个字符串本身**。

根因在 `DirectionBoardPrompt.labelPositions`：它在**整行里扫标签别名**，而模型把「疑问」两个字
写进了**值里面**（「一、关于「记到哪里」的**疑问**：是要写进 Notion 某一页……」）——
第二个「疑问：」被当成新标签，于是**第一个值的终点就落在那儿**（`valueEnd` = 下一个标签的起点）。

修法 `isAtLabelBoundary`：**标签必须落在行首或空白之后**。既挡掉句子里的词，又不影响模型把几行
挤成一行时写的「目标：… 细节：…」（那里有空格）。回归测试 `labelWordInsideAValueIsNotASecondLabel`
用 `主Agent诊断.log` 里那条真实回复钉住。

⚠️ **那条测试红了两次，两次都是我的断言写错**（实现一次就对了）：
1. `parseUnderstandingLines` 第一行就把**全角冒号统一成半角**，我的期望串里写的是全角；
2. 「—」是**空值标记**，解析出来本来就是空串（`dashMeansEmptyNotContent` 早就钉过）。

**教训：解析类的问题先写探针，别在测试里猜。** `DirectionBoardPrompt.swift` 只 `import Foundation`，
给它补两个类型桩（`DirectionBoardDisplayItem` / `DirectionBoardTurnDecision`）就能
`swiftc -o probe DirectionBoardPrompt.swift stubs.swift main.swift` 单独跑（本仓已经这么干过几次）——
十秒钟就能看见"解析出来到底是什么"，比来回跑 40 秒的测试快得多。

### 9.20 左下角折叠钮贴边：负内边距后面**不许再套 `frame(height:)`**

他要的是「按钮最左边跟卡片外边框之间**不应该有间距**」。做法是把取消那一行整体向左、向下
各顶出卡片内边距那么多：

```swift
.padding(.leading, -Self.horizontalPadding)
.padding(.bottom, -Self.cardBottomPadding)
```

**第一版在后面又写了一个 `.frame(height: cancelRowHeight + cardBottomPadding, alignment: .top)`，
于是等于没写。** 负内边距起作用的方式是"**内容的布局高度比它画出来的高度小 10pt**"——
再套一个 frame 就把这个高度**顶了回去**，屏幕上量到的仍是 15pt 的缝。

去掉那个 frame 之后用 AX 核对（**坐标只从 AX 树拿，不看截图目测**）：

| 元素 | AX frame |
|---|---|
| 面板 | `x:1293 y:32 w:680 h:584` |
| 折叠钮 | `(1293, 580, 22×36)` |
| 复制 / 执行 / 退出 | `(1359/1418/1478, 580, 58×26)` |

折叠钮的**左边缘 1293 = 面板左边缘**、**下边缘 616 = 面板下边缘** ✓ 贴住了；
三个按钮 26 高、离卡片下沿 10pt ✓（它们不该跟着贴边）。

### 9.30 ⭐ 一个"沉默的空问题"——「我问他问题，他没有回复我」的根因（2026-09-27 深夜）

**症状**（用户附图）：需求 `—`、矛盾 `—`、右下角没有答案、**左上角那五行方向格整块消失**。
他一共报了三件事，**前两件是同一个根因**。

**根因**：`DirectionBoardSession` 里有**两个**同名的孪生字段 —— `latestTranscriptUpdateAt`
与 `lastTranscriptUpdateAt` —— 而**后一个从来没被赋值过**，永远停在 `Date.distantPast`。
`latestTranscriptAfter(_:)` 读的正是它，于是恒返回空串。

这条链是怎么炸的：我这一轮刚把「**这一轮的新问题**」定义成
`latestTranscriptAfter(recentTurns[0].at)`（用户点名要的"从 AI 回复停稳那一秒到用户第二次停顿"）。
判据一恒空，**发给模型的就是一段空问题** —— 它老老实实回了一屏「—」，右下角也没有可答的题。
而屏幕上看起来就像"他没反应"，且**不报任何错、不发任何提示**。

**两条修法，一条治标一条治本**：
1. **同一件事只留一份状态**：删掉那个孪生字段，`latestTranscriptAfter` 读唯一那份。
   （"声明了却从没写过"的字段不会报错 —— 这与仓规 E1 那条是同一族的坑。）
2. **兜底：算出来是空就用整段**。既然"这一轮的新问题"永远不该是空的，就**不允许**它是空的。
   这一条把整类失败关掉了：以后再有什么判据失效，最坏也只是退化成"拿整段当问题"，
   而不是"发一段空的过去"。

**顺带修的两件**（同一个截图里的另外两条）：
- **方向格不再凭空消失**：原来是 `if !displayedItems.isEmpty { directionList }` —— 本地关键词没命中、
  Jev 又还没回来时整块不见，**下面所有东西一起往上跳**（用户：「卡片设计出来之后，
  **整个样式和位置不应该变化**。我发现左上角这五行突然间消失了」）。现在**永远画着**，
  没内容画一行占位 —— 与「需求 / 矛盾空着也画 `—`」同一条规矩：**行的集合恒定**。
- **呼吸灯加深**（他：「颜色再深一点，有点看不见」）：底色 26% → **70%**，呼吸的谷底 12% → 30%
  （谷底太浅会闪没）。

**验证**：46+1 条单测全绿（新增"新问题不许为空"的钉子）。**真机跑了一轮 live 自检**
（34 秒，跑完立刻收掉 —— 那块卡片会吞回车，不能长时间占着他的机器）：四轮请求全部拿到回复，
最后一轮原文里有完整的需求、带 `├─` 的脑图、「矛盾：—」与 7 个方向格。
⚠️ 自检**只覆盖了后半条**（它第一轮的 `recentTurns` 是空的，走的是"整段当问题"那条路）——
真正踩到空问题的是**第二轮以后**，而这次四轮都正常，所以两条路都过了。

### 9.31 流式渲染（「你没有渲染逻辑，延迟非常长」）+ 「没关系就一个字别提之前」（2026-09-27 深夜）

**① 流式：这条链原来把分片丢了。** 用户：「我让你之前写的是在右下角这个卡片用渲染的逻辑……
**现在你没有渲染逻辑，你相当于是直接贴上去了**……那流式输出的话，你没有渲染逻辑，
**这个延迟就非常长**。所以像流式输出，然后加上渲染逻辑、加点动画啊。」

根因是一行：`analyzeImageStreaming(..., onTextChunk: { _ in })` —— **回调是空实现**，
分片全被丢掉，卡片要等整段回复回来才一次性上屏。而那个客户端的回调是**每来一个 SSE 分片
就交一次累积全文**（`BailianVisionChatAPI.swift` 的 `accumulatedResponseText += textChunk` 之后
`await onTextChunk(currentAccumulatedText)`），所以"边收边画"的材料一直都在，只是没人接。

改法：`applyStreamingParagraph(partial)`，三条分寸 ——
1. **节流到 8 次/秒**（每来一个分片就整块重排是白烧主线程；这个仓库在回答卡片上已经为
   "每来一个字重排整串"付过一次代价）；
2. **只更新"半截文本里已经有内容"的行** —— 还没写到的行保持上一次的值，
   否则每来一段，写好的行会先退回占位符再长回来（那就是闪）；
3. **答案同步流进右下角那张卡片**，并且**告诉它"这条是流式的"**（新增
   `CompanionManager.isBoardPreviewStreaming`，`OverlayWindow` 那个气泡的 `isStreaming`
   改成 `isAnswerStreamLive || isBoardPreviewStreaming`）—— 这样它才会用模糊焦点那套渲染。
   ⚠️ 特意**不复用** `isAnswerStreamLive`：那个标志的主人是主 Agent 那条管线，
   看板刷新与它可能同时在跑，共用一个布尔必然互相踩。
- 行是**固定高度** + 值带 `.id(value)` 淡入，所以流式的效果是"内容一行一行长出来"，
  **骨架一个像素都不动** —— 这正是之前那套"高度提前定死"的设计要支撑的东西。
- 加了一行可核对的打点（「流式渲染完毕 —— 边收边画了 N 次」，0 次＝分片又被丢掉）。

**② 提示词：没关系就一个字都别提之前。** 用户把这条讲成了规则 + 反例：
「有关系的话去回复，**没关系的话就不要去回复跟之前问题的任何内容**……

之前的内容、之前的结果，或者之前的聊天记录，**全部都当做一个参考的部分**。」
系统提示词 1.4 与请求里的 `<previous_turns>` 段都按这个重写了（把他的编程/中国那个例子抄了进去）。

收尾那一发 `pkill -TERM -f "Wanna.app/Contents/MacOS/Wanna"` **把他正在用的那个实例一起杀了**

### 9.35 刘海那行字幕的卡顿：**量到了，也改小了**（2026-09-27 深夜第十一轮）

用户：「在实时模式下，刘海下面这个文字**特别卡顿**，这个问题一定要修复，因为**卡顿问题非常重要**。
**在录音模式下也非常卡顿**。」（两处用的是同一个视图，所以是一件事。）

**这一行以前是"猜"过来的**：文件里那段注释写得很清楚 —— 两版时长都被否掉
（0.6s 固定＝永远在追；0.1s 固定＝一个字一个字地挪），最后改成"时长 = 上一条的到达间隔"，
而那句注释自己就承认：**「真正的根因要等采样说话」**。所以这次先量。

**量法（把故障从用户手里挪到机器手里）**：`WANNA_DIRECTION_BOARD_SELFCHECK=stream`
本来就能按 10 字/秒往那一行喂假文本，**但那一行只在相位是 Listening 时才画**，而自检没有真实语音、
相位永远到不了 —— 于是**它从来没有可复现的入口**（这就是"量不到"的原因）。
给自检开了一道门（`forcesTranscriptRowForProfiling`），然后：
① 连拍 20 帧（每帧带真实时间戳）；② 写了个 30 行的探针
（`/tmp/measure-row.swift`，CoreGraphics 读 PNG、取"最左边那个亮像素"的 x）；
③ 逐帧算位移剖面。

**量到的**：
- 主线程基本是闲的（`sample` 8 秒，叶子帧全是 `mach_msg`/`__workq_kernreturn`）——
  **不是 CPU 问题**，所以"再优化宽度计算"这条路是错的（那次 `sample` 量到的 91% 是更早的一版，
  已经修掉了）；
- 真正的症状是**速度在以 ~5Hz 摆动**：每 100ms 的位移是 **34px / 22px 交替**
  （−308、−202、−347、−255、−221、−380… px/s，**±23%**）—— 那就是"一顿一顿"。

**根因**：动画时长取的是"**上一条**的到达间隔"（≈0.10s），而到达时刻本身有抖动（实测 0.09–0.12s）。
间隔变长的那一次，**动画先跑完 → 空等几毫秒 → 再跳一下**。

**修法**：`时长 = 间隔 × 1.2`（新增 `slideDurationOvershoot`）—— **让动画永远跑不完**，
总在下一批到达时被从当前呈现值平滑接上（这条性质这个文件早就量过：打断瞬间的跳变全是 0.000pt）。
目标值是**绝对值**（`可用宽度 − 文字宽度`），所以"永远差一点点"**不会累积**，稳态只落后一步。

**改完再量一遍**（同一套探针、同一个自检）：位移 25–33px（原来 20–36），速度摆动
**±23% → ±10%**，而剩下的 10% 与我的采样间隔抖动（Δt 0.094–0.110s，±8%）同量级 ——
**基本可以认为已经到了测量噪声的水平**。录音模式用的是同一个视图，一并受益。

它要回答的问题就是"**用户到现在为止到底在做什么**"（他自己那句话），所以它不该跟着
"按了几次快捷键"重置。重开的入口留了一个 `resetAccumulatedMindMap()`，
但**目前没有任何路径自动调它**（ESC 也刻意不清：ESC 打断一句没说完的话，
不代表之前问过的问题不算数了 —— 清了才是真丢东西）。

**同轮还做了两件**：
- 提示词把"并进去"写成硬要求：「**下面那张图上的每一条都必须一字不少地出现在你这一轮的输出里**，
  然后再加上这一轮的新内容 —— **少一条就是错的**」；行数上限 12 → **20**
  （他画的那个红框里还有大片空位，说明不是地方不够）。
- 打点本身留着：**下次再有"图上少了什么"，`主Agent诊断.log` 里那两行能一眼分清**
  "没带上去"（被清了）还是"带上去没被并进去"（模型的问题）。

### 9.45 树状图"突然间消失了" —— 是**每次按下快捷键把行擦掉**，不是模型没返回（2026-09-27 深夜第十九轮）

用户（附图，右列整块空着）：「右上角的卡片，它这个树状图**怎么突然间消失了呢**？之前还很好的，
然后就突然间消失了。是不是卡片渲染的时候某一个模型的返回没有返回呀？」

他的猜测是"某次调用没返回"，**量下来不是**：`beginListening`（＝**又按了一次快捷键**）里有一行

```swift
understandingLines = DirectionBoardPrompt.understandingLabels.map { ($0, "") }
```

—— 它把卡片上那几行**重置成空占位符**，而**下一次梳理要一两秒（现在是两次调用）才回来**。
于是每按一次快捷键，那张图都先**整个消失**、过一会儿再长回来。拆成两次调用之后这个空窗更长，
所以他从"之前还很好"变成了"总是突然没了"。

**这与他早就定过的规矩直接冲突**：「只要用户**没有按退出键、没有按 ESC**，这几个卡片都持续显示」。
修法：**一律保留上一次的内容**，新一轮的梳理回来时自然覆盖（`understandingLines` 是整块赋值的，
不会新旧混在一起）。—— 与 9.38 那条是**同一个毛病的两个面**：那次清的是累积的图，
这次擦的是**画在卡片上的那几行**；都是"新一轮开始时把用户正在看的东西清掉"。

或者跟参考内容没关系，完全不要去提任何关于参考内容的关系，任何参考内容的东西**。
我发现他**还是在提之前参考的内容，或者屏幕内容**，或者其他的，没有跟我当前问题没有任何关系的
内容，而且当前的问题跟之前的问题完全没关系。」

两处加强：
1. 规则 1.4 的"没关系"那一支补成：**不要提屏幕上的东西、不要提剪贴板、不要提之前的对话** ——
   不要拿它们做类比、不要说"屏幕上没有这个"、也不要把两件事揉在一起；
2. 新增 1.45 **「没关系时的答案长什么样」**：**就事论事地答他刚问的那件事，全文不提任何背景** ——
   答案是"他问的东西"的答案，不是"他问的东西和背景的关系"的说明。
   （他报的现象正是后者：答一件跟屏幕无关的事时，还要说一句"屏幕上是……，跟这个问题没关系"。）

### 9.47 「调了十几遍」之后：不再改措辞，去找**结构性的**东西（2026-09-27 深夜第二十轮）

用户的最后一句是判决书：「**这个问题已经调了十几遍了。你去思考一下到底问题出现在哪吧？
这样调没意思。**」——他说得对：我前面十几轮有太多是在**改提示词的措辞**，
而其中至少三个是**代码里的结构性缺陷**，跟措辞一点关系都没有。

**① 解析器把长内容截掉了（`maximumContinuationLines = 4`）。**
提示词让模型画"最多 **20** 行"的关系图、矛盾/拼写错误也允许多条，而解析器**只收 4 行续行**
（整块最多 5 行）—— **多出来的全被丢掉**。用户报的「他为什么只是显示一部分呢？
**他留这么大的空间**……」有一半是这个。改成 **24**。

**② 标签下面先空一行，整块就没了。**
「细节：」换行、空一行、再开始画树枝 —— 这在**画图**时非常常见，而原来的收集循环**遇到空行就 break**，
于是 `joined` 是空的、那一行直接不记。屏幕上就是"图没了"。现在**允许跳过开头最多两行空行**
（已经开始收内容之后，空行仍然算结束）。

**③ 卡片把文字裁掉，而下面一大片空着。**
左列每一行都写死 `reservedLineCounts × 行高` 再 `.clipped()` —— 那是**左列还是自由高度**的年代
留下的（为了让卡片不随内容跳）。现在**卡片高度由整块 `contentBlockHeight` 钉死**、左右两列各自固定，
行里多出来的字**没有理由再裁**：改成按内容自然高度、**由整列兜底**（整列仍有高度与裁剪）。
"卡片高度恒定"这条不变量仍然成立 —— 它现在挂在**块**上，不挂在行上。

**④ 请求里每一块都打上 tag**（用户点名的做法：「你提的词是用提示写的吗？……用 **tag**，
标签、书签这个符号的形式来给它分开」）：`<reference_materials>` / `<previous_turns>` /
`<previous_answers>` / **`<current_question>`** —— 并在系统提示词里新增 1.42 说明
「**只有 `<current_question>` 是要你回答的，其余全是参考**」。
（他报的"总带着过去的内容"因此有了一个**机械的**判据，而不是靠模型读一长串说明去猜。）

⚠️ **这一轮真正的教训**：**"反复调不好"的时候，先怀疑解析/渲染/数据流，而不是措辞。**
①②是解析器的两个上限，③是渲染层的两个 `frame`+`clipped` —— 它们都**不报错**，
只是安静地把内容丢掉或裁掉，而屏幕上表现成"模型没做好"。

### 9.48 那张图**没有行数上限**，卡片跟着它长（2026-09-27 深夜第二十一轮）

用户纠正我（并且纠正得对）：「我看到你说什么**提示词要求模型最多画 20 行的图，没有这个限制**。
用户的内容可能是**两个小时**，那这个图就应该是两个小时的内容。**用户所有的问题都应该在图里面
显示。**我说的是右上角的这个脑图、树状图。」

三处一起拿掉天花板：
1. **提示词**：「最多 20 行」删掉，改成「**不限行数** —— 他问过多少件事就画多少」；
2. **解析器**：`maximumContinuationLines` 24 → **500**（那只是个"防模型写成一篇论文"的保险，
   正常到不了；**真正的上限只有一个：磁盘上他到底问了多少**）；
3. **卡片跟着图长**：`contentBlockHeight` 原来是个定值（max(左列所需, 264×2)）——
   现在取 max(左列所需, **图需要多少行** × 行高, 264×2)，**上限挂在屏幕上**
   （菜单栏以下那块高度的 **70%**，与右下角那张结果卡同一条规矩）。
   行数用 `value.split("\n").count × 16pt` 算，**不去量文字** —— 图是等宽字体、行高是定的，
   而量文字要么再引一层 `GeometryReader`，要么量不到自然高度（它被 `maxHeight: .infinity` 撑着）。
   行数是**可预测**的，所以卡片高度不会随渲染时机跳。

于是：**图有多长，卡片就有多高**（到屏幕的 70% 为止）—— 用户那句"他留这么大的空间，
不就是让你把这个文字能够完全地显示到这个空间里面吗"现在成立。

### 9.49 拼写错误只报"确实错的"；背景与问题**机械分离**（2026-09-27 深夜第二十二轮）

**① 拼写检查太吵。** 用户：「右上角卡片的**拼写检查过于细致**，很多没有意义的内容也会被检查。
应该**根据上下文来判断哪些地方确实有错误**，而不是**针对单个单词**去思考有哪些拼写方式。
**如果上下文逻辑正确、没有歧义，就不必纠结**。**软件名称**这类内容才是需要重点关注的，
而不是单纯的拼写。」他截图里那五条正是我说的"吵"：口语衔接词（「在这个」）、普通词同音字
（「有时→有哪些」）、光凭猜测的名字（「杨幂可能是杨颖」）、断句位置（「屏幕右侧，左侧」）。
提示词改成：**只报"确实错了、而且影响理解"的**，重点只有一类（**软件名 / 品牌名 / 英文词**），
并把他点名的那四种噪音逐条列成"不要报"，最后加一句**「没有就写「—」，宁可空着」**。

**② 答案是"100% 先看最近的问题"—— 这条到这一轮已经是第四次说了，所以不再改措辞，改结构。**
用户：「右下角卡片**过度关注屏幕内容和之前的内容**。每次提问都带着屏幕，应该把当前屏幕内容也
当作一个**参考**，但**一定要 100% 重点关注用户最近的问题**，以此问题为标准，判断跟之前的问题
是否有关系，再思考应该回答什么内容。**如果没关系，就直接回答用户的问题**。」

**结构性改法：背景与问题机械分离。** 原来所有背景（参考材料 / 最近几轮 / 上一轮那一列方向）
都拼在**用户消息**里、只靠一行标题说"这段是参考"—— 而模型对"这一轮要答什么"的判断，
读的就是**用户消息**。把参考塞在那里，等于每一轮都在用一个巨大的用户消息告诉它"这些都是要回应的"。

现在：**用户消息里只有那一句问题**（`understandingUserPrompt(newQuestion:)` 就返回它自己），
背景全部进**系统提示词**（`understandingSystemPrompt(context:)`），并在那一段前面写明
「**不是要你回答的东西**……他只让你回答**最后那条用户消息**里的事；下面这些只在你判断"有关系"时
才用，没关系就**一个字都别提**」。

**同一轮还清掉一处"偏向屏幕"的老话**：每轮末尾那段原来写着「每一轮都带了当下的屏幕截图：
请**看图**再回答……「答案」那一行更是**必须看图算**」—— 那句话本身就是"过度关注屏幕"的来源。
改成：**屏幕是参考，不是问题本身**；只有他真在问屏幕上的东西时才看图，其余问题一律不看图、不提屏幕。

### 9.50 「卡完之后就不显示」是个真 bug：晚到的梳理被**整块丢掉**（2026-09-27 深夜第二十三轮）

用户（附图，右列空着，而右下角答案正常）：「右上角卡片的内容是对用户问题的梳理，**但总是显示不出来**，
而且会**明显拖慢速度**。它其实就是对用户问题的梳理……**这个文本没有图片、没有任何参考内容**，
就是把用户抒发的文本发给 AI，让它整理后显示出来。**但为什么返回速度这么慢？而且总是卡，
卡完之后就不显示了。**」

**"卡完就不显示"的根因**：梳理那次调用的落地处有一道闸

```swift
guard self.roundGeneration == generation, self.isListening else { return }
```

而它**往往在用户已经按了快捷键 / 开了下一轮之后才回来** —— `isListening` 已经是 false，
于是结果被**整块丢掉**；`endListening` 里还有 `requestTask?.cancel()` 补一刀。
**那张图是累积的**：晚到几秒完全无害（画的还是同一份东西）—— 只有"换了一次大循环"才该作废。
改成 `guard self.currentCycleID == cycleIDAtRequest`，并且 `endListening` **不再 cancel** 它。

**"为什么这么慢"**：梳理那条每次都要**重画整张图** —— 输入是**整份转写**、输出是**全部问题**
（而且行数已不限）。每 10 个字就重跑一次，正是他说的"明显拖慢速度"。
所以给梳理**单独一道更粗的闸**：`max(minimumAdded × 3, 30)` 个字才发一次；
**答案那条不受影响**（它照旧按原来的最小字数，用户盯的是它）。

**追问要知道"最后一个结果是什么"**：他要的是**逐块标清**——
「一定要标注哪个是**最近一次**，哪个是**上一次**，哪个是**当前这一次**，哪个是**上一次的问题**，
哪个是**上一次的结果**。**你不要直接一拥在一起，要标清楚**」。
于是 `<previous_turns>` 里每一轮拆成两块、各有标题：

```
【上一次的问题｜22:10:02】
…
【上一次的结果】
…（**最近这一条不再截断** —— 他追问"把最后一个结果展开说一说"时，
  那个"最后一个结果"就在这段文字里；原来砍到 600 字就答不上来，
  而这是他真实场景：一次回复里列了 10 个结果）
【上二次的问题】/【上二次的结果】…
```

### 9.51 三连测之后的三处修复（2026-09-27 深夜第二十四轮）

用户：「**你这测试三次，告诉我结果有问题，截屏，截屏，截屏。告诉我，然后自己修复。**」

| 第 3 轮 | 6 件事全在、层级也对 ✓ | 同样空白 |

**图本身已经能出来、内容也全（3/3）**。修了三处：

矛盾/拼写错误都是「—」（提示词的"只报确实错的"生效了）。

### 9.54 看板上那两下回车重新分配：**⌥⏎ 执行 / ⌘⏎ 粘贴**（2026-09-27 深夜第二十七轮）

用户：「之前的设置的快捷键，关于（**实时对话**）**转到 agent 模式**（快捷键替换成：**option+enter**），
和**粘贴**的快捷键（替换成：**com+enter**）」。

**这一轮改的是"判据"，不是"哪两个键被监听"** —— 监听那条链一个字没动
（那条会吞事件的全局 tap + 兜底的本地监听，两处仍然共用同一处判断）。改的是：

| | 改之前 | 改之后 |
|---|---|---|
| 执行（转 agent 模式） | `⌘⏎`（当粘贴被设成 Enter 时） | **`⌥⏎`** |
| 粘贴并退出 | `⏎`（默认） | **`⌘⏎`** |
| 裸 `⏎` | **被吞掉**（因为它是"粘贴"那个动作） | **原样放行，不吞** |
| Shift+⏎ | 放行（换行） | 放行（换行） |

三处实现：

1. **判据抽成纯函数** `BoardPasteShortcut.action(isCommand:isOption:)` → `.paste` / `.execute` /
   `.passThrough`。两个入口共用（全局 tap 与本地监听各写一遍必然漂），而且**能单测** ——
   整张表钉在 `boardReturnKeysAreOptionToExecuteAndCommandToPaste` 里。
2. **`passThrough` 是真的不吞**：那条 tap 原来在 `keyCode == 36` 之后无条件 `return nil`，
   现在**只有真做了那两件事之一才吞**。理由：那两个动作现在都带修饰键，再吞掉裸回车，
   就只是白白吃掉用户在别的 App 里的回车（他会一点都感觉不到，只以为键盘坏了）。
   顺带一条：**Command 和 Option 同时按着 → 放行**（说不清他要哪件事，不猜）。
3. **设置项**：`boardPasteShortcut` 从复用的 `ComposerSendShortcut`（Enter / Command+Enter）
   换成自己的小枚举 `BoardPasteShortcut`（Command+Enter / Option+Enter）—— 两个动作的形状
   已经不一样了，继续复用那个枚举只会让人读错。⚠️ 编码上按仓规 E1 走 **String 优先**：
   旧文件里存的 `"commandReturn"` 解得出（含义也一样）、存的 `"returnKey"` 落到新默认，
   **绝不会因为 rawValue 对不上而抛错**（一处抛错会把整份 `AppSettings.json` 带走）。

**真机验证（三条各按一次，读 `主Agent诊断.log`）**：
裸 `⏎` → 「回车 → **放行（不吞）**」；`⌘⏎` → 「回车 → **粘贴并退出**」；
`⌥⏎` → 「回车 → **执行（转 agent）**」。那行日志是这一轮新加的判据：
「按住什么键 → 走了哪条路」出问题时唯一能核对的东西。

### 9.55 「⌘⏎ 只是把内容放进了剪贴板，没有粘出去」—— 两层根因，都不是粘贴本身（2026-09-28）

**症状**：用户按 ⌘⏎，看板的日志说「粘贴并退出」、剪贴板里也确实有那段回复，
**但光标处什么都没出现**。

#### 一、先把"量错了对象"排除掉（这一步花了最久，也最值得写下来）

三个陷阱，每一个都让我读出过错误结论：

1. **靶子没有光标**。`tell application "TextEdit" to activate` 只是把窗口拿到前面，
   **正文并没有拿到焦点** —— 那时打字、⌘V 全都"没反应"，而其实是我们根本在对着一个
   没有光标的文档发指令。**判据**：先用 macos-use **真点一下** `AXTextArea`，
   再打一个标记字符确认它进得去，然后才允许下结论。
   （⚠️ `AXFocusedUIElement` 这个查询在本机经常回 `-1728 拿不到`，
   **它坏的时候也可能一切正常**，所以它不能当判据，能落地的标记字符才是。）
2. **机器上同时跑着多个 Wanna**。用户自己那份 `/Applications`（旧包）+ 我起的一到两个
   自检实例，三份都往同一个 `主Agent诊断.log` 写、都装着 tap。我一度把"键被吃掉"
   算在了自检实例头上，实际是**旧包的看板面板**。**规矩**：量之前先用
   `swift whichpid.swift`（`CGWindowListCopyWindowInfo` 按 pid 列窗口）确认屏上每个窗口属于谁，
   并只留一个实例。
3. **面板 `focused=true` 不等于它接得到键盘**。AX 里读到的 `AXFocused` 与"窗口服务器把键送给谁"
   是两件事，中途我按前者判断过一轮，方向是反的。

#### 二、根因一：启动时 AppKit 把刘海面板选成 key，连**窗口焦点**一起偷走了

`sample` 新进程启动后 8 秒（1ms 采样），在主线程栈里直接抓到了这一串：

```
-[NSApplication _sendFinishLaunchingNotification]
  -[NSWindow makeKeyWindow]
    -[NSWindow _changeKeyAndMainLimitedOK:]
      -[NSWindow becomeKeyWindow]
        -[NSApplication _stealKeyFocusWithOptions:]
          SLPSStealKeyFocusReturningID      ← SkyLight：真的去抢前台了
```

原因是 `NotchWindowController.NotchPanel` 里那一行裸的 `override var canBecomeKey: Bool { true }`
—— 启动时它是屏上**唯一可成为 key 的窗口**，AppKit 就把它选成了 key，于是**整个 App 变成活跃 App**，
`NSApp.keyWindow` 就是那颗刘海胶囊。后果有两层：

- 我们自己合成的 ⌘V 落进了**自己的 key window**（用户看到的"只写进了剪贴板"）；
- **用户在别的 App 里打字也进不去**（实测：前台 TextEdit、板子在屏上，手打的 `BBB` 一个字没进去）。

**修法**：`canBecomeKey` 跟着展开状态走（`isSheetExpandedProvider = { panelModel.isExpanded }`），
静止态**永不可成为 key**；`convergeOnRestingState` 里补一次 `resignKey()`
（AppKit 不会因为 `canBecomeKey` 变 false 就自动归还键盘）。
**验证**：交付包里启动前后 `lsappinfo front` 一直是「文本编辑」，不再被偷。

#### 三、根因二（真凶）：**本进程合成的键盘事件根本落不到前台 App**

把根因一修掉之后，粘贴**仍然不落地**，而此刻所有条件都是对的 ——
一行诊断（`⌨️ 看板：Cmd+Enter → …`）把它们全打出来了：

```
活跃 App=文本编辑｜Wanna isActive=false｜keyWindow=无｜辅助功能=true
```

于是做了两个判别探针（都是 `.hidSystemState` source → `.cghidEventTap`，与 SDK 的 `pressKey` 逐字相同）：

| 探针 | 结果 |
|---|---|
| 终端里直接发 ⌘V | ✅ 落地（`MARKPROBE-PASTE` 出现在文档里） |
| 同一进程**先装一条会吞回车的 `.defaultTap`**、再发 ⌘V | ✅ 落地（排除"我们自己的 tap 吞了它"） |
| **Wanna 进程**发 ⌘V | ❌ 不落地 |
| **Wanna 进程**发**不带任何修饰键的裸 `z`** | ❌ 也不落地 |

最后一行是决定性的：**不是 ⌘ 组合的问题，是这个进程发出去的事件整体没有投递**。
同一时刻 `AXIsProcessTrusted() == true`、系统日志里没有任何 TCC 拒绝、
`event.post` 也不报错 —— 一个"静默的失败"，只能靠探针对照才看得出来。

**修法：粘贴改走 Accessibility，绕开合成事件。** `MacosUseController.pasteKeepingClipboard` 现在
**先**把文本写进系统级聚焦元素的 `kAXSelectedTextAttribute`（**与"粘贴"同义**：有选区就替换、
没有就插在光标处），只有 AX 失败才退回合成 ⌘V。顺序不能反 —— 能落地的地方"先 ⌘V 再 AX"会粘两次。
它和本文件已有的 `selectTextByContent` 走同一套授权，没有引入新的权限面。

**验证**（连续三轮，每轮全新文档 + 唯一标记）：

| 轮 | 启动是否偷焦点 | 板子在屏上打字 | ⌘⏎ |
|---|---|---|---|
| 1（`MARK4`） | 否 | ✅ 进去 | ✅ 插入 103 字 |
| 2（`R2-`） | 否 | ✅ 进去 | ✅ 插入 112 字 |
| 3（`R3-`） | 否 | ✅ 进去 | ✅ 插入 81 字 |

#### 四、顺带修掉的第三处：看板面板自己也在抢键盘

`DirectionBoardPanelController` 的 `show()` 里有一句 `panel.makeKey()`（外加
`becomesKeyOnlyIfNeeded = false`）—— 那是我早先为了"不用点卡片就认回车"加的，
而回车**早就由那条会吞事件的 tap 接住了**。代价是：只要看板在屏上，它就**是会话的 key window**，
于是（a）合成的事件被它接走，（b）`holdsTheAutomaticSend()` 里"面板是 key"那条判据**恒为真**，
每次静音到点都被按住重算 —— 自动发送等于从来没生效过。现在：
**显示时只 `orderFrontRegardless()`、绝不 `makeKey()`**，`becomesKeyOnlyIfNeeded = true`，
那条恒真的判据删掉。

#### 五、还没验到的一处（如实记着）

`[TYPE:]` / `[PRESS:]` 走的是**同一个** `pressKey`，所以按第三节的实测，它们很可能同样落不下去。
本仓库此前对 agent 循环打字的那次"实测"是在**镜像的 harness**（MCP 服务进程）里做的，
**不是 Wanna 进程本身** —— 也就是说"App 内合成键盘事件能落地"这件事从来没有在这个进程里验过。
这一轮**没有动它**（改它要动多行输入、逐行回车、以及不吃 AX 的 App 的兜底），
等用户拍板：要的话，`typeMultilineText` 可以像粘贴一样先走 AX。

### 9.57 「第二次按下还显示上一次的历史」—— 一大轮结束 = 卡片回到零（2026-09-28）

**用户的报告（他标了"非常致命"）**：「用户按住主 Agent 的快捷键进入实时模式时，如果上一次任务
已经退出，比如按 ESC 退出了，**第二次按住之后，右上角和右下角的卡片显示的仍然是之前的历史记录**……
任何时候，无论是**任务完成**还是**任务取消**，只要**大循环结束**，显示的内容都应该是全新的，
**相当于没有历史、没有历史规划**……用户按住 ESC 就是取消任务，**取消所有任务，并且清空历史记录**。
第二次按住时，应该相当于**从零开始**的状态。」他还追问了一句「是代码没修好，还是后台还在持续显示」
—— 这一句必须给出确定答案。

**根因两条，都是"清得不够"**：

1. **`endBigRound()` 只清了两样东西**（`previousRoundItems` + `jevProbabilities`）。真正构成"历史"
   的那些 —— 累积的脑图、他讲过的话、前几轮问答、还没解决的疑问、卡片上那几行 —— **一样都没动**。
   而它正是**大轮结束的唯一收口**（`endContinuousListeningWindow` 调它）。
2. **ESC「任务执行中」那条路完全不碰看板**：`interruptTurnByEscapeWhileRunning()` 只停播报 +
   收这一轮的 agent，`DirectionBoardSession` 一个字都没清 —— 用户看到的正是这一条。

**改法**：把 `endBigRound(reason:)` 变成**整轮复位**，接在三个出口上。

```swift
func endBigRound(reason: String = "追问窗口关闭") {
    // ① 停掉在途的一切 —— 用户那句"后端那些代码也都要停止掉"
    requestTask?.cancel(); requestTask = nil
    cadenceTimer?.invalidate(); cadenceTimer = nil
    isRequesting = false; isListening = false; isUserSpeaking = false
    // ② 清累积的上下文（"历史"就是这几样）
    currentCycleID = nil; accumulatedMindMap = ""; spokenTranscript = []
    recentTurns = []; recentCornerAnswers = []; pendingQuestions = ""
    previousRoundItems = []; jevProbabilities = [:]; displayedItems = []
    latestTranscript = ""; lastRequestedTranscript = ""; paragraph = ""
    // ③ 清屏幕上那几行（视图画占位符，行数仍然恒定）
    understandingLines = DirectionBoardPrompt.understandingLabels.map { ($0, "") }
    previewAnswer = nil; answerPreviewWriter?(nil); contentRevision += 1
}
```

- **`currentCycleID = nil` 那一行不只是顺手**：在途请求的落地闸门是

### 9.65 「对话几轮之后它就不说话了」= 30 秒从"开播"起算，而不是"播完"（2026-09-28）

用户把机制说得非常清楚：「AI 语音**播放完成**、回复结果语音播放完成的那一秒开始，倒计时 30 秒。
这 30 秒持续监听用户状态：没有说话了这一轮结束；说话了或者打断它了，就进入**一个全新的小循环**，
它继续回复，**等回复完成那一秒开始重新计时 30 秒**，一直这样循环……但我发现现在跟他对话几轮之后，
**它就不说话了**。我估计是监听机制的时间**并不是在 AI 回复结果之后重新计数**的。」

**他猜得完全对，代码里就写着**：`armContinuousListeningWindow()` 的两个调用点都在**播报开始**那一刻
（注释还明写着「计时起点 = 播报开始」），而它正是那条 30 秒窗口的唯一入口。于是：
回答念 40 秒 → 30 秒的窗口**在它还念着的时候就到期了** → 念完再说话已经没人听 → 「几轮之后不说话了」。
（回答越长越早死，这正好解释了它"几轮之后才"出问题。）

**改法**：**开窗仍在开播那一刻**（那条窗口就是"打断"的耳朵，回答还在念时必须已经开着），
但**在 `scheduleVoiceStateResetAfterPlayback` 里——即"播完"那一拍——再调一次
`armContinuousListeningWindow()`**，把窗口的到期时间重新拨到 30 秒之后
（它在窗口已开时只重排到期，见那个函数自己的注释）。于是：
**每一轮回复念完 → 重新计 30 秒** ✓ 连续追问的循环就接上了。
设置页那行的说明也改成真实语义（「倒计时从最后一句念完那一秒开始，不是从开始念算」）。

### 9.66 看板"该消失时没消失/退出后粘在鼠标上" —— 判据没错，是**没人重新判**（2026-09-28）

**根因不是判据写错，是判据变了却没人重新判**：`DirectionBoardPanelController.applyVisibility()`
—— 看板显隐的**唯一判定点** —— 原来只在 `sync(...)` 里被调一次，而 `sync` 只挂在**相位变化**上
（`voiceState` 发布）。于是这四件事发生时它**不重判**，面板停在上一次的结论上：
① 这一轮交给 agent 了（`isAgentModeActive`）；② 用户取消了看板（`isCancelled`）；
③ 他终于说出字了（`liveText`，判据里那条"没说出字就不显示"）；④ 设置里把看板关了。

1. **判定点里"现读"每一个条件**（不再靠调用方传进来的快照）—— 我第一版只把
   `!isAgentModeActive` 加在 `sync(...)` 的**参数**上，而订阅触发时那个参数是**上一次**的旧值 ✗，
   于是"修完仍然不消失"。参数那一份已删掉，判据只在 `applyVisibility()` 里读一次。
2. **四个输入各订阅一次**（`bindVisibilityInputsIfNeeded`）：`$isAgentModeActive`、`$isCancelled`、
   `$liveText`、`.wannaAppSettingsChanged` —— 任何一条变了都重判（`applyVisibility` 自身幂等）。

### 9.68 「我手动退出了，它还在监听」—— ESC 那条分支根本没经过关窗口（2026-09-28）

用户的原话（他一次说了三件事，前两件在这一节和 9.69）：

> 「我进入了 agent 模式之后，我退出了，我可能是按住第二次、再一次按住快捷键，然后退出了，
>  **或者是我按住 ESC 退出了，他这个持续监听应该也退出啊**？如果我手动的去退出了，
>  那相当于是我代表这个任务，我说明这个任务已经完成了呀？他还是在监听我，这是不对的，
>  **那相当于是永远无法停止**」

**先把它变成仪器能回答的问题**：造一条脚本（`scripts/listening-stop-check.sh`），
它只做一件事 —— 走完"回答念完 → 30 秒窗口武装 → 手动退出"，然后逐条断言：

| 检查点 | 含义 |
|---|---|
| A | 回答念完之后，窗口**真的**武装了（否则这个检查是空跑） |
| B | 手动退出 → 窗口**关掉**（麦克风 tap 撤掉） |
| C | 之后 **10 秒内不许自己武装回来**（修之前它 30 毫秒就回来了） |
| D | 退出后没有再装麦克风 tap |

**结果立刻分出两条路**：`bash scripts/listening-stop-check.sh 1`（再按一次快捷键）**全绿** ✓；
`bash scripts/listening-stop-check.sh 2`（按 ESC）**B 红** ✗ —— 用户说的就是后一条。

**根因（读日志就能定位）**：ESC 那一刻打的是
`⏹️ ESC 打断这一个周期（cycle=…，任务旗标 没有）` —— 也就是走了
**「正在跑」那一支**（`interruptTurnByEscapeWhileRunning`），而那一支收的是
**播报 + 鼠标旁那张卡片 + 主循环 + 这一轮派出去的 agent**，**唯独没有关那个追问窗口** ✗。
窗口关不关只写在另外两支里（「正在听」那支、和 `interruptActiveResponse` 之外的角落），
而那一刻恰好两支都不成立。

**为什么那一刻会落到「正在跑」**：回答念完之后 `voiceState` 已经是 `.idle`（所以我上一版加的
"重新武装前先看状态"那道守卫挡对了 ✓），但 `currentResponseTask` 还没被置空
（任务收尾是异步的，`currentResponseTask = nil` 在它的尾声里），于是
`voiceState == .processing || .responding || currentResponseTask != nil || isPlaying`
这条**或**链里有一项为真 → 落到「正在跑」→ 窗口活着。

**修法不是"再加一支"，是把判据换成用户那句话本身**：
> ESC 的意思是「这个任务结束了」，而窗口存在的理由恰恰是"这次对话还在继续" —— 两者不可能同时为真。

所以在 `handleEscapeKeyPressed()` 里、**所有分支之外**先做一件事：

```swift
let escapeArrivedWithListeningWindowOpen = buddyDictationManager.isContinuousListening
if escapeArrivedWithListeningWindowOpen { endContinuousListeningWindow(reason: "user pressed escape") }
```

下面那一支的判据跟着改成读**进门前**那个值（窗口已经关了，再问 `isContinuousListening`
永远是 false，那一支就再也进不来 —— 而"回答念完之后按 ESC"要的正是那一支的收尾）。
放在分支之外的意义是**未来的分支也不可能再漏掉它**，而不是"这次补上了"。

编辑窗那一支仍然在最前面 return ✓（那里的 ESC 是"把这块收起来"，不是"结束任务"，
两条语义不许混）。

**验证**：两条退出路径**各三轮全绿**（`listening-stop-check.sh 1` / `2`）；
`direction-board-flow-check.sh` 三轮全绿（ESC 那条也动了看板的收口，怕回归）。
真机（`/Applications`）已同步并重启，新进程启动时间晚于源文件修改时间、无崩溃报告。

⚠️ **一处刻意没做**：`endContinuousListeningWindow` 里会顺带跑 `DirectionBoardSession.endBigRound`
（一大轮结束 = 卡片回零），这是 9.57 定的规矩，ESC 走窗口关闭这条路时**同样生效** ——
即"按 ESC 退出"与"窗口自然到期"对看板的效果是一致的。它们本来就该一致。

### 9.69 「从实时模式转到 agent 模式要 5 秒」—— 2 秒是音频引擎，量到了也修掉了（2026-09-28）

同一句话里的第二件：

> 「为什么从实时模式到执行模式的时候，它本质上就是一次提示词提交？为什么现在耗时将近 5 秒，
>  正常情况下应该是在 1 秒或者 2 秒。」

**先把它变成数字**：`MainFlowDiagnostics` 已经有分阶段打点，补上「截屏前 / 截屏后 / 请求发出 /
模型第一个字 / **出声**」五个时刻（最后一个是新增的，打在
`BailianTTSClient` 那句 `🔊 Bailian TTS: playing …` 旁边），然后拿探针按真实快捷键跑一轮，
把每一段的**间隔**算出来：

| 阶段 | 修之前（2026-09-28 上午） | 修之后（三次） |
|---|---|---|
| 按下 → 提交 | 0.42 s | 0.10–0.9 s（首轮冷启动偏慢） |
| 提交 → 截屏完成 | 0.58 s | 0.15–0.18 s |
| 截屏完成 → 请求发出 | ~0 | ~0 |
| 请求发出 → 模型第一个字 | 1.51 s | 0.72–1.03 s（**是模型，不是我们**） |
| **第一个字 → 出声** | **2.50 s** | **0.93 / 0.99 / 1.00 s** ✓ |
| **按下 → 出声（合计）** | **4.01 s** | **2.21 / 2.84 s** |

**根因（一条日志就能看出来）**：修之前，`🔊 VoicePlaybackEngine: engine started` 那一行
**和「出声」是同一毫秒** —— 也就是说那 ~2 秒的 **VPIO（voice processing）IO 重配置**
**发生在应答的那一刻**，而不是在用户说话的时候。用户的感受"5 秒才出声"里，
**一半是这件事**（另一半是模型自己的首字延迟，那个不是我们能改的）。

**修法一行**：提交的那一刻就**把共享引擎预热起来**（VPIO 那套重配置提前 2 秒开始，
与截图、与网络请求并行）：

```swift
MainFlowDiagnostics.stage("提交：抓截图")
let warmUpEngine = bailianTTSClient.voicePlaybackEngine
Task { await warmUpEngine.warmUpForVoiceChat() }
```

它**不改任何契约**：预热走的就是既有的 `warmUpForVoiceChat()`（回答开播那条路本来也会调它，
重复调是幂等的 ✓），一条音频路径的规矩没动（还是同一台引擎）✓，
也不需要新的设置或开关 ✓。

⚠️ **剩下没动的那 1 秒**（模型首字）**不是工程问题**：同一句问题、同一个模型，
实测首字 0.72 / 1.03 / 2.9 s 波动 —— 网络与服务端排队。要压它只能换模型或减少提示词，
两条都是用户的取舍，不由代码擅改。

### 9.69 补（同一天稍晚）：⚠️ **9.69 那个"预热引擎"当天就撤回了 —— 它带来的问题比它解决的更大**

用户当天的下一句话就是判决书：

> 「以前**每次打断、说完问题他基本上是瞬间回复我**，现在不是了。
>  然后还有另外一个问题：**我打断几次之后他就卡了，就不回复我了**。」

**先量再改（两件事都量到了）：**

| 症状 | 量到的形状 | 在代码里的哪一处 |
|---|---|---|
| 「不是瞬间了」 | 「提交一轮 → 开始截屏」在**按下说话那条路**上是 **0.93~1.33 秒**，而**连续追问那条**（引擎已经热着）= **0.00 秒** —— 两个人群的差别正好是那一句 | `Task { await warmUpEngine.warmUpForVoiceChat() }` |
| 「打断几次就不回复」 | 用户**大声说了**（麦克风峰值 0.634 ✓），定稿却是 **0 字** ✗ —— 一句真正被听见的话被整句丢掉 | 同一次 VPIO 的 IO 重配把**连续追问窗口**的采集掐掉（D28 记过的机制） |

**根因（一句）**：`VoicePlaybackEngine` **是 `@MainActor`**，所以 `Task { await … }` **仍然跑在主线程上** ——
包一层 `Task` 并没有把它挪走，只是把**同一个代价**从"回答开播那一刻"挪到了"提交那一刻"，
而后者更贵：**它卡住主线程（UI 一起停）+ 它重配 IO（把正在听的窗口弄聋）**。

**所以撤回，并把理由写进代码里**（`CompanionManager` 那一处留了长长一段注释，
开头就是「⚠️⚠️ 这里曾有一句……别再把它加回来」）——
**宁可付那 2.5 秒，也不要卡主线程 + 掐掉采集。**

**⚠️ 上面那整段归因后来被 `sample` 推翻了**（同一天，详见 `开发经验/10-踩过的坑.md` D42 补）：
bring-up 本来就跑在 `Task.detached` 上、`await` 是挂起不是阻塞 ——
真正的原因是**主线程在 `AVAudioPlayerNode.stop()` 里等引擎的 attach 锁**（那把锁正被 bring-up 握着），
而修法是让 `stopChunk()` 在 bring-up 期间**不碰 playerNode**（那时引擎没跑、也就没有声音在播）。
改后 **`提交一轮 → 开始截屏` 1.136 s → 0.002 s**，而**预热保留** ✓ ——
所以"预热"与"那 1 秒"不是二选一，撤回的那一版只是把两者绑死了。

**（下面这段是被推翻的旧结论，留在这里当反面教材）**：要真正拿回那 2.5 秒，只有一条路：把引擎启动**真正挪出主线程**（类本身是 `@MainActor`，
不是包一个 `Task` 就够）—— 那是对音频引擎的一次正经改造，要单独做、单独验，
而且必须带着「谁还在用这台引擎同一时刻」那张清单（D28/D29 的教训）。

⚠️ **这一条的教训比 bug 本身值钱**：**"把耗时挪到一个看起来并行的位置"不等于它不在主线程上。**
判断依据只有一条 —— **那个类型是不是 `@MainActor`（或那个方法是不是）** ——
而这一条**量一下就有**：同一个函数在两个入口上的耗时差出 1 秒，就是它在主线程上等的结果。
