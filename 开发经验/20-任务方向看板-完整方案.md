## 一、需求（用户的原话与逐条拆解）

### 1.1 一句话

> 主 Agent 的快捷键按下之后，整个**这两张卡片**分别是做什么用的？上面的右上角这张卡片是
> **实时的显示 AI 对用户的任务的理解**，让用户看到是不是正确的理解。

### 1.2 两张卡片的分工（用户 2026-09-27 定稿）

| | **右上角**（鼠标右上方） | **右下角**（鼠标右下方） |
|---|---|---|
| 存在的时段 | 按下快捷键 → 发送之前（含追问窗口） | **同一段** |
| 是什么 | **AI 对任务的理解对不对** | **答案预览**：对用户提问的回答 |
| 内容 | 选项 / 理解四行 / 输入框 / 取消三列 | 一段答案（与最终结果同一张卡片） |
| 交互 | 点击确认·否定、口述、键盘输入 | 只读 |
| 发送之后 | 收起 | 让位给真正的结果 |
| 打断或答完继续说 | 两张一起重新出现（"大循环里的小循环"） | 同左 |

### 1.3 逐条需求

**A. 选项（"任务方向"）**

1. **只有一个来源**：「就是一个固定的文件。我记得之前我是添加了 3 个还是 4 个来源，什么实时的，
   **这都不要**」。这个文件可以被三种方式改：**AI 之后改**、**人手动改**、
   **每天中午 12 点复盘 agent 定时追加**（先去重再追加；扫用户全部历史记录与聊天记录，
   出现**超过两次**的才收成 **3~7 个字**的选项）。
2. **判断用 JEV 决策模型**，是**实时**的：「因为用户的提示词一直在变，所以说它根据用户的提示词
   变化来去判断出来用户当前正在做的事情到底是什么」。
3. **选项可不显示**：「用户的需求可能是全新的，它会导致这些选项……显示不出来，那么如果显示不出来的话，
   就**不要去强制性的显示**」。
4. **点击与口述都要保留**：「这个表格里面这些选项它可以被点击的……或者是可以被否定，对不对？
   这个要**保留**」。

**B. 固定（用户明确说过的方向）**

5. 「只要用户明确的说哪一个方向对，哪一个方向不对，就要把这个最终确定的……**一定要去在卡片上显示，
   无论是对还是不对都要显示**」。**没说过的可以自由替换、自由轮换**。
6. 固定**保留到用户说取消**（「除非在用户下一次说取消任务方向一……」）。

**C. 两拍语义**（用户讲得最清楚的一段）

7. 「这 3 秒呢，同时调用了 JEV 模型，也同时调用了大语言模型……而这个理解是由大语言模型在
   **第二轮**……**你必须要知道用户表达的是对上一轮 JEV 模型它的结果的一个选择**」
   → 用户对选项的评论**由大模型在下一轮读懂**，并且它说的编号指的是**上一轮那一列**。
8. **跨轮连续性**：「你要在发送给下一轮模型的时候要**保留前三轮**，然后你要标记一下……
   最早的那一轮和最近的那一轮分别是什么，然后让它**重点参考最近一轮**」。

**D. 理解四行**

9. 格式固定、**换行显示、可多行**：「AI 对任务的理解是有格式的，比如软件是什么、文件是什么、
   目标是什么、类型是什么、细节是什么」；随后收敛成用户点名的四行
   **目标问题 / 类型 / 参考 / 细节**（「第三行是内容参考，或者叫参考……**它就是两个字**」）。
10. **不许跳**：「他回复结果的时候**总是跳、总是蹦**……内容有时候有软件目标细节，有时候没有，
    就是突然间有、突然间没有。**这几行固定在这**……这对体验影响太差了」。
11. **要有动画**：「这个卡片返回的结果是**一次性返回**的……我希望让它有一种**动画效果**，
    而不是突然间显示出来」。

**E. 右下角答案预览**

12. 「鼠标右下角这部分显示的是对用户提示词回复的一个**结果**……右下角这卡片其实就是一个
    **答案的预览区**」，而且「跟正常的这个任务执行之后返回结果的**卡片的动效、文字的效果渲染效果
    是一样的**」。
13. 判据是**有没有问题**：「你就要去识别出来用户的意图里面是不是**包含问题**」
    （「北京在哪」「杨幂是谁」「左右两张图有什么区别」「这道题选 A 还是 B」）。
14. 参考材料要**打标签**：屏幕截图 + 用户提示词 + 已确定的选项 + 右上角卡片的内容，
    **以用户的提示词为目标**。
15. **每轮都要能看见屏幕**（这是他实测报回来的）：「他为什么会显示**没有看到屏幕**呢？
    **他应该直接看到屏幕啊**」。
16. **不朗读**（我定的：他正在说话，念出来会和麦克风打架 —— 见 §5 的取舍清单）。

**F. 发送（按下第二次 / 静音自动发送）**

17. 发什么：「如果用户明确的说了哪一个选项，那个选项的时候**才去发这个选项**，
    **如果没说的话就不要发**……你也不要去把什么猜测的比例概率什么……也不需要去发送」；
    「这个词跟**描述**的部分就会作为提示词的一部分来去发给 AI」；
    「这个大语言模型的理解，你可以去发，发过去」。
18. **转写后面加一段固定说明**：「必须要去再增加一个……系统提示词，来去备注到用户的刚才
    **整段转写的文本的后面**，然后去让 AI 理解到其中用户关于……方向一、方向 2、方向 3，
    他是关于这个某一个位置卡片的任务的理解，然后这部分**不是真正的要去执行的任务**……
    **你帮我梳理出来一个这个提示词是固定的就可以，不需要实时生成**」。
19. 发送之后**两张卡片一起消失**，主 Agent 的结果照常落右下角。

**G. 取消**

20. 板子最下面一行三列：**取消本次 / 取消十分钟 / 取消今日**（今日 = 到明日凌晨 0 点，不是 24 小时）。
21. 总闸门也可以口述：「取消任务看板」或「取消任务方向」（**必须精准**，「取消任务」四个字不算）。
22. ESC = **全部取消**：后端监控、两张卡片、所有进程。

## 二、设计（为什么是这个形状）

### 2.1 一次请求，三节输出

每 3 秒那一轮**只调一次大模型**（用户：「同时也调用了一个大语言模型」），它一次产出三样：

```
目标问题：…   类型：…   参考：…   细节：…     ← ① 理解四行（画在右上角）
答案：…                                        ← ② 答案预览（画在右下角，没有就不写这一行）
选择：1 对，3 不对                              ← ③ 对上一轮选项的判定（没有就不写这一行）
```

三节**各自解析**（`DirectionBoardPrompt.parseUnderstandingLines` / `parseAnswer` /
`DirectionBoardMatching.parseSelectionVerdict`），任一节缺失不影响其余两节。
选这个形状的理由：省钱（一次调用 vs 三次）、延迟低（答案与理解同时到）、
而且**三样本来就共享同一份输入**（用户的话 + 屏幕 + 方向清单 + 上一轮那一列）。

### 2.2 两拍判定：为什么必须记「上一轮那一列」

- 第 N 轮：JEV 按概率选出 1..N 格 → 画在板上；
- 用户说「方向一对、方向二不对」；
- **第 N+1 轮**的请求里带上「上一轮显示的是哪几格」（编号 → 关键词 + 当前状态），
  模型回一行 `选择：1 对，2 不对`；
- 代码用**上一轮的编号映射**回填固定状态。

**为什么不能按当前屏幕的编号回填**：JEV 每 3 秒重判一次，用户说话的这几秒里那一列**可能已经重排**。
所以 `DirectionBoardSession` 存一份 `previousRoundItems` 快照，
`parseSelectionVerdict(_:previousRound:)` 收的就是它。有单测钉着这条
（含"上一轮第 2 个这一轮已经换人"的情形）。

**由此删掉的东西**：本地那一整套"口述第 N 个方向"的正则解析（`spokenSelectionNumber` /
`spokenCancelSelectionNumber` / `applySpokenSelectionIfAny`，以及曾经为了修"说第二个方向却选了两格"
而加的编号映射表）。口述统一走大模型那一拍、**点击仍然是瞬时的**。
只有**总闸门**（「取消任务看板」）继续本地判定 —— 它要立刻生效。

### 2.3 显示规则：固定项在前，且"对"和"不对"都留着

```
[ 固定的（按固定顺序，编号 1..k，✓ 或 ✗）] + [ JEV 过阈值的（可轮换，编号接着排）]
```

- 固定项**不参与 JEV 提问**（状态已知，省一次判断）；
- 列数满了（默认最多 10 格、屏幕上一行 5 列）**先砍 JEV 那部分**，固定项一个都不砍；
- 用户没提过的那些**可以自由轮换** —— 这正是他说的"其他没有说过的……都可以自由的替换"。

### 2.4 数据放在哪

| 数据 | 文件 | 为什么在这 |
|---|---|---|
| 方向清单 | `~/Library/Application Support/Wanna/TaskDirections.json`（0600） | 用户说它只由 AI / 人 / 复盘改，所以**只有那三个写入口** |
| 用户的固定状态 | 同目录 `TaskDirectionPins.json`（0600） | 他选的是"一直保留到说取消"（跨大轮、跨对话），所以要落盘；而**不写进清单** —— 清单要保持是"一份可读的备选项列表" |
| JEV key | 同目录 `JevKey.txt`（0600） | 不进 `AppSettings`，所以**导出设置不会把它带出去** |

三个文件都是同一个形状：`nonisolated` + `NSLock` + 原子写后补 0600 + 变更通知（仓规）。

⚠️ 一个死锁的坑：`TaskDirectionStore` 的**公开入口只加一次锁**，内部一律叫 `…Locked`
（假定已持锁）。第一版是 `allDirections()` 持锁 → `loadFromDisk` 里又调 `write` 再锁一次，
`NSLock` 不可重入 → **第一次读清单就死锁**，App 卡死在 Listening。

### 2.5 节奏闸门（三条，都是用户要的）

每 3 秒看一次，但**要同时满足**才发：

1. 识别文本**变了**（用户：「检测这 3 秒之内用户的提示词是否跟上次相同，如果相同就不发送」）；
2. **新增 ≥10 个字**（标点不算；用户：「如果 3 秒之内用户新增的内容少于 10 个字，也不发送，
   因为相当于这句话还没说完」；阈值在设置页可调 5…20）；
3. 同时**最多一个请求在飞**（代次计数丢弃过期回复）。

### 3.4 关键类型

```swift
// 一条方向（清单里的一行）
struct TaskDirection { id; keyword; detail; matchKeywords: [String]?; source; addedAt }

// 用户明确说过的判定（存 TaskDirectionPins.json）
enum TaskDirectionStore.PinState { case confirmed, denied }

// 板上的一格（每一轮算出来）
struct DirectionBoardDisplayItem {
    directionID; keyword; number;          // number 从 1 开始、连续
    state: .pending / .confirmed / .denied
    reason: .pinnedByUser / .localKeyword / .jevProbability
}

// 提交时带走的东西
struct DirectionBoardTurnDecision {
    confirmedDirections: [(keyword, detail)]
    typedInput: String
    understanding: [(label, value)]
}
```

### 3.5 提示词

**系统**（`understandingSystemPrompt`）只给方向清单（约三百 token，不是主 Agent 那五千字）+
那三节的格式要求 + 「每一轮都带了当下的屏幕截图，请**看图**再回答……**看不到就照实说，不要编**」。

**用户消息**（`understandingUserPrompt`）三块：用户说的话 / **上一轮显示的那一列**（编号 + 关键词 + 状态，
并说明"如果用户在评论这些方向，请按**这套编号**理解"）/ **最近三轮的理解**（标「最近一次 /
倒数第二次 / 倒数第三次」，写明以最近一次为主）。

**发送时的两个块**（`DirectionBoardPrompt.decoration` + `boardReferenceNote`）：

```
<user_intent_tags>
用户真实意图的任务方向是：看图说话（看屏幕或某张图，描述/识别里面有什么）
模型对这次任务的理解是：目标问题：…；类型：…；参考：…；细节：…
用户的补充说明是：…
</user_intent_tags>

<screen_contents> …（图形界面读取，如果有）… </screen_contents>

the user just said, out loud: <用户原话>

<board_reference>
上面这段转写里出现的「方向一 / 任务方向 3 / 第 4 个」这类说法，是用户在跟屏幕上那块任务方向看板
交互（确认或取消某一条方向），**不是**要你执行的任务本身 —— 请忽略这些片段，只按其余的话执行。
</board_reference>
```

### 3.6 三个解析器（最容易静默出错的地方）

| 解析器 | 契约 | 已踩过的坑 |
|---|---|---|
| `parseUnderstandingLines` | **永远返回四行**（缺的值是空串），按用户定的顺序 | ① 模型把四行写在**同一行**里（要按标签位置切）② `目标问题:` 里嵌着 `目标:` 与 `问题:`（要去重叠，否则那一行被切成三段空值）③ 模型写回老标签（`软件`/`文件`/`目标`）—— 每行带一串**别名** ④ 「答案」「选择」是**边界标签**：只截断、不成行 |
| `parseAnswer` / `parseSection` | 取「标签:」到行尾或下一个标签处，最多续两行；**没有就返回 nil** | 解析读的必须是**原文**，不是被 200 字上限截过的显示文本（否则「细节」写到一半就断了） |
| `parseSelectionVerdict` | 按**上一轮的编号**回填判定；认阿拉伯与中文数字 | ① 不能按空格/逗号切（`1 对，3 不对` 会被拆成四段、每段缺一半）② `取消 2` 的判定词在编号**前面** → 取"两个编号之间那一段" ③ 越界的编号直接忽略（不猜） |

### 3.7 视图与那两块窗口

**卡片四段**（自上而下）：编号方向格（多列，最多 5 列）/ **理解四行**（标签列定宽 50，
空值画 `—`）/ 三行输入框 / 暗红三列取消（分割线**纯白**、1.5×20）。

- **高度恒定**：四行永远画着（即使是占位符），所以模型怎么写卡片都不跳；
- **淡入**：每行的值带 `.id(value)` + `.transition(.opacity + offset(y:6))`，
  外层 `.animation(.easeOut(0.28).delay(行号 × 0.05))` —— **逐帧验过**（回复落地那一刻连拍五帧，
  第一帧占位符正在上移、错开不同高度，末帧就位，骨架全程不动）；
- 宽度 = 340 × 设置倍数（默认 2 → 680），**与内容无关、恒定**。

**那块面板**（`DirectionBoardPanelController`）三条分寸：

1. **不抢键盘**：`orderFrontRegardless()`，绝不 `makeKey()`；`becomesKeyOnlyIfNeeded = true`
   —— 只有点了输入框才是 key；
2. **尺寸归 SwiftUI、位置归我们**：`NSHostingView` 会按内容改窗口尺寸（
   `updateAnimatedWindowSize` ← `windowDidLayout`）而且**保持顶边** —— 实测它把窗口一路推到
   `AppKit y = -7`（底边掉出屏幕，卡片最下面那行被切）。所以订阅 `NSWindow.didResizeNotification`，
   每次改尺寸之后用「锚点 + 夹进屏幕」重算**原点**（只改原点，所以不成环）。净效果正是用户要的
   「左下角固定、内容往上长」；
3. **按住自动发送**：`holdsTheAutomaticSend()`（鼠标在板上 / 面板是 key / 2 秒内交互过）
   —— 静音到点那一下据此按住不发，并让边框呼吸一下（用户：「让用户知道任务没有完成、没有发送出去」）。

**右下角那张卡片**（`OverlayWindow`）只多了一个数据源：

```
conversationBubbleText：完成通知 → streamingAnswerText → **answerPreviewText** → liveTranscriptText
渲染分支：streamingAnswerText 或 answerPreviewText 非空 → 那张 AnswerCardView
```

→ 「跟正常结果卡片的动效与渲染一模一样」是**结构上成立**的，不是照着调的。
预览由看板通过**注入的闭包**写进 `CompanionManager.answerPreviewText`
（与 `voiceIdleProvider` / `sharedVoicePlaybackEngineProvider` 同一个先例：
跨子系统只走注入，不让对方去猜）。

### 3.8 设置页（设置 → 操作 → 任务方向看板）

总开关 / 看板宽度（1、1.5、2 倍）/ 每隔 3 秒问一次的门槛（新增字数 5…20）/
概率阈值（0.3…0.9）/ 取消状态 + 立刻恢复 / **方向清单**（在访达中显示、恢复默认、逐条删除、手动加一条）/
**已固定的方向**（列出 ✓✗、全部取消）/ JEV API Key。

## 四、怎么验证

### 4.1 单测（`WannaTests/DirectionBoardTests.swift`，37 条全过里的一部分）

- 关键词命中（**4 字以下只认精确** —— 3 字关键词给容错会误命中：「帮我**点一下**」命中「**存一下**」）；
- 显示组合：固定项排最前 / 编号稳定 / ✓✗ 都留 / 列数满了先砍 JEV；
- 判定回填：**按上一轮编号**（含"上一轮第 2 个这一轮换人了"）、越界忽略、中文数字、`取消 2`；
- 四行解析：永远四行、同一行切得开、别名、去重叠、边界标签；
- 答案：可以没有、续两行、与理解互不影响；
- `decoration`：只带确认过的（关键词 + 描述）、理解无条件带、顺序固定；
- 节奏闸门：文本没变不发 / 标点不算字数 / 取消后不发。

### 4.2 自检钩子（这台机器没有可用语音输入，这是唯一的端到端办法）

```bash
WANNA_DIRECTION_BOARD_SELFCHECK=live script -q /dev/null /Applications/Wanna.app/Contents/MacOS/Wanna
# 1 = 假转写、不发请求；live = 真发；stream = 只按 12 字/秒喂字幕（量卡顿用）
```

注入的句子**必须是用户真说过的那句**（这一点是踩出来的：自检原来注入的是带「参考屏幕」四个字的
那句，正好绕开了"要口令才截图"的 bug，一路绿）；间隔 3.5 秒（**大于一轮的节奏**，
否则三句挤在同一轮里，跨轮行为验不到）；`live` 模式下会打印**模型回的原文**，
用来分辨"模型没写"还是"解析器没认出来"。

### 4.3 真机验过的事（都带截图/日志）

## 八、2026-09-27 晚补：用户实测报的两个问题

### 8.1 右下角"显示了两个回复"（已修）

**现象**：他按住快捷键问第一句，右下角先显示一个回复，**没过半秒钟又变成一个全新的回复**。

**根因**：提交那一刻就把预览收了（`consumeTurnDecision` → `answerPreviewWriter?(nil)`），
而真正的答案要 1~2 秒才到 —— 于是卡片**先消失、再被真答案重新画出来**，两次内容还不一样。

**修法**：**交接**而不是"收掉再来"。
- 提交时**不动**预览（卡片一直挂着，不空一帧）；
- 真答案的**第一个字**到达时（`CompanionManager` 流式写入那一处）调 `clearAnswerPreview()`
  —— 两段文字落在**同一张卡片**上，用户看到的是"答案被补全了"；
- 这一轮被打断（`clearAnswerBubble`）、或下一轮真的开始（`beginListening`）时才收。

### 8.2 "连续问到第六七轮就卡死"（**根因未定，先装仪器**）

**现象**：一次快捷键之后连续追问，到第六七轮**字幕不再显示任何内容、问它也不回复、
三块界面全无变化**，但「不是软件卡死不能用」。

**为什么这一轮我没有直接修**：他说「你可以看一下刚才的记录」——而**那条路一个字都没落盘**。
双击启动的 App 里 `print` 进不了任何地方（既不是终端，也不在统一日志里：
`log show --predicate 'process == "Wanna"'` 返回 0 行）。唯一存在的日志是**长录音**那条路的
`录音诊断.log`，与这条链无关。**没有记录就没有根因**，靠读代码猜出来的结论这个仓库不接受。

**能排除的**（读过代码）：`VolcengineTranscriptionProvider.beginNextUtterance()` **有**重置
`connectionRecoveryAttempts = 0`，所以不是"重连预算用光"那一类。

**装了什么**（新文件 `Wanna/MainFlowDiagnostics.swift`，日志落在
`~/Library/Application Support/Wanna/主Agent诊断.log`）：

| 记什么 | 为什么是这一行 |
|---|---|
| **音频心跳**：连续监听期间每 2 秒一行 `N 块/2s 峰值 x.xxx` | **一句话三分**：0 块 = tap/引擎没了；有块但峰值恒 0 = 设备哑了（跨进程那一层）；有块有峰值 = 音频**到得了**，故障在下游（识别会话/网络） |
| **识别会话的生命周期**：这一句开始 / 定稿到达（带字数）/ tap 装 · 撤 | 「他说话了但没有字」与「字到了但没提交」是两件事 |
| **看板每一轮**：第 N 轮发请求（带转写字数） | 「看板不动了」是闸门没过还是请求没回来 |
| **主线程看门狗**：后台每 1 秒往主队列投一次，往返 > 2 秒就记一行**带当时的阶段标记** | 他的两句话（"不是软件卡死" / "界面没有任何变化"）正好是两种成因：主线程被堵住 vs 主线程闲着各条链各自停摆 |

分寸：只写文件、**不在主线程做 IO**（纯入队）；2MB 轮转；**不改变任何行为**。

### 8.3 顺带：截图从"每轮一张"改成"一句一张"

上一版为了修「他应该直接看到屏幕」把截图改成了**每一轮请求都截**（每 3 秒一次全屏
`SCScreenshotManager` 抓取）。现在改成**一句一张**：第一次请求时截、这一句里复用、
用户说「参考屏幕 / 看屏幕」时作废重截（他原来那条「每一次转写识别到就截一次屏」照旧成立）。

**这是省开销**（一句从 ~7 张降到 1 张，模型侧也少收 6 张图），**不是**"卡死的修复" ——
两者在时间上重合，但**相关不等于因果**，在拿到 8.2 的日志之前不许写成结论。

### 8.4 「按住 ESC 退出之后，右下角的卡片没有退出，一直跟着鼠标」（已修，**这是我引入的回归**）

**根因**：8.1 那次的修法把"收预览"从**提交那一刻**挪走了（挪到"真答案的第一个字"），
却没有给**其余出口**补上 —— 而 ESC 打断走的是 `cancelTurnByEscapeWhileListening()`，
它**不经过**答案管线，于是**没有任何人来收那张卡片**。用户看到的就是它永远跟着鼠标。

**修法（四道，前两道是结构性的）**：

| 道 | 在哪 | 管什么 |
|---|---|---|
| ① **相位** | `NotchWindowController.setActivityPhase(_:)` —— **相位的唯一写入口** | **相位一旦变成 `.idle` 就作废预览**。ESC 打断、监听窗口到期、空转写、以后新加的出口 —— 全都经过这里，**不可能再漏**。判据是 `== .idle` 而**不是** `!= .listening`：提交之后相位要先经过 `.transcribing`（等定稿）再 `.thinking`（截图 + 视觉请求），那段正是"预览等着被真答案交接"的 1~2 秒，用 `!= .listening` 会把它清掉 —— 那就又回到 8.1 的"两个回复"（两个 bug 会把对方改回来，这是量出来的） |
| ② **轮次出口** | `DirectionBoardSession.endListening(keepPreview:)` | 提交那一轮传 `true`（留着交接），**其余出口默认清**。三个调用点各自明确：ESC 清、`handleFinalTranscript` 留、窗口关闭清 |
| ③ **交接** | `CompanionManager` 流式写入第一处 | 真答案的第一个字到达时清（同一张卡片换内容，不空帧） |
| ④ **管线收尾** | `currentResponseTask` 的 `defer` | 覆盖"提交了但**根本没有答案**"——纯执行类任务不写 `streamingAnswerText`，第③道永远不会触发，不收就是又一张跟着鼠标的卡片 |

**单测钉着**（`onlyTheSubmittingTurnKeepsTheAnswerPreview`）：提交那一轮 `answerPreviewWriter` 一次都不写；
放弃那一轮写一个 `nil`。

⚠️ **教训**：一个"只在某个出口收"的资源，出口一多就必然漏。
**寿命要挂在那个子系统里唯一的那份真相上** —— 这里是相位。
（这一条与 `开发经验/18-状态类问题的查法.md` 是同一件事的两面：该写的那一格没人写 → 先找判据。）
