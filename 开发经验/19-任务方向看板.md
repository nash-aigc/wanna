# 19 · 任务方向看板（鼠标右上角，说话期间显示）

> 用户 2026-09-27 的需求（原文是一份完整的规格，见下面各节的引文）。
> 一句话：**主 Agent 说话的时候，除了刘海下面那行字幕，鼠标右上角还应该有一块板**，
> 告诉他「AI 现在怎么理解你这次要做的事」，并让他点一下确认/否认。右下角那块仍然是结果。

## 一、它长什么样

```
┌─────────────────────────────────────────┐
│ 笔记类  [保存到 Notion   ] ✗  [存成一条录音] ✗ │   ← 3 行 2 列 = 6 个方向
│ 显示类  [指给我看      ] ✗  [圈出来      ] ✗ │      第 1 行笔记类 / 第 2 行显示类 / 第 3 行执行类
│ 执行类  [操作电脑      ] ✗  [派个 Agent ] ✗ │
├─────────────────────────────────────────┤
│ 用户想让我把屏幕上的那段文字存进 Notion。      │   ← AI 的理解（每 3 秒刷新一次）
├─────────────────────────────────────────┤
│ [ 补充说明（会一起发过去）              ] │   ← 用户手打的补充，也一起发过去
└─────────────────────────────────────────┘
```

- **位置**：鼠标**右上角**（`NotchSupport.directionBoardPanelFrame`：左下角 = 鼠标 +12pt，向右上展开，
  夹进屏幕、避开刘海那条带子）。**锚点只在显示那一刻取一次** —— 用户：「位置固定，不随鼠标移动」。
- **宽度与样式与右下角那张结果卡片完全一致**：`AnswerCardView` 的那几个常量与 `cardBackground`
  2026-09-27 放开成 internal，看板读的就是同一份（宽度固定 340）。
- **点文字 = 确认**（文字变绿、叉变对勾）；**点右边的叉 = 否认**（文字与叉整体变红）；再点一次取消。
  已决定的格子**冻住**：AI 之后改不了一格已经被点过的文字（否则他确认的那句话会在他眼前变成另一句）。

## 二、什么时候出现、什么时候消失

**与刘海那行字幕同一个判据**：`NotchPanelModel.notchBandSitsAboveTranscriptLine`
（= `activityPhase == .listening && !isFullscreenSuppressed`），写在
`NotchWindowController.syncListeningTranscriptPanel()` 里一处 —— 两者不可能不一致。

用户的原话：「当用户按住快捷键时，即用户说话时，就持续显示，直到用户按下快捷键发送问题，
或等待 2 秒自动发送问题后才不显示。返回结果之后也不显示，因为返回结果由右下角卡片显示。」

所以：按下快捷键 → 出现；提交（快捷键 / 2 秒静默）→ 收起；结果由右下角那张卡片负责。
刘海面板铺开时**整块不显示**（那块面板盖住全屏，与结果卡片同一条规矩）。

## 三、六格里的文字怎么定：**预设优先，AI 兜底**

用户 2026-09-27 的原话：「如果用户预设的内容没有匹配到，就让 AI 生成；如果用户关键词已经匹配，
就显示用户匹配的内容。因为用户可能会说『保存到 Notion 什么什么页面』，AI 可能识别不了，
所以**以用户提前预设的为准**；如果没有预设，就让 AI 生成。」

展开成三条（`DirectionBoardConfiguration.displayText` 一处实现，视图与"发出去的标签"都读它）：

1. **本地关键词命中** → 整行都用预设短语（命中的那一格高亮绿框）—— **AI 不许覆盖**；
2. **没命中** → **第 1 格**显示 AI 写的短语（≤12 字），第 2 格仍然是预设；
3. **没命中、AI 也说「无」** → 两格都是预设，谁都不高亮。

⚠️ **短关键词只认精确匹配**（4 字以下），这是探针逼出来的：3 字关键词给容错 1 时，
「帮我**点一下**那个发送按钮」会命中笔记类的「**存一下**」—— 点亮错方向，而且本地命中还会
**压掉**那个方向本该由 AI 给的标签。宁可少命中（交给 AI），不许误命中。

## 四、那次请求（每 3 秒一次，文本变了才发）

- **模型**：主 Agent 的 🧠（`BailianVisionChatAPI.analyzeImageStreaming(images: [])`，纯文字、
  自动关推理）；当前活动卡片配了别的 AI 就用那一张（`CompanionManager.visionRoleOverride(forCardID:)`）。
- **系统提示词**：`CompanionManager.directionBoardSystemPrompt(for:)` = **主 Agent 那份逐字相同**
  + 一节「怎么把理解结果写成看板要的格式」。用户：「以保证 100% 模拟主 Agent 的思考方式」。
  ⚠️ 那一节**只加在这次请求上**，真正回答用户的那一轮不带它。
- **用户消息**：`<transcript>` 当前识别文本 + 六个预设短语（让模型用词一致）+ **只列本地没命中的行**。
- **节奏**：每 3 秒看一次，**只有识别文本跟上次发出去的不一样才真发**（用户在我问「3 秒一发 vs
  文本变了才发」时选了后者）；同时最多一个请求在飞；代次计数丢弃过期回复；失败保留上一次的结果。
- 闸门收在纯函数 `DirectionBoardSession.shouldRequest(...)` 里（会话本身脱离 App 编不起来，
  收成纯函数探针才能把五条各试一遍）。

### 解析：认不出来的行一律并进正文

模型被要求回：

```
<<<看板
说明：<一到两句，≤200 字>
方向1：<≤12 字；不适用写「无」>
方向2：…
方向3：…
看板>>>
```

规则（每条都有断言，`DirectionBoardPrompt.parseResponse`）：只认 `说明:` / `方向N:` 开头的行
（全角冒号、`**说明**：`、代码块都认）；值取**第一个**冒号之后；同键重复**先到者胜**；
「无/-/空」= 这一行没有标签；**其余每一行都并进说明** —— 多写的、少写的、被截断的都不会丢，
也不会被当成标签；完全不成形时保留上一次的说明（绝不把正文清空）。

⚠️ **标签上限 12 字，不是 8**：用户自己的预设短语里「保存到 Notion」是 10 字、
「派个 Agent 去做」是 11 字，模型很可能原样回一个预设 —— 8 字上限会把它截成「保存到 Noti」，
而且**是静默的**（屏幕上只是少了一个字母）。探针抓到的。

## 五、提交时那几行（注入）

用户：「将记录内容作为标签追加到用户提示词的前一行，格式为「用户真实意图的任务方向是：XXX」，
下方再接用户原始提示词。输入框中用户手动输入的内容 → 同样作为标签追加进去。未点击的项不追加标签。」

```
<user_intent_tags>
用户真实意图的任务方向是：保存到 Notion
用户真实意图的任务方向是：指给我看
用户的补充说明是：顺便截图
</user_intent_tags>

the user just said, out loud: 帮我把这段存起来看看
```

两处分寸：

1. **只写点过确认的**（没点的、点否认的都不写；输入框为空就整段不出现）；
2. **只进发给模型的提示词**，不进历史、不进界面上那两颗气泡 —— 会话记录里仍然只有用户自己说的话。
   所以它单独一个 `<user_intent_tags>` 块，**不塞进 "the user just said, out loud:" 里**：
   那几行不是他嘴里说的，是他在看板上点的。

**取走只在一处**：`sendTranscriptToVisionChatWithScreenshot` 的开头（四条提交路径全部经过它：
快捷键发送 / 2 秒静默 / 确认模式轻点 / 连续追问），所以不可能漏一条、也不会取两次。
其余"这一轮结束了但没发送"的路（ESC 打断正在听、追问窗口关闭、空转写）都显式取走丢掉 ——
否则他点过的方向会跟到下一次**打字**提问上。

## 一、改了什么

| 项 | 第一版 | 第二版 |

## 二、几条关键规则（都有断言）

- **只显示说到的**：`DirectionBoardConfiguration.displayedItems(transcriptText:modelRowLabels:configuration:)`
  —— 本地命中 → 显示命中的那个预设短语；没命中但有 AI 标签 → 显示 AI 的；两者都没有 → **这一行不出现**；
  编号最后统一按行序分配 1…N。
- **口述选方向**：`spokenSelectionNumber(in:displayedItemCount:)` 认出「第 N 个方向 / 方向N / 选第 N /
  参考第 N」；**超出屏幕上现有格数的编号直接忽略**（他说「第六个」而屏幕上只有三格时，猜一个等于替他做决定）。
  另有 `spokenRowSelection(in:configuration:)` 认语义那一种（「关于显示方向的」），
  要求**类别名紧跟一个方向词**（方向/类/方面）—— 只认类别名本身会误报（光说「把这段**文字**存到 notion」
  里的「文字」不该把「文字类」也选上）。这一条是探针逼出来的：「显示类」根本不是「关于**显示方向**的」
  那句转写的子串。
- **上一轮的结论**：`previousReading` 把模型上一次的原文整段存下来（截 600 字）带给下一次请求 ——
  用户点名要的（「每一次都是全新的内容」）。不做字段提取：省了字段就得再写一套提取规则，
  而那是模型自己的话，它读得懂。

## 四、这一版我自己搞出来的一个 bug（记下来）

第一次把「说出字才显示」加上去之后，**自检看不到面板了** —— 因为那道闸门读的是
**刘海那行字幕**的文本（`NotchListeningTranscriptModel.liveText`），而当时的自检只喂了看板自己的文本。

要改的是自检（把两个都喂）。

# 第三版（2026-09-27 傍晚）：**"在看板上操作"时不许自动发送**，总结也能确认/否认

用户的原话：

> AI 播报时……它处于持续监听状态。无论用户打断它，还是用户在持续监听过程中又说了话，它其实还是会
> 识别用户内容，继续进行几秒钟一次的监听，并显示任务方向的卡片。问题在于……如果用户两秒之内没有说话，
> 就自动把用户说的话当作任务直接发送……那么如果两秒之内用户没有说话，而是在操作任务方向的看板，
> 或者在任务方向的看板上打字，就会出现问题。**所以一定要加上一个检测机制。**
> ……检测一次用户的鼠标是不是在这个看板上，或者这个任务方向的看板是不是被激活、被点击、正在输入。
> 如果鼠标在看板上，就让看板**边框闪一下、高亮一下或呼吸灯一下**，让用户知道任务没有完成、没有发送过去，
> 而不是直接发送任务。
> ……等待过程中，如果用户又说了话，**不要把用户这个全新的内容当作一个全新的任务，而是把它当作后来
> 追加的提示词**……本质上就是没有发送任务，没有发送任务其实就是打断到发送任务中间的内容。
> ……**在系统总结这块，也要增加一个选中或者确认、否认的按钮，即添加一个 X 叉按钮。**

## 一、那个检测机制

**在哪一层**：`BuddyDictationManager` 的连续监听 VAD 循环里，静音倒计时到点、正要
`requestContinuousListeningFinalTranscript()` 的那一处。

**怎么接**：音频层**不认识看板** —— 它只问一个注入的布尔量
（`automaticSendShouldWaitProvider`，与 `sharedVoicePlaybackEngineProvider` / `recordingActiveProvider`
同一条规矩：**注入判断，不注入模块**），外加一个 `onAutomaticSendHeld` 回调。

**三个判据**（`DirectionBoardPanelController.holdsTheAutomaticSend()`，满足一个就算"他正在跟看板打交道"）：

1. **鼠标在板上** —— `NSEvent.mouseLocation` 落在面板矩形里；
2. **面板是 key** —— 他点了输入框正在打字（`becomesKeyOnlyIfNeeded` + `becomeKey` 回调记一笔）；
3. **上一次交互在 2 秒内** —— 点完立刻把鼠标挪开一点，仍然算"他还在弄这个"。

**按住之后发生什么**：不发送、**静音倒计时从头再来**（`continuousListeningSilenceStartedAt = now`），
并让看板呼吸 1.2 秒（`DirectionBoardSession.isHeldFromAutomaticSend` → 视图把边框换成琥珀色并加粗，
`.easeInOut(0.35)`）。

**"后来追加的提示词"是免费的**：窗口没关、识别没停，所以他再说话时那句话**自然接在同一句里** ——
中间不会有一次发送，也就没有被切成两个任务。这正是用户要的那条语义。

**为什么把检测放在"到点那一刻"而不是 1.5 秒**：他建议 1.5~1.8 秒时查一次，但那样会出现
"1.5 秒时鼠标不在板上 → 2.0 秒发送"，而他在 1.7 秒时把鼠标挪上去了 ✗。**查得越晚越准**，
所以放在正要发送的那一帧查。（他说"检测一次可能花很长时间"—— 这个判断是一次点到矩形的包含测试，
不花钱也不阻塞。）

## 二、AI 那段总结也能确认/否认

- `DirectionBoardSession.summaryState` / `summaryConfirmedText`（与方向格同一套两态）；
- 视图：总结区右边一颗 ✓/✗（点正文 = 确认、变色；点叉 = 否认、变红），**只有真的有总结时才画**；
- 取走时：确认过的总结会作为一条标签发过去 —— `用户确认的任务理解是：<那段话>`（与方向那条同一个形状）；
- **空的总结确认不了**（`!confirmedSummary.isEmpty` 才收）—— 探针里那次正好验到了这一条：
  探针没跑请求、总结是空的，确认之后装饰里只出现方向那一条 ✓。

## 三、用户输入框那一条

用户：「如果用户输入了提示词，就一定要发送；但如果输入的提示词是空格这些没有意义的符号，

对输入框那句先 `trim`，空了整段不出现（探针 15 节实测：`typedInput = "   "` → 装饰里没有那一行 ✓）。

## 五、第三版之后又调了一次发送节奏（同一天）

> 用户按下主 A 快捷键时，会从最开始检测用户的提示词，然后发给 AI。之前是每隔 3 秒发送一次，
> 我觉得太机械了。你刚才说的那个检测机制比较好，要保留：检测这 3 秒之内用户的提示词是否跟上次相同，
> 如果相同就不发送。**在此基础上再增加一个：如果 3 秒之内用户新增的内容少于 10 个字，也不发送**，
> 因为相当于这句话还没说完。**标点符号不算字数**……比如用户只说「嗯」「啊」这类没有意义的词，
> 发送也没有意义。

所以闸门现在是**三条**（全在 `DirectionBoardSession.shouldRequest` 这一个纯函数里）：

1. 每 3 秒看一次（`cadenceSeconds`）；
2. 内容跟上次发出去的不一样；
3. **新增 ≥ 10 个字**（`minimumAddedCharacters`）—— 标点、空格、表情都不算。

或者这是追问窗口里的**新一句**）→ 从最长公共前缀之后算起。

**旧的 4 字门槛删掉了**（被 10 字这条取代，留着就是同一个问题两个答案）。

"≥10 → 发"）。**代码没错，是断言错** —— 记在这里是因为它正是"探针的价值在断言本身要准"这件事的实例。

## 一、取消的三档与它们的语义

# 第五版（2026-09-27 深夜）：字幕卡顿的根因、多列布局、口述取消某个方向

用户的三个问题：

> 1. 我在说话的时候，刘海下面这个字幕非常卡顿……**这个字幕必须非常顺畅。**
> 2. 表格上面那几个表格应该是**多列**的，不是单列……我最开始跟你说的是这个卡片的宽度一定要跟
>    正常情况下 AI 生成结果那个卡片的宽度一致，**现在取消这个限制**，它可以很宽，但是**左下角的
>    位置必须固定**。AI 总结出来这个卡片的**关键词最好是在 3~7 个字**……最多不要超过 5 列。
> 3. 用户说第一个方向正确的时候，它能识别……但是如果用户说**取消第一个方向**，我发现它无法取消……
>    **这个是必须要有的。**

## 一、字幕卡顿的根因：**动画时长 0.6 秒 vs 识别结果每 0.1 秒一次**

`NotchTranscriptMarquee.SmoothRevealedTranscriptText` 里那个 `slideDuration` 原来是 **0.6 秒**，
而识别器给的是**每秒约 10 次**的累积文本（每 ~100ms 一次）。每一次新结果都用
`withAnimation(.linear(0.6))` 起一段新动画，100ms 后下一条就把它打断 ——
**每一小段只走完约 1/6 的距离，目标又往前跑了**：字永远在追、永远追不上，
屏幕上就是"又卡又滞后"。

**修法：`slideDuration = 0.1`** —— 一段动画刚好在下一条结果到达时结束，位移连成一条匀速的线。
⚠️ **这个数不是调出来的感觉值，它等于识别结果的间隔**（10 次/秒）：换识别服务、改推送频率时，
这个数必须跟着改，否则卡顿会原样回来。

**第二处结构性开销**：那一行字幕与黑带（两翼的渐变、描边、中段形状）原来在**同一个 body** 里，
于是每来一个字都要把整条带子重画一遍。现在带子是一个独立类型 `NotchRestingBand`，
输入全是稳定量（相位、几何、角落开关）—— SwiftUI 会跳过它，每个字只重画那一行文字。
（它的内容是从 `git show HEAD:Wanna/NotchActivityView.swift` 整块搬过来的，逐像素不变，
只把 `panelModel.activityPhase` 换成参数、`geometry.size` 换成 `container*`。）

## 二、多列布局 + 宽度放宽

- **列数 = 显示的格数**（最多 5 列）：`LazyVGrid`，每列 190pt —— 用户：「可以到 2 到 3 列」
  「最多不要超过 5 列」。
- **宽度不再固定 340**：`cardWidth(forColumnCount:)` = 列数 × 190 + 两边内边距 ——
  用户：「现在取消这个限制，它可以很宽，但是**左下角的位置必须固定**」（左下角固定由面板那一侧
  保证：原点 = 鼠标 +12pt，往右上长）。
- **标签 3~7 字**：写进提示词（软要求）；解析层的硬上限仍是 **12**，因为要容得下他自己的预设短语
  （「保存到 Notion」10 字、「派个 Agent 去做」11 字）—— 按 7 截会把它们静默截断。
- 每格里那 38pt 的类别名去掉了（列宽 190 放不下），编号 + 文字已经够认出是哪一格。

## 三、口述取消某个方向

`spokenCancelSelectionNumber(in:displayedItemCount:)`：句子里带**取消词**（取消 / 去掉 / 删掉 /
不要 / 不对 / 不算）**且**带编号 → 那一格变回"没选"。与"选中"共用同一套数字识别，只多一个取消词门槛。
探针 9 条钉住边界：四种说法都认、「第一个方向**正确**」不算取消（仍走选中）、光说「取消」不认、
越界编号忽略。

**这一版的验证**：纯逻辑探针 **127 条全过**；离屏渲染验了多列版面（三格一行、594pt、暗红三列在底）。
⚠️ **字幕顺不顺只能由用户说了算** —— 我在这台机器上量不动（没有可用语音输入；试过让自检按 12 字/秒
喂假文本再 `sample`，但那条路要先把相位钉在 Listening 才画得出那一行，自检实例在这台机器上又时起时不起）。
所以这一版的依据是**读代码找到的两个确定性原因**，不是采样。

>    第二来源：**用户口述**的任务方向也要能显示。第三来源：**每天中午 12 点**由复盘扫历史对话，
>    提炼高频任务/工具类型，**追加**进那个文件（标注日期、去重、只改这一个文件）。
> 6. AI 那段理解也一样，只发「方向清单 + 用户的话」；
> 7. 设置页要有这一整套的设置；
> 8. 方向选择**不要用大模型**（太贵），用 **Jev** 决策模型 —— 它专门做判断，给**概率**，
>    把高概率的显示出来。

## 一、字幕卡顿：**这次是量出来的**

前面两版都是凭推理改时长（0.6 → 0.1 → 自适应），第二版还把录音那条一起带坏了（用户当场报）。
这一版先把**测量**打通：自检加一档 `WANNA_DIRECTION_BOARD_SELFCHECK=stream` —— 按 **12 字/秒**
喂假文本（真人识别的速率），只喂字幕；相位**延迟一秒**再钉到 Listening（第一次直接钉是 nil，
`notchWindowController` 还没建好 —— 采样扑空就是这么来的）。然后 `sample`：

```
SmoothRevealedTranscriptText.body.getter        44 个样本
  └ static SmoothRevealedTranscriptText.width(of:) 40 个 ← 91% 在这里
```

**根因：每一帧都拿整串（最多 160 字）去问 `NSString.size(withAttributes:)` 有多宽**，
而识别结果每秒来约 10 次、每次 body 求值算两遍。

**修法：增量量化**（`TextWidthCache`）—— 识别器给的是**累积**文本，新串 = 旧串 + 新增的几个字，
宽度也就是「上次的宽度 + 新增那几个字的宽度」（汉字 advance 恒定，本仓实测 14.883268pt，加法成立）。
串不是"旧串 + 新字"时（换句、被修剪）**老老实实整串重量**，缓存绝不猜。

**修后同一个采样**（20 秒，样本数是修前的 2.5 倍）：

| | 修前（8s） | 修后（20s） | 归一化比 |
|---|---|---|---|
| `body.getter` | 44 | 18 | **≈ 6× 少** |
| `width(of:)` | 40 | 13 | **≈ 8× 少** |
| `NotchRestingBand`（黑带） | — | **0** | 完全不跟着每个字重画 ✓ |

外加**黑带摘成独立类型** `NotchRestingBand`（输入全是稳定量 → SwiftUI 直接跳过它），
于是每个字只重画那一行文字。

## 二、方向落成一个文件（`TaskDirectionStore`）

`~/Library/Application Support/Wanna/TaskDirections.json`（0600，仓库外 —— 与其它几个 store 同形）。

一条方向 = **一个关键词 + 一句描述**（+ 可选的同义说法 `matchKeywords`）。三种来源：

| 来源 | 怎么进来 |
|---|---|
| `builtin` | 出厂 12 条 —— **我读主 Agent 的基础段 + 图形/执行两个技能段 + 所有动作标签提炼的**，只写它真的会做的事 |

## 三、判断交给 Jev 决策模型（`JevDecisionClient`）

**实测过的协议**（不是照文档猜的）：`POST https://openrouter.ai/api/alpha/decisions`、
`~typesafe/jev-latest`、OpenRouter 的 key、**一个请求问多题按"次"计费**。
三个原语的 `criteria` 形状**各不相同**，写错就是 400 `invalid_union`：
`choice` 用对象、`score` 用字符串数组、**`noul` 的键必须字面量是 `"true"`/`"false"`**（第一次就踩这个坑）。
`noul` 只回**一个数** P(true) —— 阈值自己定。

用法：**每条方向一道 `noul` 题**，`state` 只有「用户到目前为止说的话」；
回来看 P(是) ≥ 阈值（默认 0.5，设置页可调 0.3~0.9）就显示那一格，按概率从高到低。

# 第七版（2026-09-27 深夜）：临时类型单独一个文件 + **口述类型改成"屏幕 + 你的话"**

用户的原话：

> 预设类型一共三个类型。第一个类型是本地文件，第二个类型是复盘之后写入本地文件，第三类是用户在
> 输入时**临时的口述类型**……我觉得应该在保存预设类型的文件里，在**文件的同级目录创建一个叫"临时类型"
> 的文件**。一个是固定类型的文件，一个是临时类型的文件。把用户口述类型里提取出来的这些内容保存到
> 临时文件里。发送给这个模型的时候，**把这两个文件拼接在一起发送**，这样方式会更简单一点。
> 临时文件在**每一轮对话结束时清掉**。是每一**大**轮，就是一整个大轮，中间可能有打断、有些东西，
> 这算一个轮，不算两轮，算一轮，然后自动清掉。
> 预设类型要再**调整一个来源**：把口述类型现在"分析用户提示词"，调整为**用户的提示词加上桌面截图**。
> 用户每一次说「参考桌面」「参考图片」「请看图片」「根据图片」，或者「根据屏幕」，就是**屏幕或图片加
> 参考或根据**这样的组合词时，**每一次转写识别到就截一次屏**。这样口述类型就变成了屏幕加上用户的
> 口述，然后总结出来的类型。
> ……比如屏幕上有一道数学题，有 A、B、C、D 四个选项，用户说「参考屏幕内容，分析一下这道题可能选哪一个」
> ……**这个结果对应的预设类型就一个**，因为结果是固定的，比如这道题应该选 A，那结果就是固定的。
> ……也就是说在用户提示词发送之前，就能**提前知道这个问题的答案**，没有必要按发送了。

## 一、两个文件（固定 + 临时）

```
~/Library/Application Support/Wanna/
  TaskDirections.json            ← 固定：出厂 12 条 + 每天中午复盘追加
  TaskDirectionsTemporary.json   ← 临时：这一大轮里用户口述出来的类型 + 带屏幕参考时模型算出来的结果
```

- **发送时两份拼接**（`allDirections()` = 固定 + 临时）—— 用户说的"更简单一点"；
- 临时那份**不种子**（空的就该是空的）；固定那份第一次读时才写出厂那份；
- **清空的时机 = 一大轮结束**：新的一大轮开始（`cycleID` 变了）清一次 + 追问窗口关闭时清一次。
  中间无论打断几次、续说几句，都算同一个大轮 ✓（这正是用户强调的那句"不算两轮，算一轮"）；
- 设置页把两份**分开显示**（各自条数），临时那份给一颗「立刻清空」。

## 二、口述类型 = 屏幕 + 你的话

- **触发**：转写里出现「参考/根据/请看/看一下 + 屏幕/图片/桌面/截图/画面」的**相邻组合词**
  （`screenReferenceRequested`）→ **当场截一张屏**。相邻判定是刻意的：只要求"句子里同时出现这两个词"
  会把「我的屏幕上没有这个图片」也算成一次截屏。边缘触发（同一次提到只截一张，与
  `BuddyScreenKeywordDetector` 同一个做法）。
- **那一次请求带上截图**（`analyzeImageStreaming(images:)` 本来就吃图）+ 追加一条要求：
  「另外给一行 `类型：<≤7 字>`」+「这一次带了屏幕截图，请**看图**再回答，并直接给出你的判断/答案」。
- **模型给的那个标签变成一条临时类型**（进临时文件 + 这一轮强制显示）——
  用户那个数学题的例子：「这道题应该选 A，那结果就是固定的」，那个答案本身就是能点选的选项 ✓。
  于是**发送之前**他就看到"AI 会怎么处理 + 结果大概是什么" ✓（用户要的正是这个）。
