## 一、先证明它死了，再删（这一条比删除本身值钱）

用户说「删除」时，我手上**没有**任何证据说那些代码没在跑。差一点就凭「应该没在跑吧」动手。

**改之前先装的是判据，不是刀。** 三条独立证据，全部来自 `~/Library/Application Support/Wanna/主Agent诊断.log`：

| 打点 | 位置 | 实况 |
|---|---|---|
| `🧩 解析：动作 N 个…` | 解析那一行的正下方 | **0 次** |
| `📥 回复收完 N 字` | Python 返回之后第一行 | **0 次** |
| `[CLICK:` `[POINT:` `[TYPE:` `[SKILL:` `[WAIT:` | 整个日志 | **各 0 次** |

而同一份日志里 `⏱️ 环节：开始截屏` 422 次、`出声` 211 次 —— **日志是活的，只是那几行从不执行**。

### 差点被"反证"带偏的一次

先看到的是 `⏱️ 环节：截屏完成` 也是 0 次，而它和 `开始截屏`（422 次）**只隔 8 行**。
当时的第一反应是「日志坏了」。**没有下这个结论是对的** ——
`开始截屏` 在跑就证明日志没坏，那么 `截屏完成` 的 0 只有一个解释：它在某个条件分支里，而那个条件不成立。

**判据：一个打点是 0 时，先找它旁边那个非 0 的打点。** 旁边有活的，日志就是活的，
0 就是真的 0；旁边全死，才该怀疑日志。

### 为什么它们会死

决策搬去了 Python（`PythonAgentRunner`），它动手走的是 MCP 工具（`WannaMCPTools`），
回复里**不带标签** —— 于是 Swift 这边那一整套「解析标签 → 执行动作 → 再截一张图 → 继续」
永远拿到空的 `parseResult`，循环第一轮就 `break`。

### ⚠️ 我在这两步都删多了东西，是**编译器**抓回来的

- 第 1 步：把新代码插到了枚举**闭合括号之后**（我先删了 4 段、再按旧行号算插入点，
  索引已经漂了）→ `static properties may only be declared on a type`。
- 第 3 步：按行区间删 `5506–5750`，**连带 `PointingParseResult` 和
  `screenshotPixelCoordinate` 一起删了** —— 它们正好落在那个区间里。
  → `cannot find type 'PointingParseResult'` / `no member 'screenshotPixelCoordinate'`。

**教训（是 D55 的续集，不是同一条）**：D55 的教训是"边界别猜"；
这一条是 —— **按行区间删除时，先列出区间里所有顶层声明，不只确认两个端点。**
我当时只 `assert` 了区间的首行和末行，中间夹着两个要留的函数，`assert` 全过。

**兜底是编译**：两次都是 `xcrun swiftc -typecheck` 一条命令就点出来了。
所以删完**立刻**typecheck，不要等攒几处再一起编。

## 三、留下 `[POINT:]` 的理由（不是"以防万一"）

§0.8 说别为低频问题提前防范。这里反过来成立：**它不是低频，是另一个活的调用者。**

`CompanionManager.parsePointingCoordinates` 唯一的调用点是**开机引导**那段
「光标飞过去指个东西」，它走的是**旧的视觉模型**（`onboardingDemoSystemPrompt`）——
模型真的会写 `[POINT:…]`。删了它，新装用户首次运行就看不到那段演示。

**判据是"谁还在调它"，不是"这个功能我还需要吗"。** 后者是主观的，前者一条 `grep` 就有答案。
