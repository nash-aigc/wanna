## 2. ⚠️ 冲突：第 1 条（按下就启动）与实测对不上 ✗

**你要的**：按下快捷键 → 立刻启动引擎（在你说第一句话之前就热好）。

**实测（2026-09-27，真机）**：**在录音进行中启动那台共享引擎，会把正在录音那条引擎的采集掐停**，
录到 **1204 毫秒的缝** —— 用户正在说的第一个字**整段丢掉** ✗。
根因：引擎启动要打开 VPIO（系统级回声消除），它**重配整个输入设备**，
另一条正在采集的 tap 会随之被掐停 ✗。

**所以现在的位置是**：录音期间**不碰**那台引擎；等录音结束（提交那一刻）再把它拉起来。
代价是"第一声要多等约 1 秒"（VPIO 现拉）；好处是**你的话一个字都不丢** ✓。

### ⚠️ 2026-09-28 更新：你选了 B（按下就启动），**我实现了、然后实测发现代价比说好的大得多，已撤回**

**A/B 实测（同一台机器、同一天、同一段流程，只差那一句代码）：**

| | 按下 → 松手这一段的音频 |
|---|---|
| **加了"按下就启动"** ✗ | 识别服务端报 `45000081 [Timeout waiting next packet] … 8.000000 seconds` ✗ —— **8 秒一个音频包都没收到**；自动重连两次，还是没包 ✗ |
| **撤掉之后**（现状）✓ | `🎤 音频：21~22 块/2.1s` **一直稳定** ✓，一次"连接出问题"都没有 ✓ |

**所以它不是"开头 1.2 秒被吞"** ✗ —— 是**引擎一起来，录音那条通路就断死、而且不会自己回来** ✗。
你答应的代价（"开头丢了，我重说一遍"）覆盖不了这个 ✗：**整句都可能认不出来** ✗。
**"快"不能用"你说的话识别不出来"去换** —— 所以我把它撤了，回到"提交那一刻才预热"。

**⭐ 2026-09-28 定案（用户的设计，已实现）**：**引擎先起、起来之后再开麦** ——
那一刻我们还**没有占用麦克风** ✓，所以引擎重配输入设备**伤不到任何东西** ✓，
而"说过话 → 提交"时引擎早就热好 ✓。代价（他明确接受）：「我可以去在前面等都可以，
甚至说我第一句话没读上都可以。」实测：冷启动 **1.49~1.59 秒**预热 + 一声轻响表示"可以说话了" ✓；
引擎已热时**一秒不等** ✓。诊断日志里每轮都有 `🎙️ 开麦：引擎预热耗时 N 秒` 一行 ✓。

**（下面这条 A′ 是被它取代的更早方案）**：按下时照常启动引擎 ✓，**引擎起来之后把录音的 tap 重新装一次** ✓——
那么代价就回到你愿意接受的那一条（**只有那一两秒的缝** ✓），而"AI 快速回复"照样拿到 ✓。
它是对**音频采集路径**的改动，按这个仓库的规矩要先跑采集探针、改完必须真机验，
所以我不擅自动手 ✗。

## 5. 核实结果（读代码得到的事实，不是猜）

`noteVoiceActivity()` 现在**只在这三处**被调用（`CompanionManager.swift`）：

| 调用点 | 行 | 什么时候 |
|---|---|---|
| 快捷键 `case .pressed:` | 2209 | **每次按下快捷键** ✓ |
| 听写观察里 `isRecording` 变真 | 1872 | **开始录音** ✓ |
| 语音聊天注入的 `warmUpVoiceEngine` / 会话活动 | 382 / 334 | 进语音聊天、会话活动 ✓ |

**所以你要的"循环计时"只实现了一半** ✗：

| 事件 | 现在会不会重新计时 |
|---|---|
| 按下快捷键 | **会** ✓ |
| 开始录音 | **会** ✓ |
| 语音聊天里的活动 | **会** ✓ |
| **AI 播完 → 进入追问窗口** | **不会** ✗ |
| **会话结束（ESC / 提交之后这一大轮结束）** | **不会** ✗ |

也就是说：你在追问窗口里待着（最多 30 秒）的时候，计时器**可能已经到期** ✗ ——
它会不会真的把引擎放掉，取决于 `noteVoiceActivity` 尾部那段"任何一通语音会话在跑就不许释放"的守卫
（那一条是为语音聊天写的 ✓，**不覆盖主 Agent 的追问窗口** ✗）。**这一条要补** ✓。

`【待你确认】` 补法（我倾向照你说的做）：**播完进窗口** 与 **会话结束** 两处各加一次
`noteVoiceActivity()` ✓ —— 也就是"只要还在跟你交互，就一直是热的，每一拍重新数 3 分钟" ✓。
