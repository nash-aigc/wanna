## 1. 你说的（原话要点，已落字）

1. **按下快捷键就启动引擎** —— 「不用管用户有没有说话。因为按下快捷键的话，相当于就是用户就在使用

2. **保持时间是"循环"的，不是一次性的** —— 「不是说从一开始、最开始按下快捷键的时候要保持这么长时间，
   那用户如果一直说话说了 10 分钟，那你保持 3 分钟其实就不对……AI 播放完了，那这时候引擎其实还是
   运行的状态，并且**进入重新计时**。」

   压力不是特别大。」
4. **要让用户看得见** —— 「在刘海左侧显示一个按钮/标签/倒计时，让用户能看到引擎是不是在热着、

5. **「释放引擎」快捷键很好，保留** —— 正常情况下让它尽量久地保持热；真想立刻放掉时用快捷键。

## 2. ⚠️ 冲突：第 1 条（按下就启动）与实测对不上 ✗

**你要的**：按下快捷键 → 立刻启动引擎（在你说第一句话之前就热好）。

**实测（2026-09-27，真机）**：**在录音进行中启动那台共享引擎，会把正在录音那条引擎的采集掐停**，
录到 **1204 毫秒的缝** —— 用户正在说的第一个字**整段丢掉** ✗。
根因：引擎启动要打开 VPIO（系统级回声消除），它**重配整个输入设备**，
另一条正在采集的 tap 会随之被掐停 ✗。

**所以现在的位置是**：录音期间**不碰**那台引擎；等录音结束（提交那一刻）再把它拉起来。
代价是"第一声要多等约 1 秒"（VPIO 现拉）；好处是**你的话一个字都不丢** ✓。

| 选项 | 得到 | 失去 |
|---|---|---|
| **A（现状）** | 你说的话一个字不丢 ✓ | 会话里**第一声**要多等约 1 秒 ✗ |
| **B（你要的）** | 第一声更快 ✓ | **每次按键后的头 1.2 秒可能会被吞掉** ✗（实测过） |
| **C（第三条路）** | —— | 需要一次真正的改造：让录音本身就走那台引擎（代价是**实时字幕要等约 2 秒才出字** ✗，那是你 2026-09-27 刚抱怨过并修掉的问题 ✗） |

`【可能矛盾】` **我倾向 A**（丢字比慢一秒严重得多），但这是你的取舍，你说了我才改 ✓。

## 5. 核实结果（读代码得到的事实，不是猜）

`noteVoiceActivity()` 现在**只在这三处**被调用（`CompanionManager.swift`）：

| 调用点 | 行 | 什么时候 |
|---|---|---|
| 快捷键 `case .pressed:` | 2209 | **每次按下快捷键** ✓ |
| 听写观察里 `isRecording` 变真 | 1872 | **开始录音** ✓ |
| 语音聊天注入的 `warmUpVoiceEngine` / 会话活动 | 382 / 334 | 进语音聊天、会话活动 ✓ |

**所以你要的"循环计时"只实现了一半** ✗：

| 事件 | 现在会不会重新计时 |
|---|---|
| 按下快捷键 | **会** ✓ |
| 开始录音 | **会** ✓ |
| 语音聊天里的活动 | **会** ✓ |
| **AI 播完 → 进入追问窗口** | **不会** ✗ |
| **会话结束（ESC / 提交之后这一大轮结束）** | **不会** ✗ |

也就是说：你在追问窗口里待着（最多 30 秒）的时候，计时器**可能已经到期** ✗ ——
它会不会真的把引擎放掉，取决于 `noteVoiceActivity` 尾部那段"任何一通语音会话在跑就不许释放"的守卫
（那一条是为语音聊天写的 ✓，**不覆盖主 Agent 的追问窗口** ✗）。**这一条要补** ✓。

`【待你确认】` 补法（我倾向照你说的做）：**播完进窗口** 与 **会话结束** 两处各加一次
`noteVoiceActivity()` ✓ —— 也就是"只要还在跟你交互，就一直是热的，每一拍重新数 3 分钟" ✓。
