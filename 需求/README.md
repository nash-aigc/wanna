# 需求/

**这个目录回答"这个软件应该是什么样"，`开发经验/` 回答"我们踩过什么坑"。**

两者的分工不能混：
- `开发经验/` 是**事后**的（某个问题怎么修的、量到什么数字）；
- `需求/` 是**事前**的（用户要什么、屏幕上该显示什么、按下什么该发生什么）。

**为什么要分开**：过去所有东西都只能从 `开发经验/` 里反推"应该是什么样" ✗ ——
而那份东西是**按问题编号**组织的（D39、9.55……），它回答不了"整体应该是什么" ✗。
后果是**代码逻辑变成事实上的需求**：AI 改一处代码、测试按代码的逻辑判绿 ✗，
而用户真正要的那件事可能已经被改掉了 ✗。

## 四份文件

| 文件 | 层 | 谁定稿 | 内容 |
|---|---|---|---|
| `00-词汇表与总览.md` | 第 1 层 | **你**（我只填读法） | 每个词指什么；一句话总览；**不做什么** |
| `01-交互契约.md` | 第 1 层 | 你（我填证据） | 按下什么 → **应该**发生什么；判据与时间预算 |
| `02-界面契约.md` | 第 1 层 | 你（我填证据） | 哪个位置显示什么 |
| `90-实现映射.md` | 第 2 层 | 我（你抽查） | 每条需求 → 代码落点 → **怎么验** → 状态 |

## 三条规矩

1. **标 `【待你确认】` 的一律不许我替你填。** 那是"用户需求"，只有你有资格定。
2. **改需求与改实现映射必须同一次提交**（分开必漂）。
3. **`90` 的 C 节是"悬空清单"** —— 代码在、需求没落实的东西挂在那里。发现就写，
   当场不决定也要先写：这一栏就是"AI 把需求删掉了"唯一会现形的地方。
