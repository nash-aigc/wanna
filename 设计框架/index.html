01 · 先回答时机问题

现在整理，还是等改项目时再整理？

这两个选项差别很大 —— 因为「整理」在本项目里其实是两件不同风险的事， 必须拆开决定，不能一句「现在/以后」说完。

现在做 文档结构 · 路径错误 · gitignore

已经在造成损失：reference/orca 这个路径指向不存在的地方， 13 处引用指空（5 处直接显示给用户看）；29 MB 日志和 1967 个第三方文件误入库； 根目录散着 5 个无主文件。你现在正处在设计原始稿阶段， 结构定型的成本是最低的 —— 越晚，被引用固化得越多。

等改项目时做 运行时目录归堆

Wanna录音/ Wanna图形/ Wanna复盘/ WannaAgents/ —— 它们看起来像临时文件，你想归到一处是对的， 但路径散写在多个 Swift 文件里（如 RecordingLibrary.swift:88 「checkout 里的 Wanna录音/」）。挪 = 改代码 + 迁移用户数据。这是改项目本身， 不该混进整理文档这一轮。

结论：现在就把「不碰代码」的那部分做掉，碰代码的列清单让你拍板。 理由是你说的那句 —— 「防止未来修改时找不到位置、改错路径」：这一轮已经抓到 13 处指空的路径， 说明这类错误不是理论风险，是正在发生。

03 · 设计框架

四层对照链 —— 每层点开看「在哪、缺什么」

这是本项目的设计思路本体。四层各回答一个问题，不能互相替代。 点任意一层展开细节。

1
需求 —— 你要什么你的原话 + 判据，契约级，只读
✅ 完整
在哪：需求/00-词汇表、01~06 契约、07 项目工作区。 其中 00-交互标准（锁死·只读） 是最高优先级 —— 与任何新需求冲突时以它为准。
它回答：用户要什么、什么算做对了。不回答怎么实现。
2
原型 —— 长什么样、点哪出什么HTML 三件套，验证交互，不是产品
✅ 有
在哪：index.html + app.js（约 4900 行）+ app.css（仓库根）。
它回答：交互与信息架构。
它不回答：具体参数、数据结构、边界条件、算法 —— 这些必须回源码取。
⚠ 别覆盖根目录 index.html —— 它就是原型的入口。
3
源码依据 —— 具体怎么实现别人的参数 / 字段 / 算法 / 调用顺序
⚠ 路径刚修
在哪：Clone_From/Orca/（402 MB）、reference/pi/。
原型里写了吗？写了 —— app.js 的注释精确到 文件:行号， 例如「视口预设照 Clone_From/Orca/src/shared/browser-viewport-presets.ts:13-68」。 需求里也写了：每节开头的出处行。
刚修的 bug：这 13 处原来写的是 reference/orca —— 那份已不存在，照注释找源码会扑空，其中 5 处是直接显示给用户的 toast 文案。 2026-10-01 已全部改为 Clone_From/Orca。
硬规矩：还原功能时，原型确认交互，实现细节一律回源码 —— 冲突时以源码为准。

✅ 在跑

怎么分工：碰 macOS 的必须 Swift；现成的纯逻辑保留原语言跑子进程； 只有数据格式（JSON）要统一 —— 详见 架构说明。

04 · 原型更新怎么同步

原型改了，怎么追到 Swift？

这一环之前没有 —— 03 节那条链是单向的（需求 → 原型 → 落地）， 缺反向那一半。你问「不一定要实时，但改得特别大或有颠覆性创新时要转过来」—— 机制在 02-原型同步.md，这里是摘要。

核心判据：三分法。点下面三类里的一类，看怎么处置 —— 不是所有改动都要同步：

怎么发现原型变了 —— 用现成的 git，不新增任何东西：

git log --oneline -20 -- index.html app.js app.css   # 原型变更史，每条带 §NN

§NN 是贯穿三层的钥匙 —— 这是反查的入口， 三层用的是同一个编号：

app.js 注释§23.4我改的这处属于哪一批
↓
需求/07 §23.4你的原话 + 判据验收标准在这，别只看代码
↓
需求/90 的 23.4.x 行怎么验 + 状态这一栏就是 Swift 侧的验收用例
↓ 判据是交互 → 必须同步
Wanna/*.swift改这里先读 全局框架/NN-*.md，再 grep 功能名兜底

欠账表 —— 「不要求实时」的代价是允许欠账， 但欠账必须登记，否则三个月后没人记得 Swift 落后了多少。只记交互级的：

§NN原型改了什么该改的 Swift 落点提交于同步状态
— （当前为空 —— 截至 2026-10-01，原型改动都还停留在 HTML 侧，未进 Swift）
已知边界：这张表没有闸门

它靠第 ④ 步的自觉。真要硬化，可以像仓库里其它闸门那样 挂进 scripts/git-hooks/pre-commit（「改原型的提交必须回答要不要同步」）—— 但按 §0.8 极简：非高频问题不提前防范，等它真的失守过一次再做。

07 · 硬规矩

三条，加新东西之前过一遍

① 根目录不放散装文件 新东西先问「属于哪一类」（见 02 的五类），不属于就先想清楚职责再建目录。 本批已把 5 个无主截图/OCR 文件收进 .cache/。
② git add -A 前先看 git status 更要紧的是：新加 ignore 规则后跑一次 git ls-files 目录名 | wc -l —— 非 0 就是「以为挡住了、其实在仓库里」。 ①②两个问题就是这么来的。
③ 移动目录前先搜引用 grep -rn "目录名" --include="*.swift" --include="*.js" --include="*.md" —— 注释里的引用也算，那是「按图索骥」的线。本批修的 13 处指空就是没搜的后果。
