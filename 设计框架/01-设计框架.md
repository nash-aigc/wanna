# 01 · 设计框架 —— 从需求到落地，四层对照链

> 回答这几件事：**设计思路是什么**、**原型从哪来**、**该参考哪份源码**、
> **原型和落地之间有没有对照**。以及一条硬规矩：**还原功能时以源码为准，不以原型为准**。

---

## 一、四层，各管一件事

```
第 1 层  需求        用户的原话 + 判据              需求/NN-*.md（契约，只读）
   ↓     我把它翻译成可点的东西
第 2 层  原型        HTML 三件套，验证交互            index.html / app.js / app.css
   ↓     照着第三方源码做，不照截图猜
第 3 层  源码依据    别人的实现细节（参数/结构/算法）  Clone_From/Orca、reference/pi
   ↓     两边对齐后落到真产品
第 4 层  落地        Swift 真实现                    Wanna/*.swift
```

**关键区分 —— 每层回答的问题不一样，不能互相替代**：

| 层 | 它回答 | 它**不**回答 |
|---|---|---|
| 需求 | 用户要什么、什么算做对了 | 具体怎么实现 |
| **原型** | **长什么样、点哪里出什么、状态怎么流转** | 具体参数、数据结构、边界条件、算法 |
| **源码** | **具体参数、字段名、算法、边界、调用顺序** | 用户要什么 |
| 落地 | 在 macOS 上怎么真跑起来 | 交互该长什么样 |

**所以你说的那条原则是对的，而且必须写成规矩**：

> **还原功能时，原型只用来确认「交互和信息架构」，实现细节一律回源码取。
> 两者冲突时，以源码为准。**

理由：原型是我为了验证需求做的**简化**——我可能省掉细节、可能猜错参数、
可能为了让 demo 跑通而抄近路。源码是被真实使用过的实现。原型里看到一个按钮，
不代表我知道它点了之后到底发了什么请求、超时多少、失败怎么退。

## 三、原型里到底写没写「参考了哪份源码」？—— 写了，精确到行

你问「原型里有没有写」：**写了，而且是行号级的**。在 `app.js` 里搜 `Clone_From/Orca`
就是全部出处，例如：

```js
// §22.14 浏览器页 —— 形状照 Clone_From/Orca …/shared/browser-workspace-types.ts:174-180
const BROWSER_VIEWPORT_PRESETS = [ … ];   // 视口预设照 …/browser-viewport-presets.ts:13-68
/// §23.3.4 色板**逐字照 Orca**：…/tab-bar/SortableTabContextMenu.tsx:27-88
```

同样，**需求里也写了**：`需求/07` 每一节开头基本都有「取自 `Clone_From/Orca/…`」的出处行。

⚠️ **这些路径刚修过**：原来写的是 `reference/orca`，那份已经搬走，全仓库 13 处
（需求/07 三处、需求/90 三处、`app.js` 八处，其中 5 处是**给用户看的 toast 文案**）
已于 2026-10-01 统一改成 `Clone_From/Orca`。**以后照注释找源码能找到了。**

**怎么用**：拿到一个功能，先去 `app.js` 搜功能名，注释里会直接告诉你
「照的哪个项目的哪个文件第几行」——**从注释反查源码，比从截图猜快得多**。

## 五、一批需求是怎么走完的（现行流程）

这是仓库里**已经在跑**的流程，`需求/90` 的状态列就是它的检查表：

```
① 你给原话
      ↓  我原样写进 需求/07 §NN（判据表，不许改写你的措辞）
② 照判据改原型（index.html / app.js / app.css）
      ↓  实现细节回 Clone_From/Orca 取，在 app.js 注释里写明 文件:行号
③ Playwright 逐条实测（读数字，不许说「应该好了」）
      ↓
④ 同一次提交里：需求/07 + 需求/90 + 代码 三者一起提交
      ↓  ★ 提交前先分个类：这次改动 **要不要同步到 Swift**？
      ↓    样式 → 不用；交互 → 要（没跟就记进 02 的欠账表）；结构 → 回①改判据
      ↓  分支 → 验证 → --ff-only 合回 main → push
⑤ 踩到坑写进 开发经验/10-踩过的坑.md；量到的数字进 09-实测数据.md
      ↓  改了系统现状就同步 全局框架/
```

**④ 是最不能省的一步**：需求、映射表、代码分开提交必然漂 —— 这个仓库已经吃过。
**④ 里那个 ★ 是 2026-10-01 补的**：它同时是「原型变了要不要追到 Swift」的入口，
判据与欠账登记见 [`02-原型同步.md`](02-原型同步.md)。

## 六、目前唯一缺的一环（要你拍板）

**「原型 → Swift 落地」没有对照表。**

- `需求/90-实现映射.md` 是 **需求 → 原型代码落点**（左列是你的原话）
- 但从**原型的某个页面/某个组件**，反查「Swift 侧该落在哪个文件」——这一步没有

后果是：将来要「把原型还原成 Swift 功能」时，得先从 90 的需求行反推原型代码，
再想 Swift 怎么实现，**多一跳，而且原型代码（app.js 4900 行）不是按 Swift 的
模块边界组织的**，对不上。

**三个选项（我不替你定）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A** | 在 `需求/90` 每行加一栏「Swift 落点」，现状先留空 | 改现有表结构；没做的行天然显示为「待落地」 |
| **B** | 新建 `需求/91-落地映射.md`：原型组件 → `Wanna/*.swift` | 多一份文档要同步维护 |
| **C** | 不建，等真开始落地时逐条补 | 现在最省事；风险是落地时找不到对应关系，重蹈「路径指空」的坑 |

我倾向 **A**（一张表胜过两张表，`90` 本来就是那张对照表），但这是长期维护负担，
由你定。定下来我再动手。

> ⚠️ 别把这一节和 [`02-原型同步.md`](02-原型同步.md) 混了：**这一节问的是
> 「有没有一张逐行的落点表」（静态对照），02 问的是「原型变了怎么追到 Swift」（动态同步）**。
> 02 现在不依赖这张表 —— 它靠 `§NN` 三层反查就能跑；但有了表，02 第三节第 4 步会更快。
