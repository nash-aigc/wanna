# 02 · 原型更新怎么同步到 Swift

> 回答你 2026-10-01 的问题：**「原型更新了，我该怎么同步到当前组件的某个功能？
> 不一定要实时同步，但如果原型改得特别大、或出现颠覆性创新，就需要把它转过来。
> 这个方案里有没有？」**
>
> **答：之前没有。** `01-设计框架.md` 写的是**单向**的四层链（需求 → 原型 → 落地），
> 缺反向那一半。这一份补上它，含判据、流程和一张欠账表。

---

## 一、先分类 —— 不是所有原型改动都值得同步

这是整套机制的核心判据。**改动分三级，只有中间那级需要"同步"，上面那级根本不用管，
下面那级不叫同步、叫重做**：

| 原型改了什么 | 要不要动 Swift | 为什么 |
|---|---|---|
| **样式**：颜色、字号、间距、圆角、文案措辞 | ❌ **不同步** | Swift 有自己的设计令牌，跟着 `需求/02-界面契约.md` 走。原型的样式是给我自己调效果用的，不是规格 |
| **交互**：点哪里出什么、状态怎么流转、快捷键语义、**新增/删除一个面板或菜单分组** | ✅ **必须同步** | `需求/90` 的「怎么验」那栏写的全是交互判据 —— 不同步，Swift 侧就跟需求脱钩了 |
| **结构**：信息架构重排、布局骨架换掉、一整块功能重来 | ⬆️ **先回需求层** | 这就是你说的「颠覆性创新」。它可能**推翻已有的需求条目**，直接改 Swift 会做出「原型想要、但需求没定」的东西 |

**「颠覆性创新」为什么不走同步**：同步的前提是「需求没变，只是实现要跟上」。
颠覆性的东西连「什么算做对了」都变了，所以必须回到 `需求/07` 先改判据，
再正向走一遍 `01-设计框架.md` 的四层链。**硬要走同步，就会出现需求文档和实际行为分叉**。

**一句话记法**：**样式不动，交互必动，结构回上游。**

---

## 二、怎么知道原型变了 —— 用现成的 git，不新增机制

```bash
# 原型三件套的变更史（每条都带 §NN）
git log --oneline -20 -- index.html app.js app.css

# 某一批到底改了原型的哪些行
git show <commit> --stat -- index.html app.js app.css
```

**这个仓库已经有的两个习惯，正好是天然的变更登记**：

1. 每批提交信息都带 **`§NN`**（如「需求07 §23 第十四批」）—— 这就是批次号；
2. `app.js` 的行内注释带 **`§NN`**（如 `// §22.14 浏览器页…`）—— 这就是改动落在哪。

**所以不需要任何新工具**：`git log` 看变了什么，`§NN` 看属于哪一批，`需求/90` 查这一批的判据。

---

## 三、`§编号` 是贯穿三层的钥匙 —— 反查就靠它

这是现有体系里最好的设计，只是以前没人把它当成同步的入口：

```
app.js 里的注释 §23.4          ← 我改的这处，属于第 23 批第 4 条
      ↓ 拿这个编号去查
需求/07 §23.4                  ← 你的原话 + 判据（验收标准）
      ↓ 同一个编号
需求/90 的 23.4.x 行           ← 原型代码落点 + 怎么验 + 状态
      ↓ 判据是交互 → 必须同步
Wanna/*.swift                  ← 找对应子系统：全局框架/NN-*.md + grep 功能名
      ↓
改完跑 90 表「怎么验」那一栏    ← 用同一把尺子验收 Swift 侧
```

**具体操作**（原型改了一处，要同步到 Swift）：

1. `grep -n "§NN" app.js` —— 定位这批改动的注释，看它照抄了哪份源码；
2. 翻 `需求/07` 的 `§NN` 节 —— **读你的原话和判据**，别只看代码；
3. 翻 `需求/90` 的 `NN.*` 行 —— 拿到「怎么验」那一栏，**它就是 Swift 侧的验收用例**；
4. 找 Swift 落点：`全局框架/` 里对应的子系统文档（改某个子系统前必读那一份），
   再 `grep -rn "功能名" Wanna/` 兜底；
5. 改完**用第 3 步那栏验收** —— 同一把尺子，两侧都能量。

## 四、同步流程（四步，挂在现有流程的第 ④ 步上）

```
原型改了
  ↓
① git log 看这一批改了什么、属于哪个 §NN
  ↓
② 按第一节的三分法定级：样式 / 交互 / 结构
  ↓
③ 分三支
   样式 → 结束，什么都不做
   交互 → 按第三节反查 → 改 Swift → 跑 90 的「怎么验」 → 需求+90+代码 同批提交
   结构 → 回 需求/07 改判据 → 重新走正向四层链（01 第五节）
  ↓
④ 交互级但这次没同步 → 记进第五节的欠账表（不实时，但不能忘）
```

**第 ④ 步是"不要求实时"的代价**：不要求实时 = 允许欠账，但欠账必须登记，
否则三个月后没人记得欠什么，Swift 侧会静默地、长期地落后于需求。

## 六、这套机制的边界（别指望它做到的事）

| 它**能**做到 | 它**做不到** |
|---|---|
| 有明确的"要不要同步"判据，不靠感觉 | 实时自动同步（原型和 Swift 是两套实现，没有任何自动桥） |
| 反查路径固定（`§NN` 三层通用） | 覆盖"结构级"改动（那要回需求层，不是同步能解决的） |
| 欠账看得见（一张表） | 自动发现"Swift 落在哪个文件"—— 最后一跳仍要 `全局框架/` + `grep` |
| 用同一把尺子验收两侧（90 的「怎么验」） | 保证执行（表空着没人拦，靠第 ④ 步的自觉） |

**最后一条是最实际的风险**：欠账表没有闸门。如果它长期空着但 Swift 明明落后了，
说明第 ④ 步没被执行。真要硬化，可以像仓库里其它闸门那样挂进 `scripts/git-hooks/pre-commit` ——
**但那是「改原型的提交必须回答『要不要同步』」，成本不低，等它真的失守过一次再做**（§0.8 极简：非高频问题不提前防范）。
