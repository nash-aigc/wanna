# 04 · 模型接入

这个 App 要**三个模型**，分别叫三个「角色」。这一篇讲它们怎么被解析、请求打到哪个路径、以及踩过的那些**报错信息完全不指向真正原因**的坑。

涉及文件：`ModelConfiguration.swift`（纯数据与解析）、`ModelConfigurationStore.swift`（读写）、`BailianVisionChatAPI.swift`、`BailianTTSClient.swift`、`BailianRealtimeTranscriptionProvider.swift`、`ModelConnectionTester.swift`。

---

## 一、三个角色

| 角色 | 干什么 | 默认 |
|---|---|---|
| 👂 `transcription` | 语音转文字 | `qwen3-asr-flash-realtime`（websocket 流式） |
| 🧠 `vision` | 看截图、回答问题 | `qwen3-vl-plus` |
| 👄 `speech` | 把回答念出来 | `qwen-audio-3.1-tts-flash` + 克隆音色 |

每个角色可以指向**不同的服务商**，服务商各自有自己的 URL、Key、模型名。全部存在仓库外的 `ModelConfiguration.json`（0600）。

---

## 二、请求路径由「协议」决定，不由 URL 决定

**这是这一块最重要的一条设计。** 路径不写在客户端里，也不让用户填，而是由服务商的协议类型推导：

| 路由 | 协议 | 服务哪个角色 |
|---|---|---|
| `POST {base}/compatible-mode/v1/chat/completions` | Bailian | 🧠 |
| `POST {base}/api/v1/services/audio/tts/SpeechSynthesizer` | Bailian | 👄（返回一个 24 小时有效的 WAV URL） |
| `WSS {base}/api-ws/v1/realtime?model=…` | Bailian | 👂 |
| `POST {base}/chat/completions` | DeepSeek | **只有** 🧠——DeepSeek 没有 ASR 也没有 TTS |

唯一的真相来源是 `ProviderProfile.effectiveFlavor.requestPath(for:)`，三个客户端都去问它，不自己拼。

**为什么 DeepSeek 要单独一条**：它长得像 OpenAI，但 chat 路由**没有 `/v1` 前缀**。所以决定路径的是**协议**，不是 base URL 长什么样。

`ResolvedModelRole` 承载解析结果：`requestPath` 把协议带到路由上，`allowsVisionReasoning` 把「要不要关推理」带到请求体上。

**每个请求现读配置。** 三个客户端都在**即将发请求的那一刻**才去 `ModelConfigurationStore` 解析角色，而不是在初始化时把 URL/Key/模型名捕获下来。这是「在设置窗口保存之后立刻生效，不需要重建客户端」的原因。

两个刻意的后果：

- `BailianTTSClient.speakText` 在**开头快照一次**角色，然后所有分块都用它——否则一次回答可能前半句一个服务商的声音、后半句另一个。
- 转写会话拿到的是**值**（URL 和 Key），不是引用——否则一次「保存」落在录音中途，可能产出一个 host 和 model 对不上的 socket。

## 三、推理关掉了吗？——一次完整的实测过程

### 问题

改造前没有这个问题，因为它用 Claude。换成 `deepseek-flash` 之后，用户问一句「屏幕右上角有什么？」，要等 4.5 秒才听到声音。

### 实测（2026-09-21）

用**App 自己的真实载荷**测：1280×827 的 JPEG 截图 + 4923 字的系统提示词，问「屏幕右上角有什么？」。

`deepseek-flash` 在吐出回答的**第一个字之前**，先产生了 **664–868 个推理 token**：

| 阶段 | 耗时 |
|---|---|
| 思考 | 3.4 s |
| 上传 | 0.5 s |
| 回答 | 0.3 s |
| **合计** | **4.5 s** |

Wanna 问的是**感知问题、而且是念出来听的**。那 3.4 秒用户只能看着转圈，一个字都听不到。

### 怎么关

**不是随便试出来的，是量出来的。** 四个看起来都合理的开关，两个真的有用，两个完全没用：

| 字段 | 结果 |
|---|---|
| `thinking: {"type": "disabled"}` | ✅ 有用 |
| `reasoning_effort: "none"` | ✅ 有用 |
| `enable_thinking: false` | ❌ 仍然产生 629 个推理 token |
| `chat_template_kwargs.thinking: false` | ❌ 仍然产生 378 个 |

后两个**会被接受**（HTTP 200），**静默地什么都不做**。这就是为什么这个常量在代码里被详细注释，而不是凭印象写。

### 结果

首 token 时间从 **4298 ms 降到 817 ms**（四轮中位数），而且 `[POINT:x,y:label]` 标签**四次全中**（4/4），仍然落在 0–1000 的归一化网格上。

### 这是用户的设置，不是 DeepSeek 的特例

每个服务商卡片上有一个「推理」开关，写 `ProviderProfile.visionReasoningEnabled`：

- 字段**只在开关处于「关闭推理」那一侧时才发**。
- 百炼**接受这个字段但忽略它**（HTTP 200，输出无变化，因为它本来就没有推理帧可关）。这正是「一个用户可见的开关能同时覆盖任何一个 🧠 服务商」的原因。
- 但如果开关在另一侧，就没必要浪费这几个字节。

**两个刻意的细节：**

**① 属性是 `Bool?` 而不是 `Bool`。** 合成的 `Codable` 遇到缺键会抛错——写成一个非可选的 `Bool`，会让**所有在这条设置存在之前写下的配置文件全部读不出来**。`nil` 在访问器里读作「关」，而开关会写入显式的 `true`/`false`，所以用户一旦做过选择，文件里就记下来了。

**② `allowsVisionReasoning` 的默认值是 `false`（关推理）。** 一个从没打开过设置窗口的用户直接拿到快的那条路。

## 四、`max_tokens` 的天花板由**最窄的那个**服务商决定

一个常量要同时服务所有服务商，所以它必须在**每一个**上都合法。而它们的天花板差一个数量级（2026-09-21 逐个探测）：

| 服务商 | 接受范围 |
|---|---|
| DeepSeek | `[1, 393216]` |
| 百炼 | `[1, 32768]`，超过报 `InternalError.Algo.InvalidParameter` |

**32768 是两边都合法的最大值**，所以默认值就是它。往 DeepSeek 的上限靠，**用户一切回百炼，🧠 立刻坏掉**。

两个边界都用真实的 1.2 MB 截图 + App 自己的 4923 字提示词复测过：都还能答，都还能吐 `[POINT:…]`。

这现在是「看与截图」页上的滑块（**单次回答字数上限**，范围 `256...32768`，步长 256），存在 `AppSettings.visionMaxCompletionTokens`，`clamped()` 负责把它夹回范围。

**为什么这个预算不能给得太小**：推理模型的思考**也算在这个预算里**，预算耗尽时返回的是 **HTTP 200 + 空的 `content`**，不是错误。视觉客户端现在会把这种情况**抛成异常**，而不是当作「什么都没发生」。

## 五、DeepSeek 上只有一个模型能当 🧠

2026-09-21 实测：端点只暴露两个模型。

| 模型 | 结果 |
|---|---|
| `deepseek-v4-pro` | **直接拒绝截图**（"Unsupported Image"） |
| `deepseek-flash` | 能看图、能回答，而且**会吐归一化的 `[POINT:…]` 标签** |

第二条是**不能假设**的部分——能看图不代表会用归一化网格指位置。所以 DeepSeek 服务商预填的 🧠 模型就是 `deepseek-flash`。

它同时是一个推理模型，所以第三节那套抑制逻辑是必须的。

## 六、TTS：两个端点族**不能混用**

百炼的语音合成有**两条不同的路由**，配错了会报一个**完全不指向真正原因**的错：`InvalidParameter: url error, please check url`。

| 端点 | 模型族 | 请求体字段 | 举例音色 |
|---|---|---|---|
| `/api/v1/services/audio/tts/SpeechSynthesizer` | Qwen-Audio-TTS / CosyVoice | `input.{text, voice, format, sample_rate}` | `yuxiaoyun_v3.1`、`yeqinghe_v3.1` |
| `/api/v1/services/aigc/multimodal-generation/generation` | Qwen-TTS | `input.{text, voice, language_type}` | `Cherry` |

**音色名也是族专属的**。把 Qwen-TTS 族的 `Cherry` 丢给 Qwen-Audio-TTS 端点，报的是：

```
[cosyvoice:]Engine error [411]
```

看不出是「你走错端点了」。

**所以模型、音色、请求体字段、路径这四样必须一起动。**

怎么判断一个模型属于哪一族：用阿里云自己的 CLI

```bash
bl model code --model <模型名>
```

它会给 Qwen-Audio-TTS 吐 **`tts_v2` 的 websocket 示例**，给 Qwen-TTS 吐 **HTTP 示例**。

## 七、403 的时候用户听到的是道歉，不是回答

`speakCreditsErrorFallback(failure:)` 会在**视觉调用或 TTS 调用抛错**时，用系统语音念一句固定的中文道歉。

问题在于：额度类失败（`AllocationQuota.FreeTierOnly`——免费额度用完、但控制台里「仅使用免费额度」还开着）走的就是这条路。**用户看到的现象是「不管问什么都回一句『抱歉，我这边出了点问题』」，而视觉模型其实答得好好的。**

这会让人以为是模型坏了，其实是**账号的问题**。

**现在的处理**：道歉保留（用户在等声音，什么都不说更糟），但同一个错误同时写进 `CompanionManager.lastErrorMessage`，**在面板里原样显示**，所以真正的原因永远不会被一句道歉盖住。

> **排查顺序：先查账号，再动管线。**

## 八、怎么测一个服务商能不能用

`ModelConnectionTester` 对**草稿配置**（还没保存的那份）每个角色发一个最小的请求：

| 角色 | 探针 |
|---|---|
| 🧠 | 一次不带图片的 chat |
| 👄 | 两个字 TTS |
| 👂 | 一次真实的 websocket 握手 |

这样用户在**下决心保存之前**就知道这个服务商行不行。它报的是**服务商自己的错误原文**，不是转译过的。

## 九、这一块的经验

| 经验 | 来自 |
|---|---|
| 路径由**协议**决定，不由 URL 决定 | DeepSeek 的 chat 路由没有 `/v1` |
| 「看起来合理」的开关要**量过才算数** | `enable_thinking` / `chat_template_kwargs` |
| 一个常量服务多个服务商时，取**最窄的**天花板 | `max_tokens` 32768 |
| 报错信息不指向根因时，去查**官方 CLI** | `bl model code --model …` 分辨 TTS 端点族 |
| 加非可选字段会让**旧配置文件读不出来** | `visionReasoningEnabled: Bool?` |
| 配置**每个请求现读**，不要初始化时捕获 | 保存即生效 |

## 十、⭐ Pi 那两个进程用哪个模型（2026-09-29 起）

决策大脑是 **Pi**（`PiAgentRunner`），它自己管模型 —— 我们不改 Swift 侧的任何请求代码，
只改 **`~/.pi/agent/models.json`**（pi 官方配置，`/model` 会重载；我们那两个常驻进程
**改完要重起进程**才生效，`PiAgentRunner` 靠"启动参数哈希变了就重起"自动做）。

**当前默认：`ark/doubao-seed-2.0-mini`**（火山方舟 coding plan），实时/执行两个进程都用它 ——
实时进程额外带 `--thinking off`（快），执行进程不带（走 pi 默认 = 开思考）。

### 加一个 provider（三行，实测模板）

```json
"ark": {
  "name": "火山方舟【coding plan】doubao",
  "baseUrl": "https://ark.cn-beijing.volces.com/api/coding/v3",
  "api": "openai-completions",
  "apiKey": "!cat /Users/mjm/.pi/agent/keys/ark-138.txt",
  "models": [{
    "id": "doubao-seed-2.0-mini",
    "input": ["text", "image"],
    "contextWindow": 131072,
    "maxTokens": 16384,
    "reasoning": true
  }]
}
```

**四条实测出来的硬规矩**：

1. **`baseUrl` 只到 `/v3`（或 `/v1`），别带 `/chat/completions`** —— SDK 自己拼，
   写全了会拼成双路径（官方文档与 dg-ai-notes 都点名过）。
2. **`apiKey` 用 `!cat <文件>`，key 不落明文**：key 文件放 `~/.pi/agent/keys/`（0600）。
   三种写法（`$ENV` / 字面值 / `!命令`）里这是最干净的一种。
3. **模型条目要声明能力，否则 pi 当成"瞎且不会想"**：不写 `input: ["text","image"]`
   就**不能看图**（`--list-models` 显示 images: no），不写 `reasoning: true` 就
   **没有思考档**（thinking: no）。doubao-seed-2.0-mini 这两样**实测都有**
   （64×64 纯红图 → 答"红色"；回复里带 `reasoning_content`）。
4. **`reasoning_effort: "none"` 火山认**（实测：返回正常内容、无 reasoning）——
   所以 `--thinking off` 在 ark 这条链上真的关得掉思考，实时模式能用。

### 怎么验一个端点（照 §8 的路子，先 curl 再进配置）

```bash
curl -s https://ark.cn-beijing.volces.com/api/coding/v3/chat/completions \
  -H "Authorization: Bearer $(cat ~/.pi/agent/keys/ark-138.txt)" \
  -H "Content-Type: application/json" \
  -d '{"model":"doubao-seed-2.0-mini","messages":[{"role":"user","content":"hi"}],"stream":true}'
```

配完再跑一次真进程：`pi --mode rpc --model ark/doubao-seed-2.0-mini --thinking off`
发一条 `prompt`，收到 `agent_settled` 且 `text_delta` 有字 = 通 ✓。

⚠️ **第二个 key（137）服务端拒了**：`AuthenticationError · The API key format is incorrect`，
带 `ark-` 前缀和不带都试过 —— 要么复制不全，要么它是另一个产品的 key。用之前先确认。
