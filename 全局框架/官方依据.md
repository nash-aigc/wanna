# 官方依据台账

**这不是文档，是证据。** 每一条 = 官方原文 + 我们的做法。

## 为什么要它（2026-09-29 用户定的）

用户原话：「**你在设计任何东西之前是不是没有这个习惯？我发现你总是看一下，但没有看全。**
……这个问题应该通过**系统级的方法、代码的方法、强制的方法或闸门的方法**，
强迫自己去做这件事……**如果没有官方数据做支撑，你现在所有的修改可能都偏离了，
要么缺失，要么反向矛盾。**」

同一天我犯了三次**形状完全一样**的错 —— 都是"读了，但没读全"：

| 我做了什么 | 漏了什么 |
|---|---|
| 读了 skill-creator 规范、还在回答里引用了三级披露 | 然后**反着实现**（把①也做成要调工具才知道） |
| 读了 SDK，发现 `defer_loading` | 然后**自己发明**一套"MCP 三级披露" |
| 读了 SDK 源码 `get_all_function_tools` | **没读官方 MCP 规范页** —— 所以不知道规范自己写着工具清单在上下文里 |

**共同点：我把"够回答眼前这个问题"当成了停止条件。**
正确的停止条件是：**这个东西在官方是怎么定义的，我手里有原文。**

## 怎么用

**动 agent 框架 / MCP / 技能之前，先往这里加一条，再改代码。**

每条三行，格式固定（闸门 `scripts/official-evidence-check.py` 按这个解析）：

```
SOURCE <URL 或文件路径>
QUOTE <官方原文，一行，逐字>
WHY <所以我们怎么做>
```

**闸门会真的去 fetch 每个 SOURCE，检查 QUOTE 是否真的在页面上。** 编的、记错的、过期的
—— 对不上就拒绝提交。这和「《项目全貌》事实核查」是同一个道理：**能被机器对上的才管得住。**

**查官方一律用 AnySearch**（不用内置搜索 —— 内置的经常超时、返回垃圾结果）。
**要看全，不是看一屏** —— 官方一页里往往就有推翻我方案的那一句。

## 台账

### 1. MCP 的工具清单就是「全量进模型上下文」的

SOURCE https://modelcontextprotocol.io/specification/2026-07-28/server/tools
QUOTE Deterministic ordering enables clients to reliably cache the tool list and improves LLM prompt cache hit rates when tools are included in model context.
WHY 规范自己假设工具清单就在模型上下文里，它关心的只是怎么让清单稳定以便命中 prompt cache。**所以"给 MCP 做三级披露"是我在发明机制**，不许做（2026-09-29 用户否掉）。

### 2. 工具的按需加载（defer_loading）只对 OpenAI Responses 模型有效

SOURCE https://openai.github.io/openai-agents-python/mcp/
QUOTE This is supported only on OpenAI Responses models.
WHY 我们用的是 `chat_completions` + DeepSeek。**官方那个懒加载口子我们用不了**，别照搬。本地 MCP（`MCPServerStdio` / `MCPServerStreamableHttp`）官方只提供 `tool_filter` 和 `cache_tools_list`，没有懒加载。

### 3. 官方推荐缓存 MCP 工具清单

SOURCE https://openai.github.io/openai-agents-python/mcp/
QUOTE cache_tools_list=True
WHY 官方示例里构造 MCP server 时都带这个参数。我们两个 MCP 连接都已经传了（2026-09-29 核对）。

### 4. 技能是三级披露：常驻的只有「名字 + 描述」

SOURCE /Users/mjm/.claude/skills/skill-creator/SKILL.md
QUOTE Skill information is disclosed in three stages:
WHY ①名字+描述在选择阶段就可得（= 在提示词里）②正文用得上时才读 ③附件最后。**所以"提示词为 0"做不到** —— 清单总得写在某处，官方实现也放提示词里。

### 5. 描述要「简短、有区分度」，不要罗列能力

SOURCE /Users/mjm/.claude/skills/skill-creator/SKILL.md
QUOTE Keep discovery cheap and precise.
WHY 规范说 skill names and descriptions are available before a skill is loaded —— 写得越长，它占的常驻上下文越大，而且罗列能力会**稀释区分度**。✅ **已收**（2026-09-29）：6 条过长的描述压过了 —— `search-max` 498→160、`cosyvoice-tts` 439→269、`notion` 258→87、`awesome-jev` 243→186、`macos-fast-action` 192→134、`image-station` 176→61。**常驻提示词里的技能清单 2 272 → 1 306 字符（−43%）**，功能一个字没删（`notion` 那条「提到创业必须保存」的规则本来就在正文第 14 行，只是从描述里挪走）。

### 6. 追踪：官方首选是「给 OpenAI key 用官方面板」，不是写处理器

SOURCE https://openai.github.io/openai-agents-python/tracing/
QUOTE When using non-OpenAI models, you can provide an OpenAI API key to the tracing exporter to enable free tracing in the OpenAI Traces dashboard without disabling tracing.
WHY 官方对**非 OpenAI 模型**的首选是"换个 key、用官方面板"，**零代码**。我一度把"官方支持 `add_trace_processor`"读成了"官方推荐写处理器"——**支持和推荐是两件事**，又是一次"读了 API 存在、没读推荐路径"。

### 7. 追踪导出打到 api.openai.com（写死的域名），且不在「OpenAI 兼容协议」里

SOURCE https://openai.github.io/openai-agents-python/tracing/
QUOTE custom trace processors to push traces to other destinations (as a replacement, or secondary destination)
WHY `BackendSpanExporter._OPENAI_TRACING_INGEST_ENDPOINT = "https://api.openai.com/v1/traces/ingest"`（源码实测）—— DeepSeek 这类"OpenAI 协议"的 key **不管用**，因为 `/v1/traces/ingest` 不属于那个协议（那只覆盖 chat/completions 那一类）。**用户 2026-09-29 选了官方明写的第二条路（自定义处理器）**，理由是 span 里装的是工具参数与**工具返回**（整棵界面文本、读到的文件内容），而这个仓库因为同样的理由删过一次 PostHog。

### 8. 官方的调用方式：**一个 Agent 对象，`Runner.run()` 反复调**

SOURCE https://openai.github.io/openai-agents-python/
QUOTE result = Runner.run_sync(agent, "Write a haiku about recursion in programming.")
WHY 官方 hello-world 就是这个形状：**建一次 `Agent`，然后 `Runner.run(agent, input)` 反复调**。我们的实现是**每轮起一个新 Python 进程、重建 Agent、重连 MCP** —— 那是自己设计的，不是官方的。实测每轮白付 **0.89 秒**。

### 9. 官方的状态携带：四选一，其中两个对我们可用

SOURCE https://openai.github.io/openai-agents-python/running_agents/
QUOTE There are four common ways to carry state into the next turn:
WHY 官方给的四种：`result.to_input_list()`（客户端存，**任何 provider 都能用**）、`session`/`SQLiteSession`（SDK 帮你存，**客户端管理**）、`conversation_id` 与 `previous_response_id`（**仅 OpenAI Responses API**）。官方明写：**前两个是 client-managed**。我们**一种都没用** —— 每轮只传这一轮的 `--task`，Agent 完全无记忆。

### 10. 连接建一次、Agent 复用，才是官方示例的形状

SOURCE https://openai.github.io/openai-agents-python/mcp/
QUOTE async with MCPServerStreamableHttp(
WHY 官方每一个 MCP 例子都是"**连接建一次 → 建 Agent → 反复 `Runner.run`**"。我们每轮新建连接。**"每轮起新进程"不只是慢，它是偏离官方调用方式。**

### 11. 状态策略**不能混用**

SOURCE https://openai.github.io/openai-agents-python/running_agents/
QUOTE Session persistence cannot be combined with server-managed conversation settings
WHY 官方明确：一次 run 里只能选一种。⚠️ 我们现在的"记忆在 Wanna 那边（Swift 重放历史轮次）"是**第五种、官方没有的做法** —— 要么改走官方的 `session`/`to_input_list()`，要么明确这是一处有意的偏离并写下来。

### 12. Sessions 是 client-managed，非 OpenAI provider 也能用

SOURCE https://openai.github.io/openai-agents-python/running_agents/
QUOTE result.to_input_list() and session are client-managed.
WHY 官方明写 `to_input_list()` 与 `session` 是**客户端管理**，只有 `conversation_id` / `previous_response_id` 是 OpenAI 托管。所以 `SQLiteSession` 我们可以用。**源码实测确认**：它只往 SQLite 存消息列表，没有任何 OpenAI 专属调用。⚠️ 一个坑：`db_path` 默认 `:memory:` —— 我们是每轮新进程，用默认值等于**每轮记忆从零开始，而且不报错**。

### 13.【历史存档 · 该 SDK 链已整条删除】官方历史窗口是 `limit`，数的是「条目」不是「轮」

SOURCE /Users/mjm/Documents/SuperAgent/Wanna/WannaAgent/.venv/lib/python3.14/site-packages/agents/memory/session_settings.py
QUOTE Maximum number of items to retrieve. If None, retrieves all items.
WHY 官方 `SessionSettings.limit` **默认 None = 取全部** —— 不设的话会话越聊越长，每轮把整段历史重发，**功能照常、只是越来越慢越来越贵，屏幕上完全看不出来**。它是撤掉 Swift 那套窗口/压缩之后**唯一的护栏**。⚠️ 它数的是**条目**（一次工具调用也是条目），而 Wanna 的设置项数的是**轮**，所以要做一次换算（认设置页「记住最近多少轮对话」那个值，不自己编数字）。

### 14. 「查更多历史」官方**没有**机制 —— 属应用层（所以可以自己写）

SOURCE https://openai.github.io/openai-agents-python/
QUOTE result = Runner.run_sync(agent, "Write a haiku about recursion in programming.")
WHY 官方 `Session` 的接口只有 `get_items(limit)` —— **"最近 N 条"，没有检索、没有翻页**（`agents/memory/session.py` 的 `Session` Protocol 就四个方法）。官方唯一带检索的是 `FileSearchTool`，但它是 **OpenAI 托管的 vector store**（Responses API），我们这种 provider 用不了。
**判定：在这个 provider 上，"查更多"官方没有机制 → 属应用层决定**（2026-09-29 那条新规矩允许这一类自己写，但必须在这里写明"不是替代 SDK 机制"）。
做法照抄**技能那套三级披露**：常驻少量（官方 `SessionSettings(limit:)`）+ 需要时模型自己调 `search_history` 翻完整历史。数据源必须是 SQLite 那张表 —— `ConversationSessions.json` 已经被 `trimConversationHistory` 裁过了，里面没有完整历史。

### 15.【历史存档 · 该 SDK 链已整条删除】官方压缩组件 `OpenAIResponsesCompactionSession` **用不了**

SOURCE /Users/mjm/Documents/SuperAgent/Wanna/WannaAgent/.venv/lib/python3.14/site-packages/agents/memory/openai_responses_compaction_session.py
QUOTE Works with OpenAI Responses API models only.
WHY 它是 **OpenAI Responses 专属**（`from openai import AsyncOpenAI`、"Must be an OpenAI model"）。所以"上下文压缩"在这个 provider 上**官方同样没有机制** —— 属应用层，可以自己实现（官方的 `SessionABC` 就是给这种自定义留的扩展点，`OpenAIResponsesCompactionSession` 自己就是一个 Session 装饰器）。

# Pi（2026-09-29 换血，取代 OpenAI Agents SDK）

用户判定：「**不再自己设计 agent，直接用现成的 agent**」—— 理由是 OpenAI Agents SDK 是 `0.x`，
半年 42 次发布且**没有任何稳定性承诺**（PyPI 实测：`langchain-core` 同期也是 42 次，
**所以差别不在频率，在 `0.x` vs `1.x` 的版本契约**）。
Pi 官方自称 **"a minimal agent harness"**，支持 skills / AGENTS.md、**skips sub-agents and plan mode**
（正好对上用户要的"没有内置功能，要就装扩展"）。

### P1. Pi 有四种运行模式，我们要用 RPC

SOURCE https://pi.dev/
QUOTE Four modes: interactive, print/JSON, RPC, and SDK
WHY 我们要 **RPC** —— 因为 Wanna 是 Swift（非 Node）。官方原话：*"For an in-process Node.js or Bun
integration, prefer the SDK. For a subprocess-based TypeScript integration, prefer the exported
`RpcClient`."* 两边都不是我们，所以用**裸 RPC 协议**。

### P2. RPC 是「长驻子进程 + JSONL」—— 正好解决我们每轮起新进程

SOURCE https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md
QUOTE RPC mode runs Pi as a long-lived subprocess controlled through JSON records on stdin and stdout.
WHY 启动：`pi --mode rpc --no-session`。**它同时解决三件事**：每轮起新进程（省 0.89s）、
会话要自己管（Pi 自己管）、上下游传递要自己写。

### P3. 分帧规则：**只在 LF 上切**

SOURCE https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md
QUOTE Do not use a generic line reader that treats Unicode line or paragraph separators as record boundaries.
WHY ⚠️ 官方点名 Node 的 `readline` 会在 `U+2028`/`U+2029` 上多切 —— 而那两个字符**在 JSON 字符串里是合法的**。
**查我们 Swift 侧**：`PythonAgentRunner` 用的是逐行读，要确认它不会在那两个字符上切。

### P4. `prompt` 成功 ≠ 跑完，要等 `agent_settled`

SOURCE https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md
QUOTE Wait for `agent_settled` when the client needs to know Pi will not continue automatically.
WHY ⚠️ **`agent_end` 不是终点** —— 官方明写其后还可能有 retries / overflow recovery / compaction /
steering / follow-up。**只等 `agent_end` 会把没跑完的一轮当成跑完**。

### P5. 必须先订阅事件、再发 prompt

SOURCE https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md
QUOTE Subscribe before sending a prompt to avoid missing a fast completion.
WHY 快速完成的 run 会在客户端装好监听之前就发完事件 —— 只等响应会**永久挂住**。

### P6. stdout 只走协议，日志走 stderr

SOURCE https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md
QUOTE Stdout is reserved for protocol records; diagnostics and application logging go to stderr.
WHY 我们那两条诊断日志（`主Agent诊断.log` 那种）**不能混进 stdout**，否则协议解析会炸。

### P7. Pi 官方支持 MCP（所以 19 个工具一个字不用改）

SOURCE https://pi.dev/packages
QUOTE MCP (Model Context Protocol) client extension for the Pi coding agent
WHY 官方包目录就有。**这是用户"MCP 是通用协议、不需要改"那个假设的官方依据。**

### P8. Pi 的技能就是 Agent Skills 规范 —— 三级披露，和我们那套同一个

SOURCE reference/pi/packages/coding-agent/docs/skills.md
QUOTE Pi implements the [Agent Skills specification](https://agentskills.io/specification).
WHY 官方逐字还有：*"At startup, Pi scans configured skill locations and adds each skill's
name, description, and path to the system prompt. **It does not add the full instructions.**"*
—— **这就是三级披露**（描述常驻、正文按需）。所以我们的技能**格式不用改**。

### P9. ⚠️ 技能名必须是「小写字母 / 数字 / 连字符」，上限 64 字符

SOURCE reference/pi/packages/coding-agent/docs/skills.md
QUOTE Names use lowercase letters, numbers, and hyphens, with no leading, trailing, or consecutive hyphens.
WHY **我们那 4 个中文名（图形 / 执行 / 文本 / 复盘）不符合这条**；而且同一页写着
*"Malformed SKILL.md files and declared skills without descriptions are not loaded."*
—— **加载不了，而且可能在屏幕上毫无提示**。迁移时必须改名（中文名放 description 里）。

### P10. 技能目录：Pi 认 `~/.agents/skills/` 与 `.agents/skills/`

SOURCE reference/pi/packages/coding-agent/docs/skills.md
QUOTE Pi also supports the Agent Skills locations `~/.agents/skills/` and `.agents/skills/`.
WHY 我们现在的技能在 `~/Documents/SuperAgent/APP/Design/wanna/skills/` —— **不在 Pi 认的位置**，
要挪或要配（见 settings.md#resources）。

### P11. 接第三方 OpenAI 兼容端点**不用写扩展**，配 `models.json` 就行

SOURCE reference/pi/packages/coding-agent/docs/custom-provider.md
QUOTE If the service already speaks a supported API, configure it in `models.json` instead.
WHY 官方选择表逐字：*"Add models behind a supported API → `models.json`"*。
**用户说的"用三方 OpenAI 协议就行"正是官方推荐的最小做法**，不用写 TypeScript provider 扩展。

### P12. 技能 description 上限 1024 字符

SOURCE reference/pi/packages/coding-agent/docs/skills.md
QUOTE descriptions can contain at most 1024
WHY 我们收过一遍之后最长的是 cosyvoice-tts（约 270 字符），**远在范围内** ✓

### P13. ⚠️ MCP **不在 Pi 核心里** —— 是第三方扩展

SOURCE https://pi.dev/packages/pi-mcp-adapter
QUOTE MCP (Model Context Protocol) adapter extension for Pi coding agent
WHY **实测：`extensions.md` 里没有 MCP 字样，整个 Pi 核心仓库也没有 MCP 集成**
（`grep -rli mcp` 只命中一个测试文件、一个图片工具、一个 OAuth 文件，全无关）。
MCP 支持来自 **第三方包**（官方 `pi.dev/packages` 上有两个）：
· `pi-mcp-adapter`（nicopreme，**1.2M/月**）→ `pi install npm:pi-mcp-adapter`
· `pi-mcp-extension`（irahardianto，103.7K/月）
**所以"19 个 MCP 工具不用改"成立，但前提是装一个第三方扩展** —— 它不是 Pi 核心的一部分，
升级与稳定性跟着社区走，不由 Pi 官方保证。

### P14. subagent 同样有现成第三方扩展

SOURCE https://pi.dev/packages/pi-subagents
QUOTE Pi extension for single-agent delegation and scripted multi-agent workflows
WHY Pi 核心自称 *"skips features like sub-agents"*（见 pi.dev 首页），而社区有 `pi-subagents`
（nicopreme，488.7K/月）。**这正是用户要的"没有内置功能，需要就装插件"** —— 有官方页面佐证。

### P15. 换血落地：OpenAI Agents SDK 那条链整条删除，Pi 顶上

SOURCE https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/rpc.md
QUOTE RPC mode runs Pi as a long-lived subprocess controlled through JSON records on stdin and stdout.
WHY 2026-09-29 完成：删 `wanna_agent.py` / `local_trace.py` / `PythonAgentRunner.swift` /
`requirements.txt` / venv 及全部旧实验脚本；新写 `Wanna/PiAgentRunner.swift`
（常驻 RPC、switch_session 按会话 UUID 对准、等 `agent_settled`、解析 `text_delta`
与 `tool_execution_*`、取消即发官方 `abort`）。端到端实测：合成转写提交 →
「1 加 1 等于 2」（1.9s，0 步）→「打开计算器」（1 步，Calculator 真的开了）。
会话映射实测：switch_session 指向不存在路径会创建、切走再切回记忆还在。

### P16. ⚠️⚠️ 官方源码：**没有 `read`/`bash` 就没有技能段** —— `--no-builtin-tools` 会静默杀掉技能

SOURCE reference/pi/packages/coding-agent/src/core/system-prompt.ts
QUOTE const skillFileReadTool = (["read", "bash"] as const).find((tool) => selectedTools.includes(tool));
WHY **2026-09-29 实测撞上的互斥**。起因是另一件事（见 P17）：Pi 拿内置 `bash` 把整件事
用自己的手重做了一遍，所以第一版修法是 `--no-builtin-tools`（内置全关）。
结果**技能整批消失**，而屏幕上、日志里什么都不说。金丝雀实测：往技能目录放一条
提到"紫色犀牛协议"的技能，问它认不认得 → 「没有」；换回 `--exclude-tools bash,edit,write`
（留 `read`）→ 「有：zz-canary-test」。
**只要这一行不变，Pi 的技能机制就绑死在 `read` 或 `bash` 上** —— 扩展/自定义工具顶不上去
（这里是个**写死的两个字面量数组**）。所以取舍只有一条：**留 `read`，去掉 `bash`/`edit`/`write`**。
真机复核（App 自己写的会话帧）：`toolsRemoved = [bash, edit, write]`，
`sections.tools` 只剩 `read / mcpScript / mcp / mcp__wanna`；同一轮问它技能清单，
我们的 11 条一条不少。

### P17. ⚠️⚠️ 官方源码：技能进提示词的是 **name + description + location（绝对路径）**，正文靠 `read` 去读

SOURCE reference/pi/packages/coding-agent/src/core/skills.ts

### P29. 什么叫"标签"、什么叫"标签的名字"（移交提示词的两个标签用哪个名字）

SOURCE https://developer.mozilla.org/en-US/docs/Glossary/Tag
QUOTE The name of an HTML element is the name that appears at the beginning of the element's start tag
WHY **2026-09-30 我把这两个概念搞混了，用户当场纠正**（他原话：
「**你要写的是标签的名字，标签的名字叫 goal**……你说的这个书签、这个特殊符号，**它本身就是标签**，

```xml
<history>（实时模式下的全部对话，一条不少）</history>
<goal>（用户最后问的那一句 —— 只有问题，没有回答）</goal>
```
