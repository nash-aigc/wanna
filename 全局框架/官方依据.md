# 官方依据台账

**这不是文档，是证据。** 每一条 = 官方原文 + 我们的做法。

## 为什么要它（2026-09-29 用户定的）

用户原话：「**你在设计任何东西之前是不是没有这个习惯？我发现你总是看一下，但没有看全。**
……这个问题应该通过**系统级的方法、代码的方法、强制的方法或闸门的方法**，
强迫自己去做这件事……**如果没有官方数据做支撑，你现在所有的修改可能都偏离了，
要么缺失，要么反向矛盾。**」

同一天我犯了三次**形状完全一样**的错 —— 都是"读了，但没读全"：

| 我做了什么 | 漏了什么 |
|---|---|
| 读了 skill-creator 规范、还在回答里引用了三级披露 | 然后**反着实现**（把①也做成要调工具才知道） |
| 读了 SDK，发现 `defer_loading` | 然后**自己发明**一套"MCP 三级披露" |
| 读了 SDK 源码 `get_all_function_tools` | **没读官方 MCP 规范页** —— 所以不知道规范自己写着工具清单在上下文里 |

**共同点：我把"够回答眼前这个问题"当成了停止条件。**
正确的停止条件是：**这个东西在官方是怎么定义的，我手里有原文。**

## 怎么用

**动 agent 框架 / MCP / 技能之前，先往这里加一条，再改代码。**

每条三行，格式固定（闸门 `scripts/official-evidence-check.py` 按这个解析）：

```
SOURCE <URL 或文件路径>
QUOTE <官方原文，一行，逐字>
WHY <所以我们怎么做>
```

**闸门会真的去 fetch 每个 SOURCE，检查 QUOTE 是否真的在页面上。** 编的、记错的、过期的
—— 对不上就拒绝提交。这和「《项目全貌》事实核查」是同一个道理：**能被机器对上的才管得住。**

**查官方一律用 AnySearch**（不用内置搜索 —— 内置的经常超时、返回垃圾结果）。
**要看全，不是看一屏** —— 官方一页里往往就有推翻我方案的那一句。

## 台账

### 1. MCP 的工具清单就是「全量进模型上下文」的

SOURCE https://modelcontextprotocol.io/specification/2026-07-28/server/tools
QUOTE Deterministic ordering enables clients to reliably cache the tool list and improves LLM prompt cache hit rates when tools are included in model context.
WHY 规范自己假设工具清单就在模型上下文里，它关心的只是怎么让清单稳定以便命中 prompt cache。**所以"给 MCP 做三级披露"是我在发明机制**，不许做（2026-09-29 用户否掉）。

### 2. 工具的按需加载（defer_loading）只对 OpenAI Responses 模型有效

SOURCE https://openai.github.io/openai-agents-python/mcp/
QUOTE This is supported only on OpenAI Responses models.
WHY 我们用的是 `chat_completions` + DeepSeek。**官方那个懒加载口子我们用不了**，别照搬。本地 MCP（`MCPServerStdio` / `MCPServerStreamableHttp`）官方只提供 `tool_filter` 和 `cache_tools_list`，没有懒加载。

### 3. 官方推荐缓存 MCP 工具清单

SOURCE https://openai.github.io/openai-agents-python/mcp/
QUOTE cache_tools_list=True
WHY 官方示例里构造 MCP server 时都带这个参数。我们两个 MCP 连接都已经传了（2026-09-29 核对）。

### 4. 技能是三级披露：常驻的只有「名字 + 描述」

SOURCE /Users/mjm/.claude/skills/skill-creator/SKILL.md
QUOTE Skill information is disclosed in three stages:
WHY ①名字+描述在选择阶段就可得（= 在提示词里）②正文用得上时才读 ③附件最后。**所以"提示词为 0"做不到** —— 清单总得写在某处，官方实现也放提示词里。

### 5. 描述要「简短、有区分度」，不要罗列能力

SOURCE /Users/mjm/.claude/skills/skill-creator/SKILL.md
QUOTE Keep discovery cheap and precise.
WHY 规范说 skill names and descriptions are available before a skill is loaded —— 写得越长，它占的常驻上下文越大，而且罗列能力会**稀释区分度**。✅ **已收**（2026-09-29）：6 条过长的描述压过了 —— `search-max` 498→160、`cosyvoice-tts` 439→269、`notion` 258→87、`awesome-jev` 243→186、`macos-fast-action` 192→134、`image-station` 176→61。**常驻提示词里的技能清单 2 272 → 1 306 字符（−43%）**，功能一个字没删（`notion` 那条「提到创业必须保存」的规则本来就在正文第 14 行，只是从描述里挪走）。

### 6. 追踪：官方首选是「给 OpenAI key 用官方面板」，不是写处理器

SOURCE https://openai.github.io/openai-agents-python/tracing/
QUOTE When using non-OpenAI models, you can provide an OpenAI API key to the tracing exporter to enable free tracing in the OpenAI Traces dashboard without disabling tracing.
WHY 官方对**非 OpenAI 模型**的首选是"换个 key、用官方面板"，**零代码**。我一度把"官方支持 `add_trace_processor`"读成了"官方推荐写处理器"——**支持和推荐是两件事**，又是一次"读了 API 存在、没读推荐路径"。

### 7. 追踪导出打到 api.openai.com（写死的域名），且不在「OpenAI 兼容协议」里

SOURCE https://openai.github.io/openai-agents-python/tracing/
QUOTE custom trace processors to push traces to other destinations (as a replacement, or secondary destination)
WHY `BackendSpanExporter._OPENAI_TRACING_INGEST_ENDPOINT = "https://api.openai.com/v1/traces/ingest"`（源码实测）—— DeepSeek 这类"OpenAI 协议"的 key **不管用**，因为 `/v1/traces/ingest` 不属于那个协议（那只覆盖 chat/completions 那一类）。**用户 2026-09-29 选了官方明写的第二条路（自定义处理器）**，理由是 span 里装的是工具参数与**工具返回**（整棵界面文本、读到的文件内容），而这个仓库因为同样的理由删过一次 PostHog。

### 8. 官方的调用方式：**一个 Agent 对象，`Runner.run()` 反复调**

SOURCE https://openai.github.io/openai-agents-python/
QUOTE result = Runner.run_sync(agent, "Write a haiku about recursion in programming.")
WHY 官方 hello-world 就是这个形状：**建一次 `Agent`，然后 `Runner.run(agent, input)` 反复调**。我们的实现是**每轮起一个新 Python 进程、重建 Agent、重连 MCP** —— 那是自己设计的，不是官方的。实测每轮白付 **0.89 秒**。

### 9. 官方的状态携带：四选一，其中两个对我们可用

SOURCE https://openai.github.io/openai-agents-python/running_agents/
QUOTE There are four common ways to carry state into the next turn:
WHY 官方给的四种：`result.to_input_list()`（客户端存，**任何 provider 都能用**）、`session`/`SQLiteSession`（SDK 帮你存，**客户端管理**）、`conversation_id` 与 `previous_response_id`（**仅 OpenAI Responses API**）。官方明写：**前两个是 client-managed**。我们**一种都没用** —— 每轮只传这一轮的 `--task`，Agent 完全无记忆。

### 10. 连接建一次、Agent 复用，才是官方示例的形状

SOURCE https://openai.github.io/openai-agents-python/mcp/
QUOTE async with MCPServerStreamableHttp(
WHY 官方每一个 MCP 例子都是"**连接建一次 → 建 Agent → 反复 `Runner.run`**"。我们每轮新建连接。**"每轮起新进程"不只是慢，它是偏离官方调用方式。**

### 11. 状态策略**不能混用**

SOURCE https://openai.github.io/openai-agents-python/running_agents/
QUOTE Session persistence cannot be combined with server-managed conversation settings
WHY 官方明确：一次 run 里只能选一种。⚠️ 我们现在的"记忆在 Wanna 那边（Swift 重放历史轮次）"是**第五种、官方没有的做法** —— 要么改走官方的 `session`/`to_input_list()`，要么明确这是一处有意的偏离并写下来。

### 12. Sessions 是 client-managed，非 OpenAI provider 也能用

SOURCE https://openai.github.io/openai-agents-python/running_agents/
QUOTE result.to_input_list() and session are client-managed.
WHY 官方明写 `to_input_list()` 与 `session` 是**客户端管理**，只有 `conversation_id` / `previous_response_id` 是 OpenAI 托管。所以 `SQLiteSession` 我们可以用。**源码实测确认**：它只往 SQLite 存消息列表，没有任何 OpenAI 专属调用。⚠️ 一个坑：`db_path` 默认 `:memory:` —— 我们是每轮新进程，用默认值等于**每轮记忆从零开始，而且不报错**。

### 13. 官方历史窗口是 `limit`，数的是「条目」不是「轮」

SOURCE /Users/mjm/Documents/SuperAgent/Wanna/WannaAgent/.venv/lib/python3.14/site-packages/agents/memory/session_settings.py
QUOTE Maximum number of items to retrieve. If None, retrieves all items.
WHY 官方 `SessionSettings.limit` **默认 None = 取全部** —— 不设的话会话越聊越长，每轮把整段历史重发，**功能照常、只是越来越慢越来越贵，屏幕上完全看不出来**。它是撤掉 Swift 那套窗口/压缩之后**唯一的护栏**。⚠️ 它数的是**条目**（一次工具调用也是条目），而 Wanna 的设置项数的是**轮**，所以要做一次换算（认设置页「记住最近多少轮对话」那个值，不自己编数字）。
