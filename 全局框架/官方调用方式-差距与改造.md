**完全地、100% 地采取官方的方案**。禁止再出现这种跟官方方案完全不一致的情况。」

这份文档是**改造前的差距清单**，每条都带官方原文（台账 `官方依据.md` 第 8–11 条）。

---

## 一、官方是怎么调的

**最小形状**（官方 Overview 逐字）：

```python
agent = Agent(name="Assistant", instructions="...")
result = Runner.run_sync(agent, "...")
```

**MCP 的形状**（官方 MCP 页每个例子都是）：

```python
async with MCPServerStreamableHttp(...) as server:      # 连接建一次
    agent = Agent(..., mcp_servers=[server])
    result = await Runner.run(agent, "...")              # Agent 复用
```

**跨轮状态**（官方 "Choose a memory strategy"，四选一）：

| 策略 | 状态在哪 | 对我们 |
|---|---|---|
| `result.to_input_list()` | 你的内存 | ✅ **任何 provider 都能用** |
| `session` / `SQLiteSession` | 你的存储 + SDK | ✅ 可用（**client-managed**） |
| `conversation_id` | OpenAI 服务器 | ❌ 仅 Responses API |
| `previous_response_id` | OpenAI 服务器 | ❌ 仅 Responses API |

官方明写：`to_input_list()` 与 `session` 是 **client-managed**；后两个**只适用于 OpenAI Responses API**。
⚠️ **一次 run 只能选一种**（"Session persistence cannot be combined with…"）。

## 二、我们现在的实现（对不上的地方）

| 官方 | 我们 | 后果 |
|---|---|---|
| 一个 Agent 对象、反复 `Runner.run()` | **每轮起一个新 Python 进程**，重建 Agent | 每轮白付 **0.89 s**（实测） |
| MCP 连接建一次 | **每轮重连** | 同上 |
| 用 `to_input_list()` / `session` 带状态 | **一种都没用** —— 每轮只传 `--task` | Agent 无记忆 |
| 状态策略四选一 | **第五种：记忆放在 Wanna 那边**（Swift 重放历史轮次） | 官方没有这个做法 |

---

## 三、改造方案（待做）

**① Python 侧改成常驻 + 一条 IPC 通道**

- 进程启动一次，`Agent` 建一次，`MCPServerStreamableHttp` 连一次（`async with` 包住整个生命周期）
- Wanna 每轮把任务发过去、读回结果 —— 通道用本地 socket（stdout 一问一答的 subprocess 不再适用）
- **省掉每轮 0.89 s 的启动**

**② 状态走官方机制**

- 按**会话 id** 建 `SQLiteSession`（或自己持有 `to_input_list()` 的结果）
- **正好对上用户问的「新建对话怎么办」**：新建对话 = **换一个 session id**，官方就是这么设计的
- 要决定的是：**Wanna 那边现有的历史重放要不要撤**。官方只允许一种策略，两套并存就是第 11 条禁止的混用

**③ 进程生命周期（用户 2026-09-29 的要求）**

> 「用户结束这一轮使用时，它不自动退出，可以常驻，也可以等待几个小时之后自动退出……
> 如果它不特别耗进程，可以常驻，系统开机就自动常驻。」

- 常驻 + 空闲 N 小时后自动退出（跟 `audioEngineIdleReleaseMinutes` 同一个形状）
- 实测空跑一个 Python 进程 **28 ms**、常驻内存待测
